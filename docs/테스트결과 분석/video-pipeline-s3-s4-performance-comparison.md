## 1. Executive summary

1. 네 실행 모두 24/24 READY다. S3·S4 양쪽에서 성공률은 100%로 같고, 최종 실패·누락 영상은 0건이다.
2. 대표 처리량(회차 makespan 기준)은 S3 48.02 → 56.37편/시(+17.4%), S4 29.34 → 33.43편/시(+13.9%)로 올랐다. 단 S4 리팩토링은 embedding text가 192 → 180개(-6.25%)로 줄었으므로, 작업량을 맞춰 보정하면 S4 개선폭은 +6.8%다.
3. 사용자 관점 완료 지연은 S3 평균 440.8 → 390.8초(-11.3%), p95 594.4 → 522.4초(-12.1%)다. S4는 평균 915.6 → 700.2초(-23.5%), p95 974.4 → 876.2초(-10.1%)다.
4. 초기 Queue 대기는 S3 평균 153.1 → 72.0초(-53.0%), S4 평균 436.0 → 157.5초(-63.9%), S4 p95 897.8 → 278.2초(-69.0%)다.
5. S4의 선두 작업 막힘은 해소됐다. 구버전은 3회차 모두 long 4개가 전부 끝난 뒤에야 short 4개가 완료됐다(short가 마지막 long보다 먼저 완료된 건수 0/12). 리팩토링은 12/12가 마지막 long보다 먼저 완료됐고 3/12는 첫 long보다도 먼저 끝났다.
6. Cloud Run Worker의 지속 사용률은 S4에서 올랐고(CPU 50% 이상 표본 15.8% → 25.0%, 75% 이상 8.8% → 18.8%) S3에서는 오히려 내렸다(50% 이상 12.5% → 3.7%). embedding VM은 양쪽 모두 지속 사용률이 올랐다(container CPU 50% 이상 표본 S3 43.6% → 57.8%, S4 54.5% → 62.3%).
7. 가장 크게 개선된 것은 embedding endpoint의 입장 대기다. S3 평균 13.44 → 0초, S4 평균 52.05 → 0초이고, 구버전 S3에 있던 503 queue timeout 재시도 32건이 리팩토링에서는 0건이다.
8. 명확한 퇴행은 두 가지다. long 영상의 초기 Queue 대기가 평균 0.76 → 59.45초로 늘었고, long 한 편의 normalization 실행시간이 구버전 download+audio 합 66.2초 대비 110.3초로 늘었다(그중 프레임 후보 추출이 평균 79.5초).
9. 현재 1순위 병목은 `EMBED_BATCH` 실행 슬롯이다. 대기 작업이 있는 표본이 S3 53.3%·S4 58.1%인데 그 동안 슬롯은 100% 차 있었고(빈 슬롯 비율 0.0%·0.3%), 대기 중 최고 대기 나이는 S3 p95 119.4초·S4 p95 379.3초다. 완료 지연에서 마지막 enrichment 이후 구간이 차지하는 비중은 S4 long 411.9초/709.0초(58.1%), short 376.6초/691.5초(54.5%)다.
10. 다음 실험의 1순위는 stage 동시성이 아니라 **연산 코어**다. 두 병목 모두 코어 수가 실체다. embedding endpoint는 `e2-standard-4`의 연산 코어 2개(vCPU 4개 = 물리 코어 2 + 하이퍼스레드 2)를 이미 다 쓰고 있고, Worker는 CPU 한도가 1 vCPU인데 normalization을 2개씩 돌린다. 같은 "동시 1 → 2"라도 코어 안에서 일어난 embedding은 1건당 1.07배로 끝나 처리율 +88%였고(5.9), 코어를 넘어선 normalization은 1.84배가 되어 +9.0%에 그쳤다(5.4). 따라서 동시성을 더 올리는 대신 Worker CPU 한도와 embedding VM 코어 수를 올리는 쪽이 먼저다. 입력 길이 축소도 총량을 직접 늘리며, 512 → 256에서 처리량 2.11배가 이미 측정돼 있다.

### 2.4 S3 구버전의 `EMBEDDING_MAX_LENGTH`에 관한 데이터 계보

**사실.** `20260816T122033Z-video-s3/environment.json`의 `runtime_config.availability`는 `unavailable_legacy_not_captured`다. 즉 실행 당시 설정이 artifact에 직접 기록되지 않았다. 같은 파일의 `recovery_context.embedding_vm_snapshot_at_migration.config.EMBEDDING_MAX_LENGTH=256`에는 `This is not the historical test-time configuration.` 경고가 붙어 있으므로 실행 설정으로 읽지 않는다.

**개발로그 근거.** `agent_memory/inbox/2026-08-16.md`(181~183행)에 Terraform 전체 apply 없이 실행 중이던 VM `.env`와 컨테이너에 1024를 반영했고 컨테이너 환경값이 1024임을 확인했다는 기록이 있다. `agent_memory/inbox/2026-08-25.md`(86~89행)은 같은 사실과 함께, 이후 VM 재생성 때 startup metadata의 256으로 되돌아가 S4-256이 만들어졌다고 기록한다.

**artifact 자체의 교차 확인.** 개발로그 외에 산출물만으로도 확인할 근거가 있다. 입력 길이가 거의 같은 조건에서 endpoint 추론시간이 max length에 따라 크게 갈린다.

| 실행 | 선언된 max length | batch 4 요청 payload 평균 | batch 4 추론시간 평균 |
|---|---|---:|---:|
| S4 `maxlen256` (비교 제외 자료) | 256 (artifact에 기록됨) | 15,559 B | 19.3초 |
| S4 리팩토링 | 1024 (artifact에 기록됨) | 14,714 B | 86.8초 |
| S3 리팩토링 | 1024 (artifact에 기록됨) | 7,112 B | 42.3초 |
| **S3 구버전** | **기록 없음** | **7,060 B** | **37.1초** |

같은 S4 작업량에서 256과 1024의 추론시간 비는 86.8/19.3 = 4.5배다. S3 구버전이 256이었다면 batch 4 추론시간은 42.3/4.5 ≈ 9.4초 부근이어야 하는데 실제는 37.1초로, 확인된 1024 실행(42.3초)과 12% 차이다. 비교 대상 네 실행과 위 256 실행을 합친 다섯 실행의 `max_text_chars` 평균은 1,708~1,757자로 서로 비슷해 입력 길이 차이로 설명되지 않는다.

**결론과 한계.** 실행 당시 1024 적용은 개발로그로 확인되며 산출물의 추론시간으로도 뒷받침된다. 다만 원본 artifact의 runtime config 필드에는 기록되지 않았다. 이 항목은 "간접 근거로 강하게 뒷받침되지만 artifact 단독으로는 증명되지 않음"으로 둔다.

한 가지 더 적어 둔다. S3 구버전의 `embedding.admission` 대기시간은 입장 시도 80건 기준 p90 20.0005초, p95 20.0007초, 최댓값 20.0011초로 20초에 붙어 끊긴다. 그중 32건이 `queue_timeout`이다. 이는 실행 당시 endpoint 입장 대기 제한이 20초였다는 그 실행 자체의 직접 근거다. `recovery_context` 스냅샷의 `VIDEO_PREPROCESS_WAIT_TIMEOUT_SEC=20`이 우연히 같은 값이지만, 스냅샷을 실행 설정의 근거로 쓴 것이 아니라 실행 이벤트에서 나온 값이다.

근거 파일: `20260816T122033Z-video-s3/events.jsonl`(`embedding.admission`), `comparison-excluded/20260817T033406Z-video-s4-maxlen256/events.jsonl`, `metrics.json > embedding_max_length_probe`.

## 3. 시간 구간과 지표 정의

아래 정의를 서로 섞지 않는다. 모든 지표는 `metrics.json > definitions`에도 같은 문장으로 들어 있다.

| 지표 | 정의 | 계산 근거 |
|---|---|---|
| runner wall-clock | `environment.started_at` → `finished_at` | `environment.json` |
| workload active window | 첫 `complete_started_at` → 마지막 `terminal_observed_at` | `video-results.jsonl` |
| 회차 makespan | 해당 회차의 첫 `complete_started_at` → 그 회차 마지막 `terminal_observed_at` | 회차는 요청 시작 간격이 120초를 넘으면 나눈다 |
| 사용자 관점 완료 지연 | `complete_responded_at` → `terminal_observed_at` | `video-results.jsonl` |
| 초기 Queue 대기 | `complete_responded_at` → 그 영상의 첫 Worker 작업 시작. 구버전은 `pipeline.stage.started(stage=download)`, 리팩토링은 `pipeline.work.started(stage=NORMALIZE_VIDEO)` | `events.jsonl` |
| stage 실행시간 | 구버전 `pipeline.stage.started`→`finished`, 리팩토링 `pipeline.work.succeeded.execution_ms` | `events.jsonl` |
| stage span | 그 stage 작업들의 가장 이른 시작 → 가장 늦은 종료 | `events.jsonl` |
| embedding tail | 그 영상의 마지막 `enrichment.completed` → `terminal_observed_at` | 리팩토링 전용. embedding 대기 + 실행 구간 |
| slowdown ratio | 완료 지연 / 영상 재생시간 | `fixtures.json`의 `duration_seconds` |

percentile은 정렬 표본에 선형 보간을 쓴다(numpy `linear`, R type 7). 반복이 3회뿐이라 회차별 원값과 변동계수를 함께 싣고 통계적 유의성은 주장하지 않는다.

리팩토링 stage는 서로 겹치므로 stage span을 더해 전체시간을 만들지 않았다. 구버전의 stage 실행시간 합은 영상 단위 순차 실행이라 영상 처리시간과 거의 같지만, 리팩토링에서는 그렇지 않다.

**사실.** S3는 embedding text가 양쪽 모두 192개로 같다. 작업량 보정을 해도 처리량 개선율은 +17.4% 그대로다. 회차 사이 업로드 공백은 구버전 88.3초, 리팩토링 91.4초로 비슷해 대표 지표를 왜곡하지 않는다. observability 수집 구간은 `finished_at` 뒤에 있어 wall-clock에 들어가지 않는다(관측 tail -0.8초, -0.6초로 사실상 0).

**해석.** 리팩토링은 같은 작업량을 15% 짧은 시간에 끝냈다. 개선의 출처는 4.3에서 본다.

**한계.** 반복 3회다. 회차별 편/시는 구버전 47.06/48.67/48.37, 리팩토링 54.47/57.25/57.51로 두 집단이 겹치지 않지만, 표본이 작아 유의성을 주장하지 않는다.

여섯 stage 평균의 합은 285.5초다. 여기에 초기 Queue 대기 평균 153.1초를 더하면 438.6초로, 실제 완료 지연 평균 440.8초와 거의 일치한다. 즉 구버전 S3의 완료 지연은 "Queue에서 기다린 시간 + 순차 처리시간"으로 거의 전부 설명된다.

리팩토링 stage는 작업 단위이고 서로 겹친다.

| stage (리팩토링) | 실행 건수 | 실행시간 평균 | p95 | 최댓값 | Queue 대기 평균 | 관측 최대 동시 | slot 점유율 |
|---|---:|---:|---:|---:|---:|---:|---:|
| NORMALIZE_VIDEO | 24 | 36.3초 | 74.7초 | 76.9초 | 0.5초 | 2 | 33.0% |
| TRANSCRIBE_PART | 24 | 133.9초 | 153.6초 | 204.7초 | 0.3초 | 7 | 31.7% |
| ENRICH_CHUNK | 192 | 2.1초 | 4.2초 | 14.4초 | 0.8초 | 4 | 7.8% |
| EMBED_BATCH | 57 | 35.8초 | 45.9초 | 46.9초 | 0.2초 | 2 | 71.1% |

"관측 최대 동시"는 `pipeline-db` 표본의 `dispatched_count + running_count` 최댓값이다. 이벤트 구간이 겹치는 것으로 세면 한 작업의 종료와 다음 작업의 시작이 1밀리초 미만 겹치는 경계에서 1 크게 나올 수 있어(S4 `EMBED_BATCH`에서 실제 발생) 표본 쪽 값을 썼다. slot 점유율은 `실행시간 합 / (관측 최대 동시 × stage span)`이다.

영상 1편 기준 리팩토링의 완료 지연 분해(평균):

- 초기 Queue 대기 72.0초
- NORMALIZE~ENRICH 구간 span 170.4초
- 마지막 enrichment → terminal(embedding tail) 148.5초
- 합계 390.9초 (실제 완료 지연 평균 390.8초)

**사실.** 구버전에서 영상 1편당 121.0초를 쓰던 embedding stage가, 리팩토링에서는 batch 단위 35.8초짜리 작업 57건으로 쪼개졌다. 구버전 STT 120.0초와 리팩토링 TRANSCRIBE_PART 133.9초는 medium 영상이 한 part라 사실상 같은 일이다.

**해석.** 개선은 각 stage를 빠르게 만들어서 온 것이 아니다. 구버전은 영상 4편만 동시에 돌 수 있었고 한 편 안에서는 모든 stage가 줄 서 있었다. 리팩토링은 stage를 별도 작업으로 쪼개 서로 다른 영상의 서로 다른 stage가 겹치게 만들었다. TRANSCRIBE_PART가 최대 7개 동시에 돈 것이 그 직접 증거다.

**한계.** medium은 한 part짜리라 part 병렬화의 효과가 S3에는 나타나지 않는다. S3의 개선은 "영상 간 stage 겹침" 효과에 가깝다.

| **EMBED_BATCH** | **2.01 / 6.0 / 7** | **1.26 / 2** | **53.3%** | **61.6%** | **0.0%** | **62.8 / 119.4 / 134.4초** |

`EMBED_BATCH`만 "슬롯이 모두 찬 표본 비율(61.6%)"이 "대기 있는 표본 비율(53.3%)"보다 크다. 대기가 없을 때도 슬롯 2개를 계속 쓰고 있었다는 뜻이다.

**대기열이 끝까지 남는가.** 표본을 앞·중간·뒤 1/3로 나눈 ready 평균은 `EMBED_BATCH` 2.36 → 1.78 → 1.90, `NORMALIZE_VIDEO` 0.90 → 1.12 → 1.05다. 단조 증가하지 않고, 모든 Queue와 stage 테이블이 실행 종료 시점에 0으로 비었다. 구버전 `PREPROCESS_REQUEST`도 1.94 → 1.91 → 1.94로 평평하다가 0으로 끝난다. S3는 8편씩 3번 던지는 유한 wave 테스트라 대기열이 발산할 수 없는 구조다. 따라서 "대기열이 계속 늘어난다"는 병목 신호는 이 시나리오에서 원리상 관측될 수 없고, 대신 "wave 안에서 대기가 쌓이는 동안 슬롯이 항상 차 있었는가"를 판정 근거로 썼다.

pgmq 쪽 `EMBED_BATCH` ready는 평균 0.00이다. 리팩토링은 슬롯이 빌 때만 Queue에 메시지를 내보내므로, 실제 대기는 pgmq가 아니라 stage 작업 테이블에 쌓인다. 이 둘을 같은 값으로 보면 안 된다.

**병목 판정(세 조건 모두 확인).**

1. `EMBED_BATCH`는 대기 작업이 존재한 표본이 53.3%이고, 대기 중 oldest age p95가 119.4초다.
2. 대기가 있는 동안 실행 슬롯이 비었던 표본은 0.0%다. 슬롯 2개가 항상 차 있었다.
3. 이 구간은 완료 지연의 38.0%(148.5초/390.8초)를 차지하는 마지막 구간이다.

**해석.** S3 리팩토링의 1순위 병목은 `EMBED_BATCH` 실행 슬롯이다. 두 번째는 `NORMALIZE_VIDEO`로, 대기 표본 31.6%에 대기 중 oldest age p95 163.8초다. 다만 대기 중에도 슬롯이 빈 표본이 29.4%라 순수한 슬롯 부족만은 아니다.

`ENRICH_CHUNK`는 대기가 생겨도 슬롯이 65.6% 비어 있었다. 슬롯 부족이 아니라 상류에서 chunk가 몰려 들어왔다가 금세 소화되는 형태다. 병목으로 보지 않는다.

**병목 이동.** 구버전의 병목은 "영상 4편 동시 실행 상한"이었다(Queue oldest age p95 565.1초). 리팩토링에서 그 상한은 사라졌고, 병목은 파이프라인 마지막의 embedding 슬롯으로 옮겨갔다. 제거가 아니라 이동이다.

**사실.** 구버전 short의 완료 지연 946.6초 중 871.2초(92.0%)가 초기 Queue 대기다. stage 실행시간 합은 73.2초에 불과하다. 리팩토링에서는 short 12편 전부가 그 회차의 마지막 long보다 먼저 끝났고, 12편 모두 어떤 long이 실행 중일 때 완료됐다.

**해석.** 선두 작업 막힘은 해소됐다. 이것은 short 우선 처리가 아니다. 정책상 short에 우선순위를 준 적이 없고, 3회차에서는 long 2편이 short보다 먼저 끝났다. 정확한 서술은 "long이 끝날 때까지 short가 시작조차 못 하던 구조가 사라져 완료 순서가 섞이고 short의 대기가 70% 줄었다"이다.

**한계.** 구버전 Worker 동시성이 4였고 long이 정확히 4편이라 short가 완전히 밀린 것이다. 동시성이 5 이상이었다면 구버전도 일부 섞였을 수 있다. 즉 이 개선은 stage 분리 자체와 "Worker 동시성 4"라는 구버전 설정이 함께 만든 대비다.

**제안.** `NORMALIZATION_CONCURRENCY`를 3으로 올리는 방향은 권하지 않는다. 1 vCPU에서 3개를 돌리면 1건당 3배에 가깝게 느려지고 처리율은 거의 늘지 않을 것으로 본다. 대신 두 가지다. 첫째, Worker의 CPU 한도를 올려 동시성 2가 제값을 하게 한다. 둘째, 실행시간의 71~75%를 차지하는 프레임 후보 추출을 이 단계에서 분리한다(5.5). 프레임 추출을 빼면 normalization은 대부분 I/O가 되어 코어 1개에서도 두 작업이 실제로 겹칠 수 있다.

**한계.** 위 1.84배는 S3(medium, 프레임 13장)에서 나온 값이다. S4의 long은 프레임이 29장이라 CPU 비중이 더 크므로 2.00배에 더 가까울 수 있으나, S4는 동시성 1로 완주한 실행이 없어 확인하지 못했다.

**normalization의 프레임 추출 비중.** 리팩토링 normalization은 GCS에서 스트리밍으로 읽고(media 준비 평균 0.43초) probe → audio part 추출 → 프레임 후보 추출을 한다.

|---|---:|---:|---:|

**해석.** "전체 디코딩을 없앴다"는 것과 "normalization 단일 영상 시간이 줄었다"는 다른 이야기다. long 기준 구버전 download 37.9초 + audio 28.3초 = 66.2초였는데 리팩토링 normalization은 110.3초다. 44.1초 늘었고 그 대부분이 새로 들어온 프레임 후보 추출(79.5초)이다. 즉 리팩토링은 다운로드를 없앤 대신 이 단계에 프레임 추출을 앞당겨 넣었고, 단일 영상 기준으로는 이 단계가 느려졌다.

**프레임 작업 총량은 어떻게 됐나.** 구버전은 프레임을 chunk마다 뽑았다. 구버전 S4의 `enrichment.step`을 영상 단위로 합치면 다음과 같다.

| 작업 | 구버전 (chunk마다) | 리팩토링 (normalization에서 한 번) |
|---|---|---|
| long 1편의 프레임 추출 총 시간 | 95.6초 (14회 × 평균 6.50초) | 79.5초 (1회, 29장) |
| long 1편의 프레임 업로드 총 시간 | 11.5초 (14회 × 평균 0.73초) | 1.7초 (29회, `gcs.operation.succeeded(upload_frame_candidate)`) |
| short 1편의 프레임 추출 총 시간 | 8.4초 (2회 × 평균 6.50초) | 2.7초 (1회, 2장) |
| short 1편의 프레임 업로드 총 시간 | 0.2초 (2회) | 5.1초 (2회) |
| long 1편의 Vision 총 시간 | 45.1초 (14회 × 평균 3.18초) | 62.4초 (14회 × 평균 4.43초) |
| short 1편의 Vision 총 시간 | 5.8초 (2회 × 평균 3.18초) | 1.7초 (1회 × 평균 1.55초) |

short의 프레임 업로드만 0.2 → 5.1초로 늘었는데, 이는 업로드 건수가 아니라 건당 시간(long 0.06초 대비 short 2.55초) 차이다. short 프레임 업로드가 다른 영상 작업과 겹치는 혼잡 구간에 몰렸을 가능성이 있으나, 이 산출물로 확정할 수 없다. 절대값이 작아 완료 지연에 주는 영향은 미미하다.

즉 프레임 추출 총량은 long 기준 95.6 → 79.5초로 16.8% 줄었다. 문제는 총량이 아니라 위치다. 구버전은 이 일을 `chunk_enrichment` 안에서 chunk 단위로 나눠 했고, 리팩토링은 normalization 한 작업에 몰아넣었다. normalization 슬롯이 2개뿐이라, 이 stage의 회전이 느려지면 그 뒤 모든 단계의 공급이 늦어진다.

**한계.** 두 버전이 같은 일을 다른 단계에서 한다. 단계별 시간을 1:1로 빼는 것은 맞지 않고, 위 비교는 "같은 일의 총량과 위치가 어떻게 바뀌었는지" 확인용이다. 구버전 `chunk_enrichment` stage 실행시간(long 평균 82.8초)이 그 안의 step 시간 합(152.9초)보다 짧은 것은 chunk들이 stage 안에서 동시에 처리됐기 때문이다. 이 값들을 stage 시간과 직접 더하거나 빼지 않았다.

구버전 S3에는 `enrichment.step` 이벤트가 없어 같은 분해를 할 수 없다.

**assembly.** 리팩토링에서 새로 생긴 transcript 조립 단계는 별도 Queue 작업이 아니라 STT part 완료 뒤 호출된다. 실행시간은 S3에서 24건 평균 1.0초(중앙값 0.11초, 최댓값 3.3초), S4에서 35건 평균 1.7초(중앙값 0.15초, p95 8.0초, 최댓값 16.5초)다. 이와 별도로 아직 이어 붙일 part가 없어 아무 일도 하지 않고 끝난 호출이 S3 24건·S4 25건 있었다(`assembly.skipped`, outcome `inactive_or_no_contiguous_parts`). 조립 자체가 전체 완료시간에 주는 영향은 무시할 수준이다.

**enrichment 내부.** 리팩토링 S4의 keyframe 준비는 GCS 다운로드 평균 1.0초·업로드 평균 1.0초다. Vision 요청은 long chunk 평균 4.43초, short chunk 평균 1.55초, 전체 평균 4.2초(p95 10.4초)다. S3 리팩토링은 평균 1.88초(p95 3.6초)다. 구버전 S4의 Vision은 chunk당 평균 3.18초였다.

**사실.** long chunk의 Vision 요청시간이 3.18 → 4.43초로 39% 늘었다.

**해석.** 원인은 확정할 수 없다. 외부 Gemini 응답 변동, 리팩토링에서 늘어난 enrichment 동시 실행(관측 최대 4)으로 인한 요청 겹침, 실행 시간대 차이가 모두 후보다. 리팩토링 S4에는 429 1건과 ReadTimeout 2건이 있었고 구버전 S4에는 제공자 실패 이벤트가 없었다는 점이 "동시 요청이 늘어 외부 API가 더 밀렸다"는 방향을 약하게 지지한다. `enrichment` 자체는 슬롯 부족 병목이 아니므로(대기 있는 표본 15.0%, 그중 빈 슬롯 37.2%) 전체 완료시간에 준 영향은 크지 않다.

### 5.9 endpoint 동시성을 더 올리면 되는가

이 실행만으로는 `EMBED_BATCH` 슬롯을 2에서 4로 늘렸을 때의 결과를 알 수 없다. 판단에 쓸 수 있는 측정값을 모아 정리한다. 아래 수치는 모두 원본 산출물 또는 원자료 문서에 기록된 실측값이다.

**사실 1 — 이 VM의 연산 코어는 2개다.**

`(source)2026-08-09-검색-임베딩-동시성설정-적용후-재측정-원자료.md` 3절에 `e2-standard-4`의 CPU 구성이 "vCPU 4개, 물리 코어 2개 + 하이퍼스레드 2개"로 기록돼 있다. 현재 설정인 동시 실행 2 × 스레드 1은 연산 코어 2개를 하나씩 쓰는 상태다.

**사실 2 — 이 파이프라인에서 슬롯 1 → 2는 1건당 7%만 느려졌다.**

4.7의 중간 설정 S3와 최종 S3를 비교하면 슬롯 증가 효과를 직접 측정할 수 있다. 두 실행의 embedding endpoint 설정은 완전히 같고(`MAX_CONCURRENCY=2`, `INFERENCE_THREADS=1`, `max_length=1024`), Worker가 동시에 보내는 요청 수만 1에서 2로 달랐다.

| | batch 4 추론시간 | text 1건당 payload |
|---|---:|---:|
| 동시 요청 1 (`00094-xtl`) | 39.7초 (n=43) | 1,781 B |
| 동시 요청 2 (`00095-jk6`) | 42.3초 (n=43) | 1,778 B |

입력 길이가 사실상 같은 조건에서 **1.07배**만 느려졌다. 요청 두 개가 각각 진짜 코어 하나씩을 쓰기 때문으로 본다. 슬롯 2까지는 확실한 이득이었다.

**사실 3 — 코어 총량이 같으면 배치를 바꿔도 처리량은 거의 안 움직인다.**

`(source)2026-08-12-배치-임베딩-동시성·토큰길이-S2-실험-원자료.md`의 배치 임베딩 실험은 영상 파이프라인과 같은 형태다(같은 VM, `bge-m3-base`, batch 4 texts/request).

| 설정 | 총 스레드 | 추론 1건 (p50) | 성공 처리량 |
|---|---:|---:|---:|
| 동시 1 × 스레드 2 | 2 | 22.94초 | 0.1743 texts/s |
| 동시 2 × 스레드 1 | 2 | 40.67초 | 0.1926 texts/s |

주의해서 읽어야 한다. 이 비교는 **슬롯을 늘린 것이 아니라 같은 스레드 2개를 다르게 나눈 것**이다. 요청 하나에 스레드 2개를 주면 22.94초, 요청 둘이 하나씩 나눠 가지면 각각 40.67초로 거의 정확히 2배가 되고 처리량은 10.5%만 늘었다. 즉 이 표는 "슬롯을 늘려도 소용없다"가 아니라 "**연산 코어가 총량을 정한다**"는 근거다.

**사실 4 — 검색 워크로드에서 동시 2 → 4는 이득이었다.**

같은 8월 9일 문서 6절에 검색 VM을 동시성 4로 올려 측정한 결과가 있다.

| 지표 | 동시 2 | 동시 4 | 변화 |
|---|---:|---:|---:|
| 성공 처리량 | 3.034 RPS | 3.880 RPS | +27.9% |
| 추론 1건 평균 | 657.3ms | 1,024.4ms | +55.8% |
| VM 최대 CPU | 63.45% | 97.37% | +33.92%p |

1건당 1.56배 느려지는 데 그쳐 슬롯 2배의 이득이 남았다.

**손익분기.** 슬롯을 2배로 늘릴 때 1건당 처리시간이 정확히 2.0배 느려지면 처리량은 변하지 않는다. 현재 S4의 batch 4 추론시간 86.8초 기준으로는 이렇다.

| 동시 4로 올려 1건당 느려지는 배수 | 시간당 batch | 현재 대비 |
|---:|---:|---:|
| 1.5배 | 110.6 | +33% |
| 1.8배 | 92.2 | +11% |
| **2.0배** | **83.0** | **±0%** |
| 2.5배 | 66.4 | −20% |

**해석.** 슬롯 1 → 2와 2 → 4는 성격이 다른 구간이다. 1 → 2는 연산 코어 2개 안에서 일어나 1.07배로 끝났다(사실 2). 2 → 4는 연산 코어를 넘어 하이퍼스레드에 얹는 구간이다. 검색에서 그 구간이 1.56배였지만(사실 4), 검색은 추론 1건이 1초 수준이고 영상 batch 4는 86.8초라 연산 밀도가 다르다. 사실 2의 1.07배를 2 → 4에 그대로 옮길 근거도, 검색의 1.56배를 영상에 옮길 근거도 없다.

**한계.** 영상 워크로드(1024 토큰, batch 4)에서 동시성 4를 실제로 측정한 자료는 없다. 손익분기 2.0배를 넘는지 여부는 이 보고서로 확정할 수 없다.

**총량을 확실히 늘리는 변수.** 같은 8월 12일 실험에서 embedding 입력 상한을 줄인 결과는 다음과 같다.

| 지표 | max_length 512 | max_length 256 | 변화 |
|---|---:|---:|---:|
| 성공 처리량 | 0.1926 texts/s | 0.4065 texts/s | **2.11배** |
| 추론 p50 | 40.67초 | 19.04초 | −53.2% |
| 503 비율 | 60.53% | 5.88% | −54.65%p |

동시성 조정과는 크기가 다르다. 다만 같은 문서 18절이 "256 토큰 뒤의 내용은 임베딩 입력에서 잘리며 이번 실험은 검색 품질 손실을 측정하지 않았다"고 명시한다. 현재 파이프라인이 1024를 쓰는 것은 무절단을 위한 결정이므로, 이 레버는 검색 품질 측정을 함께 해야 판단할 수 있다.

### 8.2 재시도가 지연에 준 영향

**사실.** S4 리팩토링의 `DBAPIError` 2건은 `ENRICH_CHUNK` 작업 단위 실패이고, 실행시간 4.0초와 3.2초를 버린 뒤 재시도로 복구됐다. assembly 재시도 1건은 `cursor_or_run_changed`(두 STT part가 동시에 완료돼 커서가 어긋난 경우)로 발생했고 바로 다음 시도에서 성공했다.

**해석.** 재시도가 있었다는 이유로 이 실행을 비교에서 빼지 않는다. 회차 makespan에 준 영향은 각각 수 초 수준으로, 회차 makespan 편차(818.2~888.3초)보다 훨씬 작다. 이것은 지연 손실이 아니라 자동 복구가 작동했다는 신뢰성 결과다.

**중요.** 이 assembly 재수렴 로직은 바로 직전 S4 실행(`comparison-excluded/20260825T191500Z-…`)이 6개 chunk를 `WAITING_FRAME`에 남기고 멈춘 문제의 수정이다. 그 실행은 완주 자료가 아니므로 성능 통계에는 넣지 않았고, 여기서는 이번 실행의 `assembly.retrying` 1건이 실제로 복구됐다는 회귀 확인 근거로만 인용한다.

### 8.3 품질에 영향을 줄 수 있는 항목

**Vision fallback.** S4 리팩토링에서 Vision 제공자 요청 3건이 실패했다. 다만 `(video_id, chunk_index)` 기준으로 확인하면 enrichment를 마친 180개 chunk 전부에 Vision 성공 기록이 있다. 즉 실패는 제공자 호출 단위의 실패였고 재시도로 모두 성공했다. 이번 실행에서는 fallback 때문에 캡션 품질이 낮아진 chunk가 없다.

**chunk 수 감소 (S4).** short 1편당 chunk가 2 → 1로 줄었다. 이것은 성능 지표가 아니라 결과물 자체의 차이다.

- 사실: 구버전 short는 chunk 2개, 리팩토링은 1개다. long은 양쪽 14개로 같다. `CHUNK_MAX_TOKENS`는 양쪽 300이다.
- 해석: 131초짜리 short 영상의 transcript가 리팩토링에서 한 chunk 안에 들어갔다는 뜻이다. 리팩토링은 STT part를 이어 붙이는 조립 단계가 새로 생겼으므로, chunk 경계 계산 시점이나 입력 단위가 달라졌을 가능성이 높다.
- 한계: chunk 경계나 chunk별 텍스트 길이를 기록한 이벤트가 없어 산출물만으로 원인을 확정할 수 없다.
- 제안: short 영상 1편으로 두 버전의 chunk 경계와 토큰 수를 직접 비교하는 소규모 검증. 검색 결과의 타임스탬프 정밀도가 실제로 떨어지는지 확인해야 한다. chunk가 절반이면 타임스탬프 해상도도 절반이 될 수 있다.

**STT 단어 시간축 보정.** S4 리팩토링에는 `stt.word_offsets.corrected` 60건과 `stt.word_offsets.block_realigned` 12건이 있다. 이는 보정 로직이 실제로 동작한 기록이다. 구버전 S4는 원본 `f572829`가 아니라 그 위에 같은 STT 보정을 이식한 이미지로 실행됐다. 근거는 이미지 태그 `baseline-f572829-sttfix-ffmpegfix-gcs300-20260825`와 `agent_memory/inbox/2026-08-25.md`(47·63행)다. 구버전 artifact에 해당 이벤트가 없는 것은 로그 스키마가 달라서지 보정이 없어서가 아닐 수 있다. 두 버전의 transcript 품질 차이는 이 산출물로 판정하지 않는다.

## 9. 한계와 추가 실험

### 9.1 한계

1. **반복 3회.** 모든 회차별 값은 원값으로 실었다. 회차 makespan 변동계수는 S3 구버전 0.018·리팩토링 0.030, S4 구버전 0.007·리팩토링 0.044다. 리팩토링 쪽이 회차 간 변동이 더 크다. 표본이 3개라 어떤 차이에도 통계적 유의성을 주장하지 않는다.
2. **STT 동시성 차이.** `STT_PART_CONCURRENCY`가 S4 구버전 2, 리팩토링 8이다. long은 2 part라 이 값이 part 병렬 처리 속도에 직접 영향을 준다. stage 분리 효과와 이 설정 효과를 분리하지 못한다.
3. **embedding 입장 대기 제한 차이.** S4 구버전 180초, 리팩토링 300초다. 구버전에서 입장 대기 최댓값이 89.9초로 180초에 닿지 않았으므로 이번 결과에는 영향이 없었지만, 조건이 다르다는 사실은 남는다.
4. **외부 API 변동.** STT와 Gemini는 외부 서비스다. 구버전 S4는 2026-08-25 09시대, 리팩토링 S4는 2026-08-26 00~01시대에 실행됐다. 외부 응답시간의 시간대 변동을 통제하지 못했다. S4 STT 요청시간 평균은 102.7 → 98.6초로 4% 차이라 크지 않다.
5. **chunk·embedding text 수 차이.** S4에서 192 → 180개다. 영상 수 기준 처리량과 작업량 보정 처리량을 함께 실었다.
6. **stage timing 계약 차이.** 구버전은 영상 단위 순차 stage, 리팩토링은 작업 단위 병렬 stage다. 같은 이름의 stage 값을 직접 빼지 않았다.
7. **S3 구버전의 runtime config 부재.** Worker 이미지·CPU·메모리·동시성 설정이 artifact에 없다. Worker 동시성 4는 S4 구버전 artifact와 개발로그에서 온 값이고, S3 구버전에서 관측된 최대 동시 실행 영상 수 4가 이와 일치한다.
8. **리팩토링 stage 동시성 설정 부재.** `NORMALIZATION_CONCURRENCY`·`EMBEDDING_CONCURRENCY`가 수집 대상 환경변수 목록에 없다. 실제 2였다는 근거는 `pipeline-db` 표본의 관측 최대 점유 2뿐이다.
9. **Cloud Run 표본 해상도.** 60초 간격이라 표본이 27~57건이다. p95는 정렬한 표본에서 위로부터 2~4번째 값 사이의 보간값이라, 표본 한두 개가 값을 크게 움직인다.
10. **embedding 용량 상한의 미측정 구간.** 이 파이프라인에서 embedding 동시 실행을 2에서 4로 올렸을 때의 1건당 지연 증가폭은 측정된 적이 없다. 슬롯 1 → 2는 1.07배로 확인됐지만(5.9 사실 2) 그 구간은 연산 코어 안이고, 2 → 4는 하이퍼스레드 구간이라 같은 값을 쓸 수 없다. 손익분기는 1건당 2.0배다.
11. **비용.** 산출물에 단가가 없어 실제 비용 절감액을 계산하지 않았다. 대리 지표만 싣는다. S4 기준 STT 요청 36 → 36건, embedding 요청 60 → 57건, embedding text 192 → 180개, 처리한 media duration 22,262초로 동일, 회차 makespan 합 2,944.9 → 2,584.5초.

### 10.2 계산식과 분모

| 지표 | 계산식 | 분모 |
|---|---|---|
| 완료 지연 | `terminal_observed_at - complete_responded_at` | 영상 24건 |
| 초기 Queue 대기 | `첫 Worker 작업 시작 - complete_responded_at` | 영상 24건 |
| 회차 makespan | `회차 마지막 terminal - 회차 첫 complete_started_at` | 회차 3건 |
| 대표 처리량 | `완료 영상 수 / (회차 makespan 합 / 3600)` | 완료 24건 / makespan 합 |
| media-hours/hour | `(완료 영상 재생시간 합 / 3600) / (makespan 합 / 3600)` | 동일 |
| 작업량 보정 처리량 | `리팩토링 편/시 × (리팩토링 text 수 / 구버전 text 수)` | S4: 33.43 × 180/192 = 31.34 |
| slowdown ratio | `완료 지연 / fixture duration_seconds` | 영상 24건 |
| slot 점유율 | `stage 실행시간 합 / (pipeline-db 표본 기준 슬롯 상한 × stage span)` | stage별 |
| 대기 있는 표본 비율 | `ready_count ≥ 1인 표본 수 / 전체 표본 수` | stage별 표본 수 |
| 대기 중 빈 슬롯 비율 | `ready ≥ 1이면서 (dispatched+running) < 관측 최대인 표본 수 / ready ≥ 1인 표본 수` | ready ≥ 1인 표본 |
| CPU N%↑ 표본 비율 | `값 ≥ N인 표본 수 / 값이 있는 표본 수` | 자원 표본 수 |
| 시간 가중 평균 | `Σ(값 × 다음 표본까지 간격) / Σ(간격)` | 표본 구간 합 |
| embedding tail | `terminal_observed_at - 마지막 enrichment.completed` | 리팩토링 영상 24건 |

percentile은 선형 보간(numpy `linear`, R type 7)이다. 누락값은 0으로 바꾸지 않고 `missing`으로 따로 센다. 자원 지표는 workload active window 안의 표본만 쓴다.


계산 스크립트는 다른 부하 테스트 도구와 함께 `scripts/load-test/`에 둔다. 원본 산출물은 `artifacts/load-tests/video-pipeline/`에 그대로 있고 이 스크립트는 읽기만 한다.

`metrics.json`의 `runs.<key>`에 실행별 전체 지표가, `comparisons.S3`·`comparisons.S4`에 항목별 비교가 들어 있다. `input_run_ids`와 `formula_version`으로 어떤 산출물에 어떤 계산식을 적용했는지 확인할 수 있다.

## 11. 확정할 수 있는 결론 3개

1. **S4의 선두 작업 막힘은 해소됐다.** 구버전은 3회차 모두 long 4편이 전부 끝난 뒤 short 4편이 완료됐고(short가 마지막 long보다 먼저 완료된 건수 0/12), 리팩토링은 12/12가 마지막 long보다 먼저, 12/12가 어떤 long이 실행 중일 때 완료됐다. short의 초기 Queue 대기는 871.2 → 255.5초(-70.7%)다. 근거는 24건 전수의 실제 timestamp이고 교란 요인의 영향을 받지 않는다.

2. **embedding endpoint의 입장 대기와 503은 사라졌고, endpoint 처리 능력 자체는 바뀌지 않았다.** 입장 대기 평균은 S3 13.44 → 0초, S4 52.05 → 0초다. S3 구버전의 503 재시도 32건은 리팩토링에서 0건이다. 동시에 batch 4의 순수 추론시간은 S4에서 86.2 → 86.8초로 같다. 즉 개선된 것은 대기 구조이지 endpoint 성능이 아니다.

3. **현재 1순위 병목은 `EMBED_BATCH` 구간이고, 그 아래 자원은 embedding VM의 연산 코어다.** 대기 작업이 존재한 표본이 S3 53.3%·S4 58.1%이고, 그 동안 실행 슬롯이 비었던 표본은 0.0%·0.3%다. 대기 중 oldest age p95는 119.4초·379.3초다. 그리고 이 구간은 S4 완료 지연의 54~58%를 차지한다. 세 조건이 모두 충족된다. 4.7의 슬롯 1 실행이 같은 코드로 처리량 35.90편/시(슬롯 2에서는 56.37)를 낸 것도 같은 방향을 가리킨다. 다만 "슬롯을 더 늘리면 해결된다"는 뜻은 아니다 — `e2-standard-4`의 연산 코어는 2개이고 현재 2개를 다 쓰고 있다(5.9).

## 아직 확정할 수 없는 결론 3개

1. **처리량 개선의 크기.** S4 영상 수 기준 +13.9%와 작업량 보정 +6.8% 중 어느 쪽이 맞는지는 chunk 수가 왜 192 → 180으로 줄었는지에 달려 있다. 이 차이가 chunk 경계 계산 방식 변화라면 보정값을 써야 하고, 구버전이 불필요하게 chunk를 쪼갠 것이라면 영상 수 기준이 맞다. 산출물에 chunk 경계 기록이 없어 확정할 수 없다.

2. **Worker 자원 활용이 실제로 개선됐는지.** S4에서는 CPU 50% 이상 표본 비율이 15.8 → 25.0%로 올랐지만 S3에서는 12.5 → 3.7%로 내렸다. 방향이 반대다. Cloud Run 표본이 27~57건뿐이고, S3와 S4는 fixture 구성이 달라 직접 비교할 수 없다. "지속 활용률이 개선됐다"고 말하려면 지속 투입형 시나리오에서 다시 재야 한다.

3. **S4 개선에서 stage 분리와 STT 동시성 변경(2 → 8)이 각각 얼마나 기여했는지.** 두 변경이 함께 적용됐다. long은 2 part라 STT 동시성이 직접 영향을 준다. 마찬가지로 `NORMALIZATION_CONCURRENCY=2`와 `EMBEDDING_CONCURRENCY=2`도 함께 바뀌어 각각의 기여도를 분리할 수 없다. 통제 실험이 필요하다.
