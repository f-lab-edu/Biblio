# 영상 파이프라인 리팩토링 전·후 테스트 요약

- 목적: 2026-08-27 멘토링 논의 준비
- 비교 자료: `artifacts/load-tests/video-pipeline/`의 완주 실행 4개
- 상세 근거: `video-pipeline-s3-s4-performance-comparison.md`, `video-pipeline-s3-s4-metrics.json`

## 먼저 이야기할 결론

리팩토링 후 파이프라인은 **최종 성공률을 유지하면서 처리량과 업로드 완료 후 평균 완료 소요 시간을 개선했고, 긴 영상 때문에 짧은 영상이 시작하지 못하던 문제를 해소했다.**

다만 성능 병목 자체가 사라진 것은 아니다. 구버전의 병목이었던 영상 단위 Worker 동시 실행 상한은 없어졌지만, 현재는 `EMBED_BATCH` 실행 슬롯과 embedding VM의 연산 코어가 가장 큰 병목이다. 또한 S4는 리팩토링 전후의 실제 chunk 수와 일부 설정이 달라서, “리팩토링만으로 몇 % 개선됐다”고 단정할 수는 없다.

## 이력서·멘토링에 사용할 핵심 개선

### 기존 파이프라인 대비 변경사항

| 구분 | 기존 파이프라인 | 리팩토링 후 |
|---|---|---|
| 실행 단위 | 영상 한 편이 Worker 슬롯을 전체 처리 종료까지 점유 | `NORMALIZE_VIDEO`·`TRANSCRIBE_PART`·`ENRICH_CHUNK`·`EMBED_BATCH` 작업 단위로 분리 |
| Queue와 동시 실행 | 단일 `PREPROCESS_REQUEST` Queue와 영상 단위 실행 상한 사용 | stage별 독립 Queue와 실행 상한을 두어 서로 다른 영상의 stage를 겹쳐 실행 |
| 영상 간 배정 | 먼저 시작한 긴 영상이 슬롯을 점유하면 뒤의 짧은 영상은 시작하지 못함 | `TRANSCRIBE_PART`와 `ENRICH_CHUNK`를 영상별로 우선 한 건씩 배정하고, embedding은 여러 영상의 `READY` chunk를 batch로 구성 |
| 원본 영상 입력 | 원본 전체를 Worker 로컬 저장소에 내려받은 뒤 처리 | generation에 고정된 signed URL과 HTTP Range로 FFmpeg가 필요한 구간만 읽음 |
| embedding 대기 | endpoint 내부 Queue에서 대기해 timeout과 503 재시도 발생 | `EMBED_BATCH` 실행 상한을 endpoint 수용량과 맞추고 대기를 Worker의 stage 작업 테이블에서 관리 |
| 실패 복구 | 영상 단위 실행 중 오류가 전체 영상 실패나 정체로 이어질 수 있음 | 작업별 상태·멱등성·재시도를 적용하고 assembly cursor 충돌 시 최신 상태를 다시 읽어 재수렴 |

## 리팩토링된 파이프라인 처리 절차

리팩토링 후에는 영상 하나가 전체 파이프라인을 끝까지 점유하지 않는다. 작업을 stage별 단위로 나누고, 각 stage의 실행 슬롯이 빌 때 `READY` 작업을 PGMQ에 발행한다.

```text
업로드 완료
→ NORMALIZE_VIDEO
→ TRANSCRIBE_PART × N
→ ASSEMBLE_CHUNKS
→ ENRICH_CHUNK × M
→ EMBED_BATCH
→ 완료 조건 확인
→ video READY
```

| 단계 | 실제 처리 | 다음 단계로 넘어가는 기준 |
|---|---|---|
| `NORMALIZE_VIDEO` | 원본 generation에 고정된 GCS signed URL을 만들고, FFmpeg가 필요한 구간만 읽는다. 오디오는 15분 단위 part로 변환해 GCS에 저장하고, 프레임 후보는 설정된 간격으로 추출해 GCS에 저장한다. | audio part 한 건을 저장할 때마다 `TRANSCRIBE_PART`를 `READY`로 만들고, 남은 STT 슬롯이 있으면 즉시 발행한다. |
| `TRANSCRIBE_PART` | part별로 Google STT를 호출하고 전사 결과 JSON을 GCS에 저장한다. part 작업은 서로 독립적이므로 완료 순서가 달라도 된다. | 완료된 part가 앞에서부터 연속으로 모인 범위만 조립 대상으로 넘긴다. |
| `ASSEMBLE_CHUNKS` | 별도 Queue가 아니라 DB 내부 조립 단계다. part 경계의 5초 중첩을 제거하고 시간축을 보정한 뒤 transcript를 chunk로 나눈다. 각 chunk 구간 안에서 중앙 시점에 가장 가까운 프레임 후보를 고른다. | 프레임이 선택된 chunk를 `ENRICH_CHUNK READY`로 전환한다. |
| `ENRICH_CHUNK` | 선택한 후보 이미지로 keyframe을 만들고, Gemini Vision에서 caption·OCR·scene tag를 얻는다. 이를 transcript와 합쳐 `enriched_text`를 저장한다. | enrichment가 끝난 chunk를 `EMBED_BATCH` 대상에 포함한다. |
| `EMBED_BATCH` | 여러 `READY` chunk의 `enriched_text`를 한 요청으로 묶어 embedding endpoint에 전달하고, 반환 순서를 검증한 뒤 vector를 저장한다. 한 batch에는 여러 영상의 chunk가 포함될 수 있다. | 모든 audio part와 chunk의 enrichment·embedding이 완료되고 각 chunk의 vector가 존재하면 pipeline run을 완료하고 video를 `READY`로 바꾼다. |

공통 실행 규칙은 다음과 같다. Scheduler는 stage별 `DISPATCHED + RUNNING` 수가 실행 상한을 넘지 않게 작업을 고르고, DB 상태 변경과 PGMQ 발행을 같은 PostgreSQL transaction에서 처리한다. Consumer는 메시지를 가져온 뒤 작업을 `RUNNING`으로 선점하며, 성공한 작업만 완료 처리하고 메시지를 삭제한다. 재시도 가능한 실패는 메시지를 남겨 다시 실행한다. `TRANSCRIBE_PART`와 `ENRICH_CHUNK`는 특정 영상이 슬롯을 독점하지 않도록 영상별 작업을 우선 한 건씩 배정한다.


## 어떤 테스트를 비교했는가

| 시나리오 | 입력 구성 | 구버전 | 리팩토링 |
|---|---|---|---|
| S3 | medium 8편 동시 요청 × 3회 | `20260816T122033Z-video-s3` | `20260825T183422Z-video-s3-refactored-norm2-embed2-maxlen1024-wait300-worker450` |
| S4 | long 4편 요청 후 10초 뒤 short 4편 × 3회 | `20260825T1812KST-video-s4-baseline-f572829-sttfix-ffmpegfix-gcs300-maxlen1024` | `20260826T005351Z-video-s4-refactored-assembly-retry-norm2-embed2-maxlen1024-wait300-worker450` |

네 실행은 같은 fixture를 사용했고, 각각 24개 요청을 3회에 나눠 실행했다. 모두 24/24 `READY`로 끝났으며 관측 누락도 없다.

비교에서 제외한 실행은 대표 성능값에 넣지 않았다. 주요 제외 이유는 `EMBEDDING_MAX_LENGTH=256`처럼 입력 조건이 달랐거나, 예정된 요청을 모두 실행하지 못했거나, 관측 자료가 빠졌기 때문이다. 실패 실행은 원인 분석과 회귀 확인에만 사용했다.

대표 처리량은 회차마다 첫 요청을 시작한 시점부터 마지막 영상이 완료된 시점까지를 합산해 계산했다. 회차 사이의 업로드 공백은 제외했다.

S4의 영상 수 기준 처리량은 13.9% 올랐지만, embedding text 수가 192개에서 180개로 6.25% 줄었다. 처리한 text 수를 맞춰 보정하면 개선폭은 6.8%다. 이 차이의 원인이 아직 확인되지 않았으므로 두 수치를 함께 제시해야 한다.

## 리팩토링으로 실제로 좋아진 부분

### 1. 긴 영상이 짧은 영상을 막던 문제가 해소됐다

구버전 S4는 매 회차마다 `long 4편 → short 4편` 순서로 완료됐다. Worker 동시 실행 상한 4개를 long 영상이 모두 차지해, short 영상은 long 영상이 끝날 때까지 시작하지 못했다.

리팩토링 후에는 short 12편 모두 같은 회차의 마지막 long보다 먼저 끝났다. short 영상의 평균 초기 Queue 대기도 871.2초에서 255.5초로 70.7% 줄었다. 이는 short 우선순위를 추가한 결과가 아니라, 영상을 stage별 작업으로 나눠 서로 다른 영상의 작업이 겹쳐 실행될 수 있게 된 결과다.

### 2. endpoint 내부 대기와 503이 사라졌다

S4의 batch 4 순수 embedding 추론시간은 86.2초에서 86.8초로 사실상 같다. endpoint 자체가 빨라진 것은 아니다.

구버전에서는 endpoint 입장 전에 평균 52.05초를 기다렸지만 리팩토링 후에는 0초가 됐다. S3에서 발생했던 embedding 503 재시도 32건도 0건이 됐다. Worker의 `EMBED_BATCH` 동시 실행 상한 2개를 endpoint 동시 실행 상한 2개와 맞추면서, endpoint 안에서 timeout을 만들던 대기를 Worker의 stage 작업 테이블에서 관리하게 됐다.

따라서 정확한 설명은 “embedding이 빨라졌다”가 아니라 **“embedding 대기의 위치를 제어하고 관측할 수 있는 곳으로 옮겨 불필요한 timeout과 재시도를 없앴다”**이다.

### 3. 일부 실패가 전체 영상 실패로 이어지지 않았다

리팩토링 S3에서 `DBAPIError` 1건, S4에서 2건이 발생했지만 모두 작업 단위 재시도로 복구됐다. S4에서는 assembly 경합으로 `cursor_or_run_changed` 재시도 1건이 발생했고 다음 시도에서 성공했다. Vision 요청 실패 3건도 재시도 후 180개 chunk 전부 성공했다.

직전 불완전 S4 실행에서는 assembly 누락 때문에 6개 chunk가 `WAITING_FRAME`에 남았다. 최종 비교 실행에서는 같은 계열의 경합이 발생해도 재수렴해 24/24 영상이 완료됐다. 성능뿐 아니라 자동 복구 경로도 실제 부하에서 확인한 셈이다.

## 아직 남은 문제와 퇴행

### 1. 병목은 `EMBED_BATCH`로 이동했다

리팩토링 후 `EMBED_BATCH`에 대기 작업이 있던 표본은 S3 53.3%, S4 58.1%였다. 대기가 있을 때 실행 슬롯이 비어 있던 비율은 각각 0.0%, 0.3%로, 사실상 슬롯 2개가 계속 차 있었다. 대기 중 가장 오래된 작업의 p95 대기시간은 S3 119.4초, S4 379.3초다.

S4에서는 마지막 enrichment가 끝난 뒤 embedding을 마치기까지의 구간이 long 완료 소요 시간의 58.1%, short의 54.5%를 차지한다. 현재 부하에서 가장 먼저 봐야 할 병목은 `EMBED_BATCH`다.

다만 슬롯만 2개에서 4개로 늘리면 해결된다고 말할 수 없다. embedding VM은 `e2-standard-4`이고 현재 동시 실행 2개가 연산 코어 2개를 이미 사용한다. 영상 batch 4 조건에서 동시 실행 4개의 손익은 아직 측정하지 않았다.

### 2. normalization은 1 vCPU에서 두 작업이 경쟁한다

Worker는 1 vCPU인데 `NORMALIZE_VIDEO`를 2개까지 동시에 실행한다. 같은 이미지로 동시 실행을 1개에서 2개로 바꾼 S3 보조 실험에서 한 작업의 실행시간은 19.76초에서 36.27초로 1.84배 늘었고, 전체 처리율 증가는 9.0%에 그쳤다.

S4 long 영상의 초기 Queue 대기는 0.76초에서 59.45초로 늘었다. 프레임 후보 추출이 long normalization 실행시간의 약 72%를 차지해 슬롯 회전을 늦추는 것이 직접 관측됐다. 동시성 추가 상향보다 Worker CPU를 2 vCPU로 올리는 실험이나 프레임 추출 분리를 먼저 검토할 근거가 있다.

### 3. S4의 늦은 요청은 개선폭이 작다

S4 평균 완료 소요 시간은 23.5% 줄었지만 long p95 완료 소요 시간은 913.1초에서 881.4초로 3.5%만 줄었다. 전체 완료 소요 시간의 변동계수도 0.042에서 0.210으로 커졌다.

즉 대부분의 영상과 첫 완료 시점은 빨라졌지만, 늦게 끝나는 영상의 개선은 작고 요청 간 편차는 커졌다. 평균만 보면 이 문제가 가려진다.

### 4. S4 결과물의 chunk 수가 달라졌다

long 영상은 양쪽 모두 편당 14개 chunk였지만, short 영상은 편당 2개에서 1개로 줄었다. `CHUNK_MAX_TOKENS=300`은 동일하다. 이 때문에 전체 chunk와 embedding text가 192개에서 180개로 줄었다.

원본 산출물에는 chunk 경계와 chunk별 토큰 수가 없어 원인을 확정할 수 없다. 처리량 개선의 일부가 작업량 감소에서 왔을 수 있고, 검색 결과의 타임스탬프 정밀도에도 영향을 줄 수 있다. 성능 개선으로 확정하기 전에 결과 품질을 따로 확인해야 한다.

## 이 결과만으로 단정하면 안 되는 것

1. **S4 처리량이 순수하게 리팩토링 때문에 13.9% 올랐다고 단정할 수 없다.** 작업량 보정값은 6.8%이고, `STT_PART_CONCURRENCY`도 2에서 8로 함께 바뀌었다.
2. **embedding endpoint 연산이 빨라졌다고 말할 수 없다.** S4 batch 4 추론시간은 거의 같고, 줄어든 것은 입장 대기다.
3. **Worker 자원 활용이 항상 개선됐다고 말할 수 없다.** CPU 50% 이상 표본 비율은 S4에서 15.8%에서 25.0%로 올랐지만 S3에서는 12.5%에서 3.7%로 내렸다.
4. **통계적으로 일반화할 수 없다.** 시나리오별 반복은 3회이고 외부 STT·Vision API의 시간대별 변동도 통제하지 못했다.
5. **stage 이름이 같은 시간값을 단순 비교하면 안 된다.** 구버전은 영상 단위 순차 stage이고 리팩토링은 서로 겹치는 작업 단위 stage라 측정 범위가 다르다.

## 확인필요

### 우선순위 판단

1. 현재 병목의 직접 증거를 보면 embedding VM 코어 확장을 1순위로 두는 것이 맞는가?
2. 코어 확장 전에 현 VM에서 `EMBED_BATCH` 동시 실행 2 → 4의 손익분기만 먼저 측정하는 편이 나은가?
3. Worker는 동시성을 더 올리기보다 1 → 2 vCPU A/B 테스트를 먼저 하는 판단이 맞는가?
4. 프레임 후보 추출을 normalization에서 별도 stage로 분리하는 것이 구조 복잡도 대비 가치가 있는가?

### 성능 지표와 실험 설계

1. S4의 대표 개선폭을 영상 기준 13.9%와 작업량 보정 6.8% 중 어떤 방식으로 보고해야 하는가?
2. 다음 실험에서 평균보다 p95와 요청 간 편차를 더 중요한 통과 기준으로 둘 필요가 있는가?
3. 유한한 3회 wave 테스트 외에, 고정 도착률로 30분 이상 요청하는 지속 부하 테스트를 성능 판정 기준에 넣어야 하는가?
4. stage 분리 효과를 확인하기 위해 `STT_PART_CONCURRENCY`, timeout, VM 사양을 고정한 대조 실험을 한 번 더 해야 하는가?

### 품질과 운영 안정성

1. short 영상의 chunk 수가 2개에서 1개로 줄어든 것을 성능 실험 전에 반드시 해결해야 할 품질 회귀로 볼 것인가?
2. DB deadlock과 Vision 429·ReadTimeout이 모두 복구됐더라도, 부하를 높이기 전에 재시도 횟수나 실패율에 별도 중단 기준을 둬야 하는가?
3. 현재 Worker `maxScale=1`을 유지한 채 단일 인스턴스 효율을 먼저 높일지, 여러 인스턴스로 확장하는 실험을 병행할지 결정이 필요하다.

## 제안하는 다음 실험 순서

1. short 영상 1편으로 구버전·리팩토링의 chunk 경계, 토큰 수, 검색 타임스탬프 품질을 비교한다.
2. 나머지 조건을 고정한 채 embedding VM 코어 수만 늘려 S4를 다시 실행한다. batch 4 추론시간, `EMBED_BATCH` 대기 p95, 완료 소요 시간 p95를 본다.
3. 비용상 코어 확장이 어렵다면 현 VM에서 동시 실행 2 → 4만 바꿔 손익분기인 작업당 2배 지연을 넘는지 확인한다.
4. Worker CPU를 1 → 2 vCPU로만 바꿔 normalization 실행시간과 long 초기 Queue 대기를 비교한다.
5. 마지막으로 설정을 고정한 지속 부하 테스트를 실행해 Queue가 수렴하는 최대 도착률과 자원 사용률을 확인한다.

한 번의 실험에서는 한 변수만 바꾸고, fixture·실행 시간대·외부 API 조건·timeout·batch 크기·token 상한을 가능한 한 고정해야 각 변경의 효과를 분리할 수 있다.
