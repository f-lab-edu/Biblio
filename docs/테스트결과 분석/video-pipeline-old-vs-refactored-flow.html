처리 흐름 비교 — 구버전 vs 리팩토링

같은 fixture, 같은 부하(S4: long 4편 + 10초 뒤 short 4편, 3회 반복)에서 두 버전이 일을 어떻게 나누는지 비교한다. 두 그림의 단계 열은 같은 가로 위치에 맞춰져 있으므로 위아래를 그대로 대조하면 된다. 소요시간은 long 영상 1편 기준 실측 평균이다.

Before

구버전 — 작업 하나가 영상 한 편 전체

워커가 영상 한 편을 집으면 여섯 단계를 다 끝낼 때까지 그 슬롯을 놓지 않는다. 동시 실행 상한이 영상 4편이라, long 4편이 슬롯을 채우면 뒤에 온 short는 처리 자체를 시작하지 못한다.

After

리팩토링 — 단계마다 별도 작업으로 분리

작업 단위가 영상 1편에서 video · part · chunk · batch로 쪼개졌다. 단계마다 자기 실행 슬롯을 갖고, 스케줄러가 영상을 라운드로빈으로 돌아가며 슬롯을 나눠 준다. 그래서 long이 실행 중이어도 short가 끼어들어 끝날 수 있다.

LEGEND · 두 그림 공통

Queue / 완료 상태 워커가 실행하는 단계 외부 서비스 호출 Queue 없이 인라인 호출 병목 지점 사용 중인 실행 슬롯 비어 있는 실행 슬롯

무엇이 바뀌었나

  • 작업 단위가 영상 1편에서 video·part·chunk·batch로 쪼개졌다
  • Queue가 하나에서 단계별 4개 + 작업 테이블로 나뉘었다
  • 원본 다운로드를 없애고 서명 URL로 스트리밍한다 (워커 메모리 평균 43.8% → 10.2%)
  • 프레임 추출이 chunk 단위에서 normalization 한 번으로 옮겨졌다
  • 임베딩 배치가 영상 안 순차 루프에서 영상 교차 묶음으로 바뀌었다

그래서 무엇이 좋아졌나

  • 선두 작업 막힘 해소 — short 12/12가 마지막 long보다 먼저 완료 (구버전 0/12)
  • short 초기 대기 871초 → 255초
  • 완료 지연 평균 915.6초 → 700.2초
  • 처리량 29.3 → 33.4편/시 (작업량 보정 시 +6.8%)
  • 임베딩 endpoint 입장 대기 52초 → 0초, 503 재시도 소멸

남은 문제

  • EMBED_BATCH 슬롯 2개가 새 병목
  • endpoint 성능 자체는 그대로 (batch 4 추론 86.2 → 86.8초)
  • normalization은 오히려 느려짐 66.2 → 110.3초
  • long 초기 대기 0.8 → 59.5초 (슬롯을 short와 나눈 대가)
  • 다음 실험: endpoint 동시성과 EMBED_BATCH 상한을 함께 2 → 4
