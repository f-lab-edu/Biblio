  2. 여러 사용자가 여러 영상을 동시에 업로드했을 때의 파이프라인 처리

## 결론

가장 큰 갭은 **여러 사용자·여러 영상이 몰리는 상황에 대한 공정성과 확장 장치가 전혀 없는 것**이다. 파이프라인 큐는 순서대로만 꺼내는 단일 큐이고 사용자별 제한이 없어서, 한 사용자가 영상을 대량으로 올리면 다른 모든 사용자의 영상이 그 뒤로 밀린다. Worker는 1대 고정에 동시 4건이 전부고, 그 4건이 임베딩 단계에서 겹치면 슬롯 1개짜리 배치 임베딩 VM에서 다시 한 줄로 선다.

영상 1건 내부에서는 병렬 처리가 부분적으로 있으나 **배치 장벽 패턴** 때문에 설계된 동시성만큼도 못 쓴다. 2개씩 묶어 실행하고 둘 다 끝나야 다음 2개를 시작하는 구조가 STT·청크 보강·임베딩 세 곳에 반복된다. 느린 항목 하나가 같은 묶음의 빠른 항목을 막는다.

CPU 활용 관점에서는 Pipeline Worker가 가장 불리하다. CPU를 항상 할당받는 설정인데 처리 시간의 대부분(표본 기준 STT 62% 포함 약 80% 이상)이 외부 응답 대기라, 할당된 CPU가 대기 시간 동안 논다. PostgreSQL도 FTS가 단일 코어 순차 스캔이라 4 vCPU 중 1개만 쓴다.

다만 모든 갭을 지금 고쳐야 하는 것은 아니다. 각 항목에 지금 고칠 근거가 있는지, 어떤 조건에서 고칠 가치가 생기는지를 함께 적었다.

## 이미 분산 처리가 고려된 지점

갭만 나열하면 전체가 미설계로 보이므로, 이미 고려된 지점을 먼저 구분한다.

| 지점 | 구현 | 근거 |
|---|---|---|
| FTS·벡터 검색 병렬 실행 | `asyncio.gather`로 두 검색을 동시에 실행 | `search_orchestrator.py:241` |
| 검색·배치 임베딩 VM 분리 | 검색(10.20.3.15)과 색인(10.20.3.14)이 서로 슬롯을 뺏지 않음 | Terraform `embedding_vm`, `embedding_search_vm` |
| Worker 내 다중 영상 동시 처리 | 폴링 루프 4개가 영상 4건을 동시에 처리 | `main.py:64`, `WORKER_CONCURRENCY=4` |
| STT 파트 분할 | 오디오를 15분 파트로 나눠 파트 2개씩 동시 전사 | `long_audio_transcription.py:220` |
| 청크 보강 동시 실행 | 키프레임·Vision 보강을 청크 2개씩 동시 처리 | `pipeline_orchestrator.py:400` |
| Cloud Run 수평 확장 | frontend·search·core-api max 3, 요청 기반 자동 확장 | 배포값 조회로 확인 |
| async 요청 처리 | 검색 서비스가 LLM 대기 중에도 다른 요청을 처리 | FastAPI + asyncio 구조 |
| 임베딩 workload 분리 수용 | 검색 32건·영상 4건을 별도 상한으로 수용, 검색 우선 슬롯 배정 | `admission_control.py:232` |

## 갭 1 — 영상 1건 내부

### 1-1. 배치 장벽: 동시성 2를 설계하고도 2만큼 못 쓴다

STT 파트 전사와 청크 보강 모두 같은 패턴이다. 항목을 2개씩 잘라 `asyncio.gather`로 실행하고, **둘 다 끝나야** 다음 2개를 시작한다.

```python
# long_audio_transcription.py:220 — STT 파트
for offset in range(0, len(parts), self._stt_concurrency):
    current_parts = parts[offset : offset + self._stt_concurrency]
    current_results = await asyncio.gather(...)

# pipeline_orchestrator.py:449 — 청크 보강
for i in range(0, len(chunk_drafts), self._chunk_concurrency):
    batch = chunk_drafts[i : i + self._chunk_concurrency]
    batch_results = await asyncio.gather(*[process_one(d) for d in batch])
```

파트 A가 10초, 파트 B가 70초 걸리면 A를 처리하던 자리는 60초 동안 논다. 묶음 내 처리 시간 편차가 클수록 손실이 커진다. STT 파트는 마지막 파트만 짧은 경우가 흔하고, 청크 보강은 Vision 응답 시간이 이미지마다 달라 편차가 있다.

청크 보강 쪽은 특이하게 `asyncio.Semaphore(2)`를 이미 만들어놓고(`pipeline_orchestrator.py:400`) 바깥에 배치 루프를 또 두었다. Semaphore가 동시 2개를 이미 보장하므로 바깥 루프는 동시성 제한이 아니라 장벽만 추가한다.

**개선 방안**: 배치 루프를 없애고 전체를 한 번에 `gather`에 넘기되 Semaphore로 동시 수를 제한한다. 슬롯이 비는 즉시 다음 항목이 시작된다. 청크 보강은 이미 Semaphore가 있어 바깥 루프 제거만으로 되고, STT 파트는 같은 패턴을 적용하면 된다. 코드 변경이 작고 외부 계약이 바뀌지 않는다.

**지금 안 해도 되는 조건**: 항목 간 처리 시간 편차가 작으면 이득도 작다. 표본 1건에서는 편차 데이터가 없으므로, 부하테스트에서 파트별·청크별 처리 시간을 기록해 편차를 확인한 뒤 적용해도 늦지 않다.

### 1-2. 단계 간 파이프라이닝 없음

파이프라인은 DOWNLOAD → EXTRACT → STT → CHUNKING → EMBEDDING → UPSERT를 완전히 직렬로 실행한다. 앞 단계가 전부 끝나야 다음 단계가 시작된다. 예를 들어 STT 파트 1이 끝나면 그 구간의 청킹을 시작할 수 있지만, 현재는 마지막 파트까지 기다린다.

**개선 방안과 비용**: 파트 단위 스트리밍 처리로 바꾸면 STT 대기(표본 75초)와 후속 단계가 겹쳐진다. 다만 청킹이 전체 자막을 입력으로 받는 현재 설계를 구간 단위로 바꿔야 하고, 실패·재시도 단위도 다시 정의해야 한다. 변경 폭이 크다.

**판단**: 영상 색인은 사용자가 응답을 기다리는 경로가 아니므로, 처리 시간 단축의 가치가 검색보다 낮다. 색인 지연이 실제 문제로 확인되기 전에는 보류를 권한다.

### 1-3. 임베딩 배치 간 직렬 호출

`_build_embeddings`는 청크를 4개씩 잘라 배치를 **순차로** 호출한다(`pipeline_orchestrator.py:463`). 배치 2개를 동시에 보내는 구조가 아니다.

**판단**: 현재는 고칠 필요가 없다. 임베딩 VM의 실행 슬롯이 1이라(`MAX_CONCURRENCY=1` 배포값 확인) 클라이언트가 병렬로 보내도 VM에서 한 줄로 선다. 오히려 병렬로 보내면 대기 상한 20초에 걸려 실패할 수 있다. 이 항목은 VM 슬롯을 늘리는 결정과 묶어서만 의미가 있다.

## 갭 2 — 여러 사용자·여러 영상

### 2-1. 사용자 간 공정성 장치가 없다

PREPROCESS_REQUEST 큐는 단일 FIFO이고, 발행 시점(Core API)에도 소비 시점(Worker)에도 사용자별 제한이 없다. 확인한 범위에서 사용자·프로젝트 단위 동시 처리 제한, 큐 내 우선순위, 처리량 할당 중 어느 것도 없다.

부하 시 예상 동작: 사용자 A가 영상 50건을 올리고 사용자 B가 1건을 올리면, B의 영상은 A의 50건이 소비될 때까지 대기한다. Worker 동시 4건, 영상당 약 2분(표본 기준)이면 B는 최대 약 25분을 기다린다(계산값). B에게는 서비스 장애와 구분되지 않는다.

기존의 임베딩 우선순위 설계(검색 workload가 영상 workload보다 슬롯을 먼저 받는 구조)는 **workload 간** 우선순위이지 **사용자 간** 공정성이 아니라는 점을 구분해야 한다.

**개선 방안**:

| 선택지 | 효과 | 비용·조건 |
|---|---|---|
| 사용자당 동시 처리 상한(소비 시점) | Worker가 메시지를 읽고 해당 사용자의 처리 중 건수가 상한 이상이면 가시성 타임아웃으로 되돌림 | PGMQ에 우선순위 기능이 없어 애플리케이션에서 구현. 되돌린 메시지의 재조회 비용 발생 |
| 사용자당 대기 상한(발행 시점) | Core API가 사용자의 미완료 영상 수를 세어 초과 업로드를 거부 또는 지연 안내 | 구현이 소비 시점보다 단순. 사용자에게 명시적 피드백 가능. 다만 이미 큐에 들어간 불균형은 못 고침 |
| 사용자별 라운드로빈 소비 | 대기 중인 사용자들에게 처리 순서를 번갈아 배정 | PGMQ 단일 큐 구조에서는 구현 복잡도가 가장 큼 |

**판단**: 현재 사용자 수 규모에서는 실제 발생 빈도가 낮으므로 즉시 구현 대상은 아니다. 다만 부하테스트의 `둘 다` 시나리오에 "사용자 2명 이상이 동시에 업로드"하는 조건을 넣어 이 동작을 한 번 관측해두는 것을 권한다. 포트폴리오 관점에서는 발행 시점 상한이 구현 대비 설명 가치가 크다(제안).

### 2-2. Worker 수평 확장이 닫혀 있다

Worker는 max 1 인스턴스 × 동시 4건이 전체 색인 처리량의 상한이다. 5건째부터는 큐에서 대기한다. Cloud Run max를 올리면 인스턴스는 늘릴 수 있지만, 그 전에 두 가지가 검증되어야 한다.

- 같은 메시지를 두 인스턴스가 잡지 않는가 — PGMQ 가시성 타임아웃(1800초)이 기본 방어이지만, 처리 시간이 이를 넘는 영상에서 중복 처리가 생길 수 있다. 단계별 멱등성(재실행 안전성) 검증이 선행 조건이다.
- 늘어난 Worker가 배치 임베딩 VM 슬롯 1에서 다시 직렬화되지 않는가 — 아래 2-3과 연결된다.

**판단**: 색인 처리량 요구가 확인되기 전에는 현재 상한 유지가 비용이 낮다. 기존 병목 보고서의 판단과 같다.

### 2-3. 영상 4건이 임베딩 단계에서 겹치면 거부가 시작된다

Worker가 영상 4건을 동시에 처리해도, 임베딩 단계에 도달하면 배치 임베딩 VM의 슬롯 1개를 두고 다시 한 줄로 선다. 표본 기준 배치 1회 추론이 20.8초인데 대기 상한이 20초라, **두 영상이 겹치기만 해도** 뒤 요청이 상한을 넘겨 거부될 수 있다(추정). 영상 요청 수용 상한도 4라 Worker 동시성과 같은 값이어서 여유가 없다.

worker 쪽 재시도·실패 처리가 이 거부를 어떻게 다루는지가 실제 영향을 결정한다. 이번 분석에서는 확인하지 않았다.

**개선 방안**: 대기 상한을 추론 1회 시간보다 충분히 크게 잡거나(예: 추론 시간의 2~3배, 초기 제안값), Worker의 임베딩 호출에 지수 백오프 재시도를 두는 방법이 있다. 어느 쪽이든 먼저 거부 시 파이프라인이 실패로 끝나는지 재시도되는지를 코드로 확인해야 한다.

### 2-4. 외부 API 쿼터가 영상 수에 비례해 몰린다

영상 1건당 Vision 동시 2건, STT 동시 2건이다. 영상 4건이 같은 단계에 겹치면 Vision 최대 8건, STT 최대 8건의 동시 호출이 같은 GCP 프로젝트 쿼터로 나간다. 쿼터 한도와 429 응답 시 재시도 동작은 이번 분석 범위에서 확인하지 않았다.

**판단**: 부하테스트에서 색인 다건 동시 시나리오를 돌릴 때 429 발생 여부를 기록하는 것으로 충분하다. 선제 대응은 불필요하다.

## 갭 3 — 여러 건의 검색

### 3-1. 검색 임베딩이 전역에서 한 줄로 선다

검색 경로의 최대 갭이며 `docs/Bottleneck_Analysis_Current.md`의 2번 병목과 같은 항목이다. 모든 사용자의 모든 검색 질의가 슬롯 1개짜리 임베딩 VM을 지나므로, 검색 동시성은 Cloud Run이 아무리 확장돼도 초당 약 2.4건(계산값)에서 막힌다. Cloud Run은 3대까지 늘 수 있는데 그 뒤의 임베딩은 1줄이라, 수평 확장이 실질적으로 임베딩 VM 앞에서 끝난다.

대응 선택지(warm-up, 슬롯 증가, VM 증설, 질의 캐시)와 비용은 병목 보고서에 정리되어 있어 반복하지 않는다.

### 3-2. 검색 수용 상한 32도 사용자 구분이 없다

`SEARCH_REQUEST_LIMIT=32`는 전역 상한이다. 한 사용자(또는 부하 스크립트 하나)가 32자리를 전부 차지하면 다른 사용자의 검색이 수용 단계에서 거부된다. 갭 2-1과 같은 구조의 문제가 검색 쪽에도 있다.

**판단**: 실사용자 규모에서 발생 확률이 낮고, 발생해도 5초 안에 자리가 돌므로 영상 파이프라인의 공정성 문제보다 영향이 작다. 기록만 해둔다.

### 3-3. serving target 다중일 때의 병렬은 겉보기만 병렬이다

serving target이 여러 개면 target별 질의 임베딩을 `asyncio.gather`로 동시에 요청하지만(`search_orchestrator.py:208`), VM 슬롯이 1이라 실제로는 직렬 처리된다. target 2개면 질의 임베딩 시간이 약 2배가 된다(추정). 현재 serving target이 1개라 실측 영향은 없다. 모델 전환 기간(신·구 버전 동시 서빙)에만 나타나는 특성이므로, 그 시나리오를 측정할 때 기억할 항목이다.

## 갭 4 — CPU 활용

### 4-1. Pipeline Worker: 항상 할당된 CPU가 대기 시간 동안 논다

Worker는 `cpu_idle=false`(CPU 항상 할당, `cloud_run_worker/variables.tf:54` 기본값)로 배포된다. 폴링 루프가 HTTP 요청 없이 돌아야 하므로 이 설정 자체는 필요하다. 문제는 그 CPU가 실제로 일하는 비율이다.

표본 기준 영상 1건 121초 중 STT 대기 75초(62%), 임베딩 HTTP 대기 20.8초(17%), 다운로드·GCS 등 IO가 나머지 대부분이다. Worker가 CPU를 실제로 쓰는 구간은 FFmpeg(오디오 추출·키프레임)와 파싱 정도다. 동시 4건을 처리해도 4건이 모두 STT 대기 중이면 1 vCPU가 통째로 논다. CPU 사용률 실측은 없으므로 "논다"는 구조적 추정이며, VSM 문서도 같은 이유로 단정을 보류했다.

**개선 방안**: 두 방향이 있다.

- 동시 처리 수를 올린다. 대기 중심 워크로드는 1 vCPU로도 더 많은 건수를 겹칠 수 있다. `WORKER_CONCURRENCY`를 올리는 것은 환경변수 하나지만, 메모리 4GiB 안에서 영상 파일 여러 개(다운로드 원본 + 작업 파일)가 공존할 수 있는지와 배치 임베딩 VM 수용 상한 4를 함께 올려야 하는지가 선행 확인 사항이다.
- 대기와 계산을 분리한다. STT 제출과 결과 회수를 분리해 대기 중 다른 영상을 처리하는 구조인데, 현재 코드가 이미 async 대기라 동시성 수를 올리는 것과 실질 효과가 같다. 별도 재설계의 이득은 없다(판단).

**측정 먼저**: 부하테스트에서 Worker Cloud Run의 CPU 사용률을 색인 처리와 같은 시간축으로 기록한다. 사용률이 낮게 나오면 동시성 증가의 근거가 되고, 높게 나오면 FFmpeg 구간이 생각보다 크다는 뜻이라 다른 판단이 필요하다.

### 4-2. 임베딩 VM: 추론 중에는 코어를 다 쓰고, 추론이 없으면 통째로 논다

스레드 제한이 없어(배포값 확인) BGE-M3 추론 1건이 vCPU 4개를 나눠 쓴다. 추론이 도는 동안의 코어 활용은 오히려 높다. 갭은 요청이 없는 시간이다. 검색 VM과 배치 VM이 분리되어 있어 검색이 없는 시간의 검색 VM, 색인이 없는 시간의 배치 VM은 e2-standard-4가 통째로 유휴다.

**판단**: 이 분리는 검색 지연을 색인 부하에서 격리하려는 의도된 설계다(Deployment Diagram 근거). 유휴를 줄이려고 두 workload를 한 VM에 합치면 격리를 되돌리는 것이므로, 자원 활용과 격리 중 무엇을 우선할지의 문제다. 현재 운용이 세션 단위로 VM을 켜고 끄는 방식이라 유휴 비용 자체가 통제되고 있어, 지금은 격리 유지가 맞다(판단). 상시 운영으로 전환하면 이 트레이드오프를 다시 계산해야 한다.

### 4-3. PostgreSQL: FTS 스캔이 4 vCPU 중 1개만 쓴다

실측한 FTS 실행 계획에 병렬 스캔(Parallel Seq Scan)이 없다. 148행짜리 테이블은 PostgreSQL의 병렬화 최소 크기(기본 8MB)에 못 미쳐 단일 코어로 스캔된다. 데이터가 커지면 플래너가 병렬 스캔을 고려할 수 있지만(`max_parallel_workers_per_gather=2` 확인), 그것은 전체 스캔을 코어 2개로 나누는 것일 뿐 스캔 자체를 없애지 못한다.

**판단**: 병렬 스캔 튜닝보다 GIN 인덱스가 정답이다. 인덱스가 있으면 스캔량 자체가 줄어 코어 활용 문제가 사라진다. 병목 보고서 1번 항목과 같은 결론이다.

### 4-4. 검색·API 서비스: 유휴 CPU 문제가 구조적으로 없다

frontend·search·core-api는 `cpu_idle=true`(기본값)라 요청이 없을 때 CPU가 스로틀되고 과금도 요청 처리 시간 기준이다. 유휴 CPU를 비용으로 지불하지 않는 구조다. LLM 대기 4.7초 동안에도 async 이벤트 루프가 다른 요청을 처리할 수 있으므로 CPU 유휴가 아니라 요청 슬롯 점유가 문제이고, 이는 병목 보고서 6번에서 다뤘다.

## 우선순위 정리

지금 실행할 가치가 있는 것(비용 작음, 근거 확보됨):

1. **배치 장벽 제거**(갭 1-1) — 청크 보강은 바깥 루프 제거만으로 끝난다. STT 파트도 같은 패턴. 다만 편차 실측 후 적용해도 손해가 없으므로 부하테스트와 순서는 바꿔도 된다.
2. **임베딩 거부 시 Worker 동작 확인**(갭 2-3) — 코드 확인만으로 되는 항목. 거부가 파이프라인 실패로 끝나는 구조라면 부하테스트 전에 알아야 한다.

부하테스트에서 관측할 것:

3. 사용자 2명 이상 동시 업로드 시나리오에서 후순위 사용자의 대기 시간(갭 2-1)
4. Worker Cloud Run CPU 사용률과 색인 처리량의 관계(갭 4-1)
5. 색인 다건 동시 처리 시 Vision·STT 429 발생 여부(갭 2-4)
6. 영상 2건 이상이 임베딩 단계에서 겹칠 때의 queue wait와 거부(갭 2-3)

실측 후 판단할 것:

7. 사용자 간 공정성 장치의 구현 여부와 위치(갭 2-1) — 발행 시점 상한이 유력(제안)
8. Worker 동시성·인스턴스 확장(갭 2-2, 4-1) — 멱등성 검증이 선행 조건
9. 단계 간 파이프라이닝(갭 1-2) — 색인 지연이 문제로 확인되기 전에는 보류
