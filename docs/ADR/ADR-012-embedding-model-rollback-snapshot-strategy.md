# [ADR-012] 임베딩 모델 롤백 스냅샷 전략

* **상태 (Status):** 제안됨 (Proposed)
* **날짜 (Date):** 2026-06-01

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** Feedback Loop Pipeline은 새 임베딩 모델을 학습·평가한 뒤 운영 인덱스로 교체(cutover)한다. 교체된 모델이 검색 품질을 떨어뜨리면 직전 안정 버전으로 되돌려야 한다. 롤백 요청 경로와 직전 버전 복원은 이미 일부 구현되어 있다(feat/90 기준).
* **문제:** 임베딩 모델 롤백은 모델만 되돌려서는 안 된다. 모델과 그 모델로 만든 벡터 인덱스는 같은 벡터 공간을 공유하므로 한 쌍으로 묶여 움직여야 한다. 또한 새 모델이 운영되던 기간에 들어온 영상은 직전 버전 인덱스에 존재하지 않으므로, 복원 후에도 그 구간 데이터를 다시 색인해야 검색 결과가 일관된다.
* **현재 한계:** 복구 기준점이 직전 한 세대만 보존된다. 운영 상태 행에 직전 모델 버전과 인덱스 이름을 덮어쓰는 컬럼 세 개(`rollback_snapshot_active_model_version`, `rollback_snapshot_active_index_name`, `rollback_snapshot_captured_at`)로만 관리하기 때문이다. 다단계 롤백, 복구지점 선택, 롤백 안전성 판단, 계보 추적이 불가능하다.
* **목표:** 벡터 저장소가 PostgreSQL 기반 pgvector라는 점을 전제로, 빠르고 안전한 운영 롤백 경로를 정의한다. 동시에 복구 기준점을 다세대로 보존하고, 롤백 후 데이터 정합성 복구 절차까지 하나의 결정 체계 안에 둔다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 현행 단일 세대 포인터 유지

운영 상태 행에 직전 안정 버전의 모델·인덱스 이름을 덮어쓰는 방식을 그대로 둔다. 롤백은 그 이름으로 운영 포인터를 되돌린다.

**Pros**
* 추가 구현이 거의 없다.
* 롤백이 포인터 한 번 전환으로 끝나 빠르다.

**Cons**
* 복구 기준점이 직전 한 세대뿐이다. 두 단계 이전으로 되돌릴 수 없다.
* 롤백 안전성(복원 가능 여부) 판단, 계보, 문제 구간 같은 운영 정보를 담을 자리가 없다.
* 옛 인덱스를 정리(GC)하기 시작하면 포인터가 가리키는 대상이 사라져 복원이 깨진다.

### 2. 전면 스토리지 스냅샷 피봇

모델 파일뿐 아니라 벡터 데이터까지 객체 스토리지에 덤프로 저장하고, 롤백 시 스토리지에서 내려받아 다시 적재한다.

**Pros**
* 벡터까지 운영 DB와 독립적으로 보존되어 내구성이 가장 높다.
* 벡터 저장소를 교체하거나 다중 저장소로 복제하는 상황에도 스냅샷이 살아남는다.

**Cons**
* 벡터 적재는 시간이 오래 걸려 롤백이 더 이상 즉시 복구가 아니다.
* 덤프를 되돌릴 때 원본 청크·영상과의 참조 정합성을 별도로 보장해야 한다.
* pgvector는 인덱스를 DB 내부 자산으로 유지하므로, 굳이 파일로 빼냈다가 되읽는 비용 대비 이득이 현 단계에서 낮다.

### 3. pgvector 인덱스 보존 + 스냅샷 레지스트리 (채택)

벡터 인덱스는 PostgreSQL 안에 버전별로 살려 두고, 운영 롤백은 운영 포인터 전환으로 처리한다. 스냅샷의 식별·검증·계보 정보는 별도의 추가 전용(append-only) 레지스트리 테이블에 보존한다. 모델 파일과 매니페스트, 평가 보고서 같은 불변 산출물만 객체 스토리지에 둔다.

**Pros**
* 롤백이 포인터 전환이라 빠르다. pgvector에 직전 인덱스가 그대로 살아 있어 재적재가 필요 없다.
* 레지스트리가 복구 기준점을 다세대로 보존하고, 롤백 안전성·계보·문제 구간을 담는다.
* 모델 파일 저장은 이미 있는 산출물 저장 경계를 재사용한다.
* 향후 스토리지 기반 복원이 필요해지면 기존 복원 추상화(`SnapshotIndexRestorePort`) 구현체만 교체하면 된다.

**Cons**
* 레지스트리 테이블 신설과 데이터 이행이 필요하다.
* 벡터 자체의 장기 내구성은 별도 백업·보관 정책으로 따로 다뤄야 한다.
* 운영 인덱스를 정리하는 시점에는 보존 가드가 추가로 필요하다.

## 3. 결정 사항 (Decision Outcome)

* **3번, pgvector 인덱스 보존 + 스냅샷 레지스트리 방식을 채택한다.**
* **2번 전면 스토리지 피봇은 벡터 장기 보관이나 저장소 교체가 실제로 필요해질 때 재해 복구용으로 재검토한다.**
* **1번 단일 세대 포인터는 현 단계에서 유지하지 않는다. 복구 기준점 보존 한계가 분명하기 때문이다.**

**이유**
* 벡터 저장소가 pgvector이므로 직전 인덱스가 DB 안에 이미 살아 있다. 운영 롤백에는 파일 복원이 아니라 포인터 전환이 가장 빠르고 안전하다.
* 현재 한계의 원인은 저장 위치가 아니라, 스냅샷을 운영 상태 행의 덮어쓰기 컬럼에 둔 데이터 모델이다. 이를 다세대 레지스트리로 옮기면 해결된다.
* 모델 파일은 이미 산출물 저장 경계에 보관되고 있어, 스냅샷이 가리켜야 할 불변 자산의 내구성은 추가 비용 없이 확보된다.
* 시스템이 구버전 데이터를 온라인 평가 목적으로 의도적으로 보존한다는 기존 정책과, 인덱스를 DB에 살려 두는 이 방식이 정합한다.

## 4. 결정된 설계 원칙 (Decision Details)

* **스냅샷 단위:** 스냅샷은 데이터 전체 복사본이 아니라 복원 가능한 포인터 묶음이다. 한 스냅샷은 임베딩 모델 버전, 벡터 인덱스 이름, 임베딩 차원, 모델 산출물 위치, 상태, 롤백 안전 여부, 직전 스냅샷 참조, 문제 구간을 가진다.
* **저장 책임 분리:**
  * 검색에 쓰는 벡터는 PostgreSQL(pgvector) 안에 한 테이블로 두고, 인덱스 이름(`index_name`)으로 버전을 구분한다. 버전마다 물리 테이블을 따로 만들지 않는다.
  * 모델 파일·매니페스트·평가 보고서 같은 불변 산출물은 객체 스토리지에 둔다.
  * 어느 스냅샷이 어떤 모델과 인덱스를 가리키는지는 레지스트리 테이블이 보존한다.
* **벡터 검색 방식:** 현재 벡터 검색은 pgvector 거리 연산자 기반의 정확 최근접 탐색(exact KNN)이다. 별도의 근사 최근접(ANN) 인덱스(HNSW 등)는 두지 않는다. 임베딩 차원이 확정되고 데이터 규모가 커지는 시점에, 한 테이블 구조를 유지한 채 버전별 부분 인덱스(partial index) 또는 인덱스 이름 기준 리스트 파티셔닝으로 ANN을 도입한다. 이렇게 하면 버전 간 벡터 공간이 섞이지 않고, 인덱스 이름 필터가 해당 버전 인덱스로 그대로 좁혀진다. Search Service Spec이 벡터 후보 조회를 "ANN"으로 부르는 것은 개념 수준의 명칭이며, 특정 인덱스 알고리즘을 강제하지 않는다.
* **운영 포인터:** 운영 환경은 활성 모델 버전과 활성 인덱스 이름을 함께 바라본다. 두 값은 항상 하나의 트랜잭션에서 같이 전환해 모델과 인덱스가 어긋나지 않게 한다.
* **롤백 검증:** 롤백을 실행하기 전에 대상 스냅샷이 복원 가능한지 확인한다. 대상 모델 산출물이 존재하고 서빙 가능한지, 대상 인덱스가 살아 있고 벡터가 존재하는지, 임베딩 차원이 현재 서비스와 호환되는지, 롤백 안전 표시가 참인지 확인한다. 하나라도 실패하면 롤백을 진행하지 않는다.
* **문제 구간 재색인:** 문제 모델이 운영되던 기간에 들어와 그 모델로만 색인된 콘텐츠는, 복원된 모델로 다시 임베딩해 운영 인덱스에 채운다. 임베딩 입력은 보강 텍스트가 있으면 그것을, 없으면 원문 텍스트를 사용한다. 원본 텍스트와 피드백 로그 같은 원천 데이터는 보존하고, 잘못된 모델로 만든 파생 벡터만 재생성한다.
* **재색인 중 프로젝트 제한:** 재색인이 끝나기 전까지 해당 프로젝트는 검색과 영상 업로드를 제한한다. 현재 검색 제한에 쓰는 프로젝트 서빙 상태(`ROLLBACK_EXCLUDED`)를 업로드 제한까지 확장한다. 재색인이 끝나면 서빙 가능 상태로 되돌린다.
* **이행 범위:** 운영 상태 행의 단일 세대 스냅샷 컬럼은 레지스트리 테이블로 대체한다. 복원 추상화 경계는 유지하고, 검증 강화와 재색인 절차를 그 경계 안에서 확장한다.

## 5. 긍정적 효과 (Positive Consequences)

* 운영 롤백이 포인터 전환으로 끝나 복구가 빠르다.
* 복구 기준점을 다세대로 보존하므로 두 단계 이전으로의 롤백과 복구지점 선택이 가능해진다.
* 롤백 안전 여부와 계보, 문제 구간이 한곳에 남아 장애 분석 시 추측이 줄어든다.
* 모델과 인덱스를 한 쌍으로 묶어 전환하므로 벡터 공간 불일치 사고를 막는다.
* 향후 스토리지 기반 복원이 필요해져도 복원 추상화 구현체만 바꾸면 되어 확장 경로가 열려 있다.

## 6. 부정적 효과 및 위험 요소 (Negative Consequences)

* 레지스트리 테이블 신설과 기존 스냅샷 컬럼 이행이 필요하다.
  * **대응:** 추가 전용 테이블을 먼저 도입하고, 교체 시점에 직전 스냅샷 한 건을 레지스트리로 옮긴 뒤 컬럼 의존을 제거한다.
* 벡터 인덱스를 DB에 계속 보존하면 저장량이 누적된다.
  * **대응:** 인덱스 정리를 도입할 때 직전 안정 스냅샷이 가리키는 인덱스는 정리 대상에서 면제하는 보존 가드를 둔다.
* 문제 구간 재색인은 시간이 걸리고, 그동안 해당 프로젝트의 서비스가 제한된다.
  * **대응:** 재색인 대상을 문제 모델로 색인된 콘텐츠로 한정하고, 진행 상태를 관찰 가능하게 남긴다. 완료 시 자동으로 서빙 상태를 회복한다.
* 벡터 자체의 장기 내구성은 이 결정 범위 밖이다.
  * **대응:** 재해 복구용 DB 백업·보관과 스토리지 덤프는 별도 정책으로 다루고, 인덱스 정리나 저장소 교체가 실제로 필요해지는 시점에 재검토한다.
