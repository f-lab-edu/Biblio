# ADR-003-search-index-tenancy-strategy

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-02-21

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 현재 Biblio는 유저가 업로드한 '복수의 영상들'을 대상으로 하이브리드 검색(키워드 + 벡터)을 제공해야 하며, 이를 위한 검색 저장소(인덱스)의 테넌시(Tenancy) 전략을 결정해야 한다.
* (전제) 원본 메타데이터와 권한은 RDB(단일 진실 공급원, SOT)가 관리하며, 검색 인덱스는 Outbox 패턴을 통해 동기화되는 파생 데이터로 취급한다.


* **문제:** * 검색 시 타인의 데이터 유출을 막기 위해 사용자 아이디(`tenant_id`) 필터링이 필수적이나, 벡터 검색(ANN) 특성상 필터링과 결합할 때 검색 품질(Recall)과 속도가 저하될 위험이 있다.
* 사용자별로 인덱스를 완전히 분리하면 검색 품질은 보장되나, 사용자가 늘어날수록 인덱스 개수가 폭증해 치명적인 인프라 운영 병목(생성, 백업, 모니터링 등)이 발생한다.
* 반대로 단일 공용 인덱스를 사용할 경우, 코드 실수로 인한 데이터 유출 위험과 특정 헤비 유저가 시스템 전체를 느리게 만드는 'Noisy Neighbor' 문제를 통제해야 한다.


* **목표:** * **보안/격리:** 타 사용자의 데이터가 절대 노출되지 않도록 완벽히 통제한다.
* **성능/품질:** 필터링 환경에서도 일관된 검색 속도와 품질을 보장한다.
* **운영/확장:** 초기에는 최소한의 인력으로 운영 가능하게 설계하고, 추후 필요 시 특정 사용자만 별도로 확장할 수 있는 유연성을 확보한다.
* **전환 가능성:** 향후 아키텍처 변경(공용 ↔ 전용) 시 마이그레이션 비용을 최소화한다.



## 2. 고려한 대안들 (Considered Options)

* **대안 1:** 공용 인덱스 (Shared Multi-tenant Index)
* 모든 사용자의 데이터를 하나의 거대한 인덱스에 몰아넣고, 검색할 때마다 필수적으로 `tenant_id`로 필터링하는 방식.


* **대안 2:** 사용자별 전용 인덱스 (Dedicated Per-tenant Index)
* 사용자마다 물리적으로 독립된 인덱스(컬렉션)를 생성하여 데이터 자체를 완전히 격리하는 방식.


* **대안 3:** 하이브리드 (Hybrid: Shared by default + Tenant Promotion)
* 기본적으로는 대안 1(공용 인덱스)을 사용하여 자원을 공유하되, 트래픽이나 데이터량이 폭증하는 특정 대형 사용자만 대안 2(전용 인덱스)로 승격(Promote)시켜 격리하는 방식.
* **MVP 범위:** 우선 "공용 인덱스 운영"까지만 구현하며, 사용자 승격 기능은 추후 확장 옵션으로 남겨둔다.



## 3. 결정 사항 (Decision Outcome)

* **우리는 '대안 3 (하이브리드 전략)'을 선택한다.** * **단, 초기 MVP 구현은 "단일 공용 인덱스 구축 및 `tenant_id` 필터 강제"까지만 진행하며, 승격(Promotion) 로직은 당장 구현하지 않는다.**
* **이유:**
* **운영 복잡도 최소화:** MVP 단계에서는 인덱스 폭증 리스크를 피하고 인프라 관리를 단순화하여, E2E 파이프라인을 빠르게 런칭하는 것이 가장 중요하기 때문이다.
* **품질 저하 통제 가능:** 공용 인덱스에서 우려되는 벡터 검색 품질(Recall) 저하 문제는 최신 DB 엔진의 기능(필터-어웨어, 폴백)과 백엔드 앱 레벨의 보정 로직을 통해 충분히 방어할 수 있다고 판단했기 때문이다.
* **DB 종속성 탈피:** DB의 복잡한 테넌시 구조를 상위 인터페이스(`Search Adapter` 등) 뒤로 캡슐화해 두면, 추후 구조를 변경하더라도 비즈니스 로직에 미치는 영향을 최소화할 수 있다.
* **추가 고려:** 승격(Promotion)을 위한 무정지 데이터 이관(Backfill, Dual-write)은 구현 난이도가 높으므로, 현재는 아키텍처 상의 '자리(라우팅 규약)'만 만들어 두고 나중에 도입한다.



## 4. 긍정적 효과 (Positive Consequences)

* **운영 단순성:** MVP 인프라를 단일 인덱스로 유지하여 모니터링, 백업, 업그레이드 포인트가 하나로 집중된다.
* **비용 효율:** 수많은 소형 사용자들이 자원을 하나의 풀(Pool)에서 공유하므로, 불필요한 인덱스 생성 유지비(Base Cost) 누적을 막을 수 있다.
* **검색 스코프의 유연성:** 단일 공간에 데이터가 모여 있어, `tenant_id`와 `video_id`를 조합하면 "내 전체 영상 검색" 또는 "특정 영상 검색" 등 요구사항 변화에 유연하게 대응할 수 있다.
* **미래 확장성 확보:** 당장 구현하지 않더라도, 트래픽이 커졌을 때 대형 사용자를 분리해 낼 명확한 전략적 경로(승격)가 마련되어 있다.

## 5. 부정적 효과 및 위험 요소 (Negative Consequences)

* **필터 누락 시 데이터 유출 위험:** 공용 공간이므로 코드 실수로 `tenant_id` 필터가 빠지면 대형 보안 사고가 발생한다.
-> **대응 방안:** `tenant_id` 누락 시 검색을 원천 차단(Deny-by-default)하고, 공통 Query Builder 사용을 강제한다. 또한, 타인 데이터 노출을 막는 통합 테스트를 의무화하며, 최종 검색 응답 전 RDB(SOT)를 통해 권한을 한 번 더 교차 검증(서빙 게이트)한다.
* **Noisy Neighbor 문제:** 한 사용자의 과도한 활동이 전체 DB의 성능을 떨어뜨릴 수 있다.
-> **대응 방안:** 사용자별 API 요청 수(Rate limit)와 쿼리 비용 상한을 설정하여 폭주를 막는다. 근본적인 해결책인 사용자 승격(Promotion)은 추후 확장 시 도입한다.
* **필터링으로 인한 벡터 검색 품질(Recall) 하락:** 검색 대상이 너무 좁을 경우 ANN 알고리즘이 결과를 제대로 찾지 못할 수 있다.
-> **대응 방안:** 필터링에 최적화된 최신 벡터 엔진을 사용한다. 만약 DB가 찾아온 결과가 부실하다면, 백엔드 애플리케이션에서 탐색 깊이(`ef_search`)를 강제로 늘리거나 전체 스캔(Exact Search)으로 재검색하는 보정 로직을 추가한다. 동시에 p99 응답 속도와 결과 누락 비율을 상시 모니터링한다.
* **(추후) 승격 도입 시 운영 복잡도 증가:** 향후 대형 사용자를 분리하려면, 라이브 환경에서 무정지로 데이터를 옮기는 복잡한 작업(Dual-write 등)이 필요하다.
-> **대응 방안:** MVP 단계에서는 구현하지 않되, `Search Orchestrator`라는 단일 라우터를 통해서만 DB에 접근하도록 설계하여 추후 이관 로직이 추가될 때의 코드 영향 범위를 최소화한다.
