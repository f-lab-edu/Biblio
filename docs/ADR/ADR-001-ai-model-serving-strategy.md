# [ADR-001] ai-model-serving-strategy

* **상태 (Status):** [제안됨(Proposed)]
* **날짜 (Date):** 2026-02-15

## 1. 배경 및 문제 상황 (Context and Problem Statement)
* **상황:** 현재 우리는 **Biblio(영상 기반 지식 아카이브)**에서 “영상 업로드 → STT/청킹/임베딩 → 검색 → RAG 답변”까지의 E2E 파이프라인을 개발하고 있다.

* **문제:** AI 기능(STT / Embedding / LLM)을 붙이려면 모델 서빙이 필요한데,

    검색 응답 5초 이내, 1시간 영상 10분 내 검색 가능 상태 같은 목표를 만족해야 하고,<br>
    트래픽 폭주 시에도 검색은 유지되어야 하며,<br>
    동시에 **운영 복잡도(서빙/스케일링/GPU/장애대응)**를 과도하게 키우고 싶지 않다.

* **목표:** 복잡도를 최소화하면서도 비기능적 요구사항을 만족하는 AI 인프라 아키텍처 의사결정을 내린다.

## 2. 고려한 사안들 (Considered Options)
* **사안 1:** 전부 외부 API 사용
* **사안 2:** STT/LLM은 외부, Embedding은 Managed Self-host
    
    - LLM & STT: 외부 API (OpenAI, Gemini 등)<BR>

    - Embedding: 오픈소스 모델(Hugging Face 등)을 선정하여 클라우드 관리형 엔드포인트(예: Vertex AI Endpoint, AWS SageMaker)에 배포.<BR>

* **사안 3:** STT/LLM은 외부, Embedding은 완전 로컬(Self-host)

    - LLM(RAG): 외부 LLM API<BR>

    - STT: 외부 STT API<BR>

    - Embedding:  인프라(K8s/VM)에서 GPU 포함 완전 서빙(자가 운영)

## 3. 결정 사항 (Decision Outcome)
* **사안2(STT/LLM은 외부, Embedding은 Managed Self-host)를 선택했다.**
* **이유:**
  1) 복잡도 최소화 vs 통제력의 균형이 가장 좋다.
     외부 블랙박스 Embedding API(대안 1)는 가장 단순하지만 “모델 버전 고정/교체/롤백/재임베딩”을 우리 기준으로 운영하기 어렵고, 장기적으로 락인 위험이 크다.<br>
    완전 로컬(대안 3)은 통제력은 최고지만 GPU/서빙/오토스케일/장애 대응으로 복잡도가 급증한다.<br>

  2) 임베딩 모델 1개 통일(검색/색인 동일 모델)을 “가장 안전하게” 만족시킬 수 있다.<br>
    동일 모델 아티팩트(가중치/토크나이저/전처리/정규화/차원)를 고정한 채로, 검색과 색인 모두 같은 Endpoint를 호출하면 일관성이 깨질 여지가 적다. <br>

  3) 프로젝트 목표에 더 집중 할수 있다.<br>
    본 프로젝트의 핵심 목표는 고성능 모델을 밑바닥부터 만드는 것이 아니라, **"데이터 수집부터 서빙까지의 End-to-End 파이프라인을 견고하게 구축"**하는 데 있다.현시점에서 STT와 LLM을 자체 구축/서빙하는 것은 인프라 복잡도 대비 프로젝트 목표 기여도가 낮다. 때문에 이미 품질이 보장된 외부 API를 활용함으로써, 파이프라인의 안정성과 데이터 흐름(Data Flow) 설계에 더 집중 하기 위함이다.

## 4. 긍정적 효과 (Positive Consequences)
* 인프라 운영 오버헤드 최적화 : STT와 LLM을 위한 고성능 GPU 클러스터(K8s 등)를 직접 구축하고 유지보수할 필요가 없어, 시스템 복잡도와 운영 인력 리소스를 획기적으로 절감한다.<br>

* 핵심 기능의 통제권 및 확장성 확보: 임베딩 모델을 자체 관리(Managed Endpoint)함으로써, 외부 API의 정책 변경이나 모델 단종(Deprecation) 리스크 없이 안정적인 서비스 운영이 가능하며, 추후 도메인 특화(Fine-tuning)를 위한 기술적 기반을 미리 확보한다.<br>

* 초기 품질 확보 및 개발 속도 가속화 (Time-to-Market): 별도의 학습 없이도 SOTA(State-of-the-Art) 수준의 외부 STT/LLM 모델을 즉시 활용함으로써, MVP 단계에서 높은 정확도의 검색 및 요약 품질을 보장하고 비즈니스 로직 구현에 집중할 수 있다.

## 5. 부정적 효과 및 위험 요소 (Negative Consequences)
* 초기 인프라 구축의 복잡성 : 완전 외부 API(대안 1) 방식에 비해, 임베딩 모델을 컨테이너화하고 Vertex AI Endpoint에 배포/연동하는 초기 DevOps 공수가 발생한다.<br>

대응 방안: Terraform을 활용한 IaC(Infrastructure as Code)를 도입하여 인프라 프로비저닝을 자동화하고, 배포 파이프라인을 표준화한다.

* 외부 API 비용의 변동성 : 트래픽이 급증할 경우 토큰 단위로 과금되는 외부 STT/LLM 비용이 선형적으로 증가하여 예산을 초과할 위험이 있다.<br>

대응 방안: 사용자별/일별 API 호출 쿼터(Quota)를 설정하고, 비용 임계값 도달 시 알림을 보내는 모니터링 시스템을 구축한다.

* 외부 의존성 및 네트워크 지연 : 외부 API 서버의 장애나 네트워크 지연이 발생할 경우, 전체 서비스의 가용성과 응답 속도(5초 목표)에 직접적인 영향을 줄 수 있다.<br>

대응 방안: 서킷 브레이커(Circuit Breaker) 패턴을 적용하여 장애 확산을 방지하고, STT 등 시간이 오래 걸리는 작업은 비동기 큐(Queue)로 처리하여 사용자 대기 시간을 최소화한다.
