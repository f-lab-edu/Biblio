# [ADR-015] 모델 학습 자동화보다 배포·롤백 검증 우선

* **상태 (Status):** 승인됨(Accepted)
* **날짜 (Date):** 2026-06-24

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** Biblio는 사용자 피드백을 학습 데이터셋으로 만들고, 후보 임베딩 모델을 배포한 뒤 문제가 생기면 이전 모델로 롤백하는 피드백 루프를 구축하고 있다.
* **문제:** 현재 학습 단계의 산출물은 메타데이터와 평가용 JSON 중심이라 임베딩 엔드포인트가 직접 로드할 수 있는 모델 artifact가 아니다. 이 상태에서는 후보 모델 배포, active 전환, 롤백, 인덱스 정합성 검증을 배포 환경에서 끝까지 확인하기 어렵다. 실제 학습까지 완전 자동화하려면 학습 서버, GPU/CPU 자원, 학습 실패 처리, 평가 기준, 비용 통제도 함께 필요하다.
* **목표:** 현재 단계에서는 성능이 더 좋은 모델을 자동으로 만드는 일보다, 모델 버전이 바뀔 때 서비스가 안전하게 배포·전환·롤백되는지 검증하는 일을 우선한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 학습 파이프라인 완전 자동화

피드백 데이터셋이 준비되면 배포 환경의 학습 서버가 실제 모델 학습을 수행하고, 산출물을 후보 모델로 등록한다.

**Pros**
* 학습부터 배포까지 이어지는 ML 파이프라인을 자동화할 수 있다.
* 충분한 데이터와 평가 기준이 생기면 반복 학습과 모델 승격을 자동화하기 쉽다.
* 운영형 ML 플랫폼으로 확장하기 좋은 구조다.

**Cons**
* 학습용 CPU/GPU 자원 비용이 크다.
* 현재 데이터셋 규모와 평가 기준으로는 자동 학습 결과의 품질을 신뢰하기 어렵다.
* 학습 실패, 재시도, artifact 검증, 로그, 재현성까지 운영 범위에 들어온다.
* 현재 목표인 배포·롤백 검증보다 범위가 커진다.

### 2. 외부 학습 후 artifact만 배포 파이프라인에 입력

학습은 로컬, Colab, 임시 GPU 환경처럼 비용을 통제하기 쉬운 곳에서 수행한다. 배포 환경은 학습 산출물을 표준 artifact로 받아 후보 모델 등록, endpoint reload, active 전환, 롤백을 처리한다.

**Pros**
* 학습 비용을 필요할 때만 쓰도록 통제할 수 있다.
* 배포·롤백 파이프라인은 실제 운영 경로로 검증할 수 있다.
* 학습 환경과 serving 환경의 책임을 분리할 수 있다.
* 1인 포트폴리오나 초기 서비스 단계에 맞는 현실적인 범위다.

**Cons**
* 학습 실행 자체는 완전 자동화되지 않는다.
* 학습 환경 재현성을 별도로 관리해야 한다.
* artifact 업로드와 후보 등록 절차가 명확하지 않으면 수동 실수가 생길 수 있다.

### 3. active 모델을 candidate 버전 artifact로 복제해 배포·롤백 검증

실제 성능 개선 학습은 수행하지 않는다. 현재 active 모델과 같은 모델 파일을 후보 모델 버전의 artifact 경로에 준비하고, 모델 버전만 바뀐 상태로 배포·전환·롤백 경로를 검증한다.

**Pros**
* 임베딩 엔드포인트가 로드할 수 있는 후보 모델 artifact를 빠르게 만들 수 있다.
* 학습 인프라 없이도 모델 버전 전환, candidate index 생성, 롤백 정합성을 검증할 수 있다.
* 현재 문제인 "로드 가능한 후보 모델 부재"를 가장 작게 해결한다.
* 학습 품질 문제가 배포·롤백 검증을 방해하지 않는다.

**Cons**
* 후보 모델과 active 모델의 성능 차이는 검증할 수 없다.
* 오프라인 평가는 품질 판단보다 배포 gate 동작 확인에 가깝다.
* 나중에 실제 학습 산출물을 받을 수 있는 artifact 계약을 별도로 구체화해야 한다.

### 4. 작은 오픈소스 임베딩 모델로 실제 학습까지 검증

`bge-m3`보다 가벼운 임베딩 모델을 실험용 후보 모델로 사용해 실제 fine-tuning을 수행한다. 이후 해당 산출물을 후보 모델로 배포한다.

**Pros**
* 실제 학습 산출물이 배포 파이프라인을 통과하는지 확인할 수 있다.
* 학습 비용을 큰 모델보다 줄일 수 있다.
* 향후 모델 품질 개선 실험으로 확장하기 좋다.

**Cons**
* active 모델과 차원이 다르면 별도 인덱스 생성과 재색인 정책이 필요하다.
* 작은 모델의 성능이 현재 모델보다 낮을 수 있다.
* 모델 family가 달라지면 평가 기준과 운영 해석이 복잡해진다.
* 배포·롤백 검증이라는 현재 목표보다 범위가 커질 수 있다.

## 3. 결정 사항 (Decision Outcome)

* **3번, active 모델을 candidate 버전 artifact로 복제해 배포·롤백 검증을 우선한다.**
* **2번, 외부 학습 후 artifact만 배포 파이프라인에 입력하는 방식은 다음 확장 방향으로 둔다.**
* **1번 학습 파이프라인 완전 자동화와 4번 작은 모델 fine-tuning은 현 단계에서 채택하지 않는다.**

**이유**
* 현재 단계의 핵심 목표는 모델 품질 개선이 아니라 후보 모델 배포, active 전환, 롤백, 인덱스 정합성 검증이다.
* 학습 서버와 GPU 자원을 배포 환경에 붙이면 비용과 운영 부담이 커진다.
* 모델 내용이 같더라도 모델 버전과 artifact 경로가 바뀌면 endpoint reload와 release 상태 전환을 실제 경로로 검증할 수 있다.
* 실제 학습은 충분한 데이터셋과 오프라인 평가 기준이 준비된 뒤 외부 학습 산출물 업로드 방식으로 붙이는 편이 현재 규모에 맞다.

## 4. 결정된 설계 원칙 (Decision Details)

* 학습 자동화보다 모델 운영 자동화를 먼저 검증한다.
* 후보 모델은 임베딩 엔드포인트가 실제로 로드할 수 있는 artifact여야 한다.
* 후보 모델 버전은 active 모델과 다른 값을 사용한다.
* 후보 artifact는 active artifact와 내용이 같을 수 있지만, candidate 버전의 독립 경로에 준비한다.
* 모델 전환 검증은 후보 모델 로드, candidate index 생성, active 전환, 롤백, snapshot/index 정합성 확인을 포함한다.
* 오프라인 평가는 현 단계에서 품질 우위 판단이 아니라 배포 gate 동작 확인 용도로 본다.
* 실제 fine-tuning은 배포 파이프라인의 필수 전제가 아니다.
* 외부 학습 환경을 사용할 경우에도 artifact manifest, 학습 메타데이터, 데이터셋 버전, 모델 버전을 남겨 재현 가능성을 보완한다.

## 5. 긍정적 효과 (Positive Consequences)

* 학습 인프라 비용 없이 배포·롤백 경로를 먼저 닫을 수 있다.
* 후보 모델이 실제 endpoint에서 로드되는지 검증할 수 있다.
* active, previous, candidate 모델 버전 전환 계약을 명확히 확인할 수 있다.
* 롤백 후 검색 인덱스와 프로젝트 상태 정합성을 검증할 수 있다.
* 추후 실제 학습 산출물이 들어와도 같은 배포 경로를 재사용할 수 있다.

## 6. 부정적 효과 및 위험 요소 (Negative Consequences)

* 후보 모델의 품질 개선 여부는 검증하지 못한다.
  * **대응:** 이번 검증 결과를 모델 품질 개선으로 해석하지 않는다. 품질 평가는 별도 오프라인 평가 체계가 준비된 뒤 수행한다.
* active와 candidate의 임베딩 결과가 같아 검색 결과 차이가 거의 없을 수 있다.
  * **대응:** 이번 단계에서는 검색 결과 차이가 아니라 버전 전환과 정합성 유지 여부를 성공 기준으로 둔다.
* 실제 학습 산출물 업로드 계약이 늦게 정의될 수 있다.
  * **대응:** candidate artifact 경로, manifest, metadata, model version 계약은 현재 단계에서 유지하고, 외부 학습 산출물 업로드는 후속 이슈로 분리한다.
* 학습 자동화가 없으므로 반복 학습 운영에는 한계가 있다.
  * **대응:** 데이터셋 규모, 평가 기준, 학습 빈도, 비용 대비 효과가 커지는 시점에 학습 파이프라인 자동화를 별도 ADR로 재평가한다.

## 7. 결정 이후 후속 결과 (Consequences)

* 피드백 루프의 후보 모델 생성 단계는 우선 active 모델 artifact를 candidate 버전 경로로 준비할 수 있어야 한다.
* candidate artifact가 준비되면 기존 모델 release 흐름을 통해 endpoint reload, candidate index 생성, active 전환, rollback을 검증한다.
* 실제 fine-tuning은 Colab, 로컬, 임시 GPU 같은 외부 학습 환경에서 수행한 뒤 표준 artifact로 업로드하는 방향을 후속으로 검토한다.
* 작은 임베딩 모델을 이용한 실제 학습 실험은 모델 차원, 인덱스 생성, 재색인 정책을 함께 검토하는 별도 이슈로 분리한다.
