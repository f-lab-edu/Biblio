# [ADR-003] chunking-strategy

* **상태 (Status):** Proposed
* **날짜 (Date):** 2026-03-07

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** Biblio는 업로드된 비디오로부터 STT 스크립트를 생성하고, 이를 청킹하여 임베딩 및 하이브리드 검색(FTS + Vector)과 RAG 응답 생성에 활용하는 구조를 채택하고 있다.
* **문제:** 청킹은 검색 품질, 임베딩 비용, 타임스탬프 근거 정밀도, 파이프라인 복잡도에 직접적인 영향을 준다. 현재 `system-design.md`에는 "문맥 단위 청킹"이라는 방향성만 정의되어 있고, 실제 청킹 전략은 아직 확정되어 있지 않다.
* **목표:** MVP 단계에서 구현 및 운영 복잡도를 과도하게 높이지 않으면서도, 검색과 RAG에 충분한 문맥을 제공하고 타임스탬프 근거를 안정적으로 유지할 수 있는 청킹 전략을 선택한다.

## 2. 고려된 옵션들 (Considered Options)

### 1. 고정 길이 기반 청킹

전체 스크립트를 문자 수 또는 토큰 수 기준으로 고정 길이로 절단하고, 일부 overlap만 적용한다.

**Pros**
* 구현이 가장 단순하고 재현성이 높다.
* 처리 속도가 빠르고 튜닝 포인트가 적다.
* 파이프라인 테스트가 쉽다.

**Cons**
* 문장 중간 절단이 발생하여 검색 품질이 흔들릴 수 있다.
* 하나의 청크에 여러 주제가 섞이거나, 반대로 의미가 약한 파편 청크가 늘어날 수 있다.
* 타임스탬프 근거가 어색하게 잘릴 가능성이 높다.

### 2. 문장 경계 + 길이 제한 + overlap 기반 청킹

STT 결과인 `TranscriptSegment`를 순서대로 읽으며 문장을 복원하고, 복원된 문장들을 최대 토큰 길이까지 묶어 하나의 청크를 만든다. 다음 청크는 직전 청크의 마지막 일부 문장을 overlap으로 포함한다.

**Pros**
* 문장 단위 의미를 보존하면서도 청크 크기를 통제할 수 있다.
* FTS와 벡터 검색 모두에 무난한 품질의 검색 단위를 제공한다.
* `TranscriptSegment`의 `start_ms`, `end_ms`를 집계해 청크 타임스탬프를 안정적으로 만들 수 있다.
* 구현 난이도와 검색 품질 사이의 균형이 가장 좋다.
* `chunking_version`을 통해 이후 전략 교체나 재색인에도 대응하기 쉽다.

**Cons**
* 진짜 주제 전환을 이해하는 "의미 기반" 청킹보다는 정교함이 떨어질 수 있다.
* STT 문장 분리 품질이 나쁘면 청킹 품질도 영향을 받는다.
* overlap으로 인해 일부 중복 저장과 중복 검색 후보가 발생한다.

### 3. 문장 임베딩 유사도 기반 청킹

문장별 임베딩을 생성한 뒤, 인접 문장 간 유사도가 크게 낮아지는 지점을 경계로 잡아 청킹한다.

**Pros**
* 화제 전환을 반영한 의미 기반 청킹이 가능하다.
* 문장 경계 기반보다 응집도 높은 청크를 만들 가능성이 있다.
* 향후 검색 품질 고도화 방향으로 자연스럽다.

**Cons**
* 문장별 추가 임베딩 비용이 발생한다.
* threshold와 경계 탐지 규칙에 대한 튜닝이 필요하다.
* STT 품질, 문장 분리 품질, 임베딩 모델 품질의 영향을 함께 받는다.
* MVP 단계에서 복잡도 증가에 비해 성능 이점이 불확실하다.

### 4. LLM 기반 시맨틱 청킹

Gemini 등 외부 LLM에게 스크립트를 전달하여 의미 단위 청킹 경계와 구조를 직접 생성하게 한다.

**Pros**
* 의미 기반 청킹의 잠재적 품질이 가장 높다.
* 불규칙한 강의/설명형 스크립트에서도 자연스러운 경계 설정이 가능하다.

**Cons**
* 외부 API 비용과 지연이 크게 늘어난다.
* 출력 포맷 안정성, 재현성, 예외 처리 복잡도가 높다.
* 현재 파이프라인에 또 하나의 고비용 외부 의존성을 추가한다.
* MVP 단계에서 운영 복잡도 대비 효과가 불확실하다.

## 3. 결정 사항 (Decision Outcome)

* **2. 문장 경계 + 길이 제한 + overlap 기반 청킹을 기본 전략으로 선택한다.**
* **3은 추후 검색 품질 고도화 옵션으로 보류한다.**
* **4는 현재 단계에서 채택하지 않는다.**

**이유**
* 현재 서비스의 핵심 목표는 "검색 가능한 문맥 단위를 안정적으로 생성하여 하이브리드 검색과 RAG를 동작시키는 것"이며, 옵션 2가 이 목표를 가장 낮은 리스크로 만족시킨다.
* Biblio의 검색 구조는 FTS + Vector + RAG 조합이므로, 너무 짧은 세그먼트나 너무 긴 문서보다 "문장 몇 개가 묶인 중간 크기 문맥"이 더 적합하다.
* `TranscriptSegment`를 유지한 채 문장 복원 후 청킹하면, 검색 품질과 타임스탬프 정밀도 모두를 일정 수준 이상 확보할 수 있다.
* MVP 단계에서 병목이 실제로 청킹 전략에 있는지 아직 검증되지 않았으므로, 의미 기반 청킹을 먼저 도입하는 것은 비용과 복잡도 대비 우선순위가 낮다.

## 4. 결정의 세부 원칙 (Decision Details)

* 청킹의 입력은 STT 결과로 저장된 `TranscriptSegment`의 순차 목록이다.
* 워커는 인접한 `TranscriptSegment`를 읽으며 문장 경계를 복원한다.
* 복원된 문장들을 순서대로 누적하여 하나의 청크를 만들되, 청크 크기는 최대 토큰 길이로 제한한다.
* 청크를 마감한 뒤 다음 청크를 생성할 때는 직전 청크의 마지막 1~2문장 또는 전체의 약 10~15%를 overlap으로 재사용한다.
* 청크의 `start_ms`는 포함된 첫 `TranscriptSegment`의 시작 시각, `end_ms`는 마지막 `TranscriptSegment`의 종료 시각을 사용한다.
* 단일 문장 자체가 길이 제한을 초과하는 경우에만 예외적으로 문장 내부 분할을 허용한다.
* 청킹 결과에는 `chunking_version`을 기록하여 이후 전략 교체 및 재색인을 가능하게 한다.

## 5. 긍정적 효과 (Positive Consequences)

* 검색 품질, 구현 단순성, 운영 안정성 사이의 균형이 가장 좋다.
* FTS와 벡터 검색 양쪽에서 무난한 청크 품질을 기대할 수 있다.
* 타임스탬프 근거를 자연스럽게 유지할 수 있어 최종 응답의 레퍼런스 품질이 좋아진다.
* 청킹 로직이 결정적(deterministic)에 가깝기 때문에 테스트와 디버깅이 쉽다.
* 이후 유사도 기반 청킹이나 LLM 기반 청킹으로 진화하더라도 현재 데이터 모델과 파이프라인을 상당 부분 재사용할 수 있다.

## 6. 부정적 효과 및 위험 요소 (Negative Consequences)

* 의미 기반 청킹보다 주제 응집도가 떨어질 수 있다.
  * **대응 방안:** MVP 이후 검색 품질 측정에서 실제 병목이 확인되면 유사도 기반 청킹을 `chunking_version` 신규 버전으로 도입한다.
* STT의 문장 경계 품질이 낮으면 청크 품질도 영향을 받을 수 있다.
  * **대응 방안:** 문장 복원 규칙을 별도 유틸리티로 관리하고, 대표 도메인 샘플로 청킹 품질 회귀 테스트를 운영한다.
* overlap으로 인해 저장량과 검색 후보 중복이 일부 증가한다.
  * **대응 방안:** overlap을 1~2문장 또는 10~15% 범위로 제한하고, 검색 단계에서 RRF 및 SOT 게이트로 중복 노출을 억제한다.
* 고정 규칙 기반이므로 특정 도메인(예: 긴 강의, 화제 전환이 잦은 대화체)에서는 최적이 아닐 수 있다.
  * **대응 방안:** 도메인별 샘플 평가를 통해 필요 시 파라미터를 조정하거나 후속 ADR로 고도화 전략을 결정한다.

## 7. 결정 이후 후속 결과 (Consequences)
