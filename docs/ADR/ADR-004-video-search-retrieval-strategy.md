# [ADR-004] video-search-retrieval-strategy

* **상태 (Status):** Proposed
* **날짜 (Date):** 2026-03-07

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** Biblio는 영상 업로드 후 STT, 청킹, 임베딩, 검색, RAG 응답까지 이어지는 영상 기반 검색 서비스를 설계하고 있다.
* **문제:** 검색 입력은 우선 텍스트 질의를 기준으로 받되, 영상 내 시각 정보(키프레임)도 검색 품질에 반영하고 싶다. 이때 검색 정확도, 운영 복잡도, 디버깅 가능성 사이의 균형이 필요하다.
* **목표:** 텍스트 질의에 대해 정확한 검색 결과와 근거 응답을 우선적으로 제공하면서도, 시각 정보를 단계적으로 활용할 수 있는 검색 아키텍처를 선택한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 텍스트 중심 검색 + 시각 정보의 텍스트화

청크 텍스트에 키프레임 기반 `caption`, `OCR`, `scene tag`를 합쳐 하나의 검색용 텍스트 문서를 만들고, 이 문서를 텍스트 임베딩 및 FTS 검색 대상으로 사용한다.

**Pros**
* 현재의 `FTS + text embedding + RAG` 구조와 가장 자연스럽게 맞는다.
* 텍스트 질의 기준 정확도를 빠르게 확보하기 쉽다.
* 검색 실패 원인을 청킹, OCR, caption, top-k, 프롬프트 수준으로 분해해 분석하기 쉽다.
* `Managed Embedding Endpoint`를 텍스트 임베딩 전용으로 단순화할 수 있어 구현과 운영 부담이 낮다.
* 시각 정보가 검색 품질에 기여하더라도 최종 검색 문서는 여전히 사람이 읽고 검증 가능한 텍스트 형태다.

**Cons**
* 이미지 자체의 미세한 시각 특징은 손실될 수 있다.
* caption/OCR 품질이 낮으면 시각 정보 반영 효과도 낮아진다.
* 장면 이해가 매우 중요한 도메인에서는 한계가 있을 수 있다.

### 2. 텍스트 벡터 + 이미지 벡터 분리 저장 후 Late Fusion

청크 텍스트 임베딩과 키프레임 이미지 임베딩을 각각 저장하고, 검색 시 텍스트 질의로 두 인덱스를 조회한 뒤 점수를 결합한다.

**Pros**
* 텍스트와 시각 신호를 독립적으로 활용할 수 있어 확장성이 좋다.
* 이미지 정보가 실제로 검색 품질에 얼마나 기여하는지 분리 측정이 가능하다.
* 향후 이미지 질의나 멀티모달 reranking으로 확장하기 쉽다.

**Cons**
* 인덱스 2개와 fusion 로직을 함께 운영해야 해서 복잡도가 증가한다.
* 점수 결합 방식과 가중치 튜닝이 필요하다.
* 장애 지점과 성능 병목이 늘어나 운영과 디버깅이 어려워진다.
* 초기 단계에서 텍스트 질의 정확도 개선보다 시스템 복잡도 증가가 더 클 수 있다.

### 3. 청크 텍스트 + 키프레임의 단일 Fused Multimodal Vector

청크 텍스트와 대응 키프레임을 하나의 멀티모달 모델 입력으로 넣어 단일 벡터를 만들고, 이를 검색 인덱스로 사용한다.

**Pros**
* 이론상 텍스트와 이미지 정보를 한 번에 통합 표현할 수 있다.
* 저장 구조만 보면 단일 벡터 인덱스로 단순해 보일 수 있다.

**Cons**
* 적합한 멀티모달 임베딩 모델, 입력 포맷, 차원 관리, 서빙 프레임워크 선택이 어려워진다.
* 텍스트 질의만 들어오는 상황에서 검색 품질을 안정적으로 맞추기 어렵다.
* 어떤 결과가 왜 검색되었는지 설명 가능성이 가장 낮다.
* 키프레임 매핑 오류나 이미지 품질 문제가 전체 벡터 품질을 직접 흔든다.
* 현재 프로젝트 단계와 운영 역량 대비 리스크가 가장 크다.

## 3. 결정 사항 (Decision Outcome)

* **1번을 기본 검색 아키텍처로 선택한다.**
* **2번은 향후 확장 옵션으로 남긴다.**
* **3번은 현 단계에서 채택하지 않는다.**

**이유**
* 현재 최우선 목표는 "텍스트로 검색했을 때 정확한 정보를 응답하는 것"이며, 1번이 이 목표를 가장 단순하고 안정적으로 충족한다.
* 현재 시스템 설계는 `Search Service`가 텍스트 질의를 받아 하이브리드 검색과 RAG 응답을 수행하는 구조이므로, 대안 1이 기존 설계와의 정합성이 가장 높다.
* 대안 1을 선택하면 `Managed Embedding Endpoint`도 멀티모달 추론 서버가 아니라 텍스트 임베딩 전용 서버로 범위를 명확히 줄일 수 있다.
* 시각 정보 활용이 실제 품질 병목으로 확인되면, 이후 대안 2로 점진적으로 확장할 수 있다.

## 4. 결정된 설계 원칙 (Decision Details)

* 검색 입력은 우선 텍스트 질의를 기준으로 한다.
* Pipeline Worker는 청크별 대표 키프레임에서 `caption`, `OCR`, `scene tag`를 추출할 수 있다.
* 검색용 문서는 `chunk_text + visual_caption + ocr_text + scene_tags` 형태의 enriched text로 구성한다.
* FTS와 벡터 검색은 이 enriched text를 기준으로 수행한다.
* `Managed Embedding Endpoint`는 텍스트 임베딩 전용 컴포넌트로 정의한다.
* 이미지 전용 벡터 인덱스는 MVP 범위에 포함하지 않는다.

## 5. 긍정적 효과 (Positive Consequences)

* 검색 정확도 개선 작업을 청킹, OCR, caption, retrieval, prompt 단계로 분리해서 빠르게 반복할 수 있다.
* 서빙 아키텍처가 단순해져 임베딩 모델 선택과 운영 의사결정이 쉬워진다.
* 검색 결과의 근거를 텍스트 기반으로 보여주기 쉬워 RAG 응답 검증이 수월하다.
* 향후 대안 2로 확장하더라도 현재 데이터와 파이프라인을 상당 부분 재사용할 수 있다.

## 6. 부정적 효과 및 위험 요소 (Negative Consequences)

* 시각 정보가 핵심인 영상에서는 검색 품질이 부족할 수 있다.
  * **대응:** 실패 케이스를 수집해 시각 정보 누락이 반복적으로 확인되면 대안 2를 도입한다.
* caption/OCR 품질에 검색 성능이 영향을 받을 수 있다.
  * **대응:** OCR 및 caption 품질 평가 샘플셋을 별도로 운영하고, 검색 실패 분석에 포함한다.
* 이미지 자체 유사도 검색은 바로 지원하지 못한다.
  * **대응:** 이는 MVP 비범위로 두고, 필요 시 image vector index를 별도 추가한다.
