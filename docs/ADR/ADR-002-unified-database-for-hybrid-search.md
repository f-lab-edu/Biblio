# ADR-002-unified-database-for-hybrid-search

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-02-20

## 1. 배경 및 문제 상황 (Context and Problem Statement)
* **상황:** 현재 Biblio 프로젝트에서 영상 메타데이터, 텍스트 역색인, 임베딩 벡터를 저장하고 하이브리드 검색을 제공하는 데이터 저장소(Data & Storage Subsystem) 파이프라인을 설계하고 있다.
* **문제:** 사용자의 강제 삭제나 파이프라인 오류에 따른 선별적 재처리 시, 목적별로 여러 데이터베이스를 분리하여 사용하면 분산 트랜잭션 동기화 실패로 인한 유령 데이터(Orphaned Data)가 발생할 위험이 높다. 또한 제한된 인적 리소스 내에서 인프라 구성 및 파이프라인 로직의 복잡도를 최대한 낮춰야 한다.
* **목표:** 완벽한 데이터 무결성(ACID)을 보장하면서도 E2E 파이프라인 자동화 구현 목표를 안정적으로 달성할 수 있는 가장 효율적인 저장소 아키텍처를 결정해야 한다.

## 2. 고려한 대안들 (Considered Options)
* **대안 1:** 다중 저장소 분산 아키텍처 (Polyglot Persistence) - 메타데이터용 RDB, 키워드용 전문 검색 엔진, 시맨틱용 전용 벡터 데이터베이스를 각각 분리하여 운영한다.
* **대안 2:** 단일 통합 검색 아키텍처 (Converged Database) - 텍스트 역색인 및 벡터 탐색 확장을 지원하는 하나의 다목적 데이터베이스(Multi-model DB)에서 메타데이터와 검색 인덱스를 모두 처리한다.
* **대안 3:** 완전 관리형 검색 서비스 (BaaS) - 인프라 관리 없이 클라우드 제공자가 지원하는 완전 관리형 검색 엔진에 데이터 저장과 검색을 위임한다.

## 3. 결정 사항 (Decision Outcome)
* **우리는 대안 2 (단일 통합 검색 아키텍처)를 선택했다.**
* **이유:**
  * 가장 결정적인 이유는 단일 트랜잭션 내에서 메타데이터, 텍스트, 벡터 데이터를 동시에 삭제 및 갱신할 수 있어 **유령 데이터 발생을 원천 차단하고 완벽한 데이터 정합성 보장**이 가능하기 때문이다.
  * 초기 인프라 세팅 및 데이터 동기화(CDC, 메시지 큐 연동 등) 복잡도를 대폭 낮춰, 프로젝트의 핵심 목표인 'AI 피드백 루프 및 E2E 파이프라인 구축'에 리소스를 집중하는 것이 우리 상황에 적합하다고 판단했기 때문이다.

## 4. 긍정적 효과 (Positive Consequences)
* **데이터 정합성 확보:** 실패 및 삭제 연산 시 단일 트랜잭션 롤백 한 번으로 처리되어 파이프라인의 안정성이 극대화된다.
* **구현 및 운영 비용 감소:** 관리해야 할 인프라 포인트가 하나로 줄고, 애플리케이션 계층의 분산 트랜잭션 관리 코드가 불필요해져 개발 속도가 향상된다.
* **쿼리 단순화:** 사용자 권한 사전 필터링(비디오 ID)과 하이브리드 검색(텍스트 점수 + 벡터 점수 병합)을 한 번의 쿼리로 수행할 수 있다.

## 5. 부정적 효과 및 위험 요소 (Negative Consequences)
* **자원 경합(Resource Contention):** 무거운 벡터/텍스트 검색 연산이 몰릴 경우, 가벼운 데이터 삽입 및 상태 업데이트 작업의 처리 성능까지 병목을 유발할 수 있다.
  * -> **대응 방안:** 트래픽 증가 임계점 도달 시, CQRS 패턴을 적용하여 쓰기 전용(Master) 노드와 검색/읽기 전용(Read Replica) 노드로 물리적 인프라를 분리한다.
* **텍스트 검색 품질의 구조적 한계:** 전문 검색 엔진 대비 자국어 형태소 분석 및 동의어 처리 등의 정밀도가 다소 떨어질 수 있다.
  * -> **대응 방안:** N-gram 방식을 보조적으로 활용하여 키워드 누락을 방지하고, 검색 결과 병합(RRF) 시 시맨틱 검색(Vector)의 가중치를 높여 하이브리드 검색 품질을 보정한다.
* **확장성의 비효율(Scaling Asymmetry):** 특정 연산(예: 벡터 탐색)의 자원만 부족할 때도 데이터베이스 전체 시스템을 스케일업(Scale-up)해야 한다.
  * -> **대응 방안:** 애플리케이션 계층에 리포지토리(Repository) 패턴을 적용하여 결합도를 낮추고, 추후 데이터 규모 확장 시 트랜잭셔널 아웃박스(Transactional Outbox) 패턴을 통해 다중 저장소로 안전하게 마이그레이션 할 수 있는 구조적 여지를 남겨둔다.
