0단계 프롬프트 — 완성 기준 명세 (코드·설계 전)

  [기능명]의 "완성 기준"을 먼저 확정한다. 코드도 설계도 아직 작성하지 마라.

  ## 목적
  무엇이 "되면 끝"인지 기능 단위로 먼저 못박는다. 특히 이 기능이 데이터를
  만들거나 바꾸거나 지운다면, 그로 인해 함께 일어나야 하는 일까지 기준에 포함한다.
  (체크리스트가 아니라 열린 문장으로 쓴다 — 목록에 없는 것도 담기게.)

  ## 출력
  1. 완성 기준을 다음 문장 형태로 나열하라:
     WHEN [조건/사건] THE SYSTEM SHALL [일어나야 할 결과]
     - 구현 방법이 아니라 "관찰 가능한 결과"로 쓴다.
  2. 이 기능이 데이터를 생성/변경/삭제한다면, 스스로에게 묻고 답을 기준에 반영하라:
     - 이 데이터를 참조·의존하는 다른 것은? 그것들은 어떻게 되어야 하나?
     - 한 건이 아니라 여러 건을 동시에 다뤄야 하나?
     - 같은 사실을 두 곳 이상이 다루게 되나? 기준이 같아야 하나?
     판단이 도메인 결정이면 단정하지 말고 "내가 정해야 할 질문"으로 분리해 올려라.
  3. 정상 흐름만 기준으로 삼지 마라. 아래 세 유형을 각각 최소 1개 포함하거나,
     "해당 없음"을 근거와 함께 명시하라(억지로 만들지는 말되, 생각은 반드시 거친다):
     - 실패 경로: 이 작업이 실패하면 사용자에게 무엇이 관찰되나? 실패 흔적이
       화면·데이터에 잘못 남지는 않나?
     - 동시/중복/진행 중 조작: 같은 걸 두 번, 또는 진행 중에 사용자가 다른
       조작(삭제·재시도·새 입력)을 하면?
     - 생명주기: 작업이 진행되는 동안 화면 전환·새로고침·프로세스 재시작이
       일어나면 그 작업과 부수 효과는 어떻게 되나?

  ## 규칙
  - 내가 질문에 답하기 전에는 1단계로 넘어가지 마라.
  - 이 완성 기준은 1단계의 입력이 되고, 코드에 맞게 한 번 조정된 뒤
    최종적으로 설계 문서(2단계)의 "검증 기준" 섹션이 된다. 같은 실을 계속 들고 간다.
