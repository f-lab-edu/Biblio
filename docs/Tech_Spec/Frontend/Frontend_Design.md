## 1. 목적과 범위

GCP 배포 환경에서 실제 사용자가 가입하고, 자기 영상을 올리고, 검색까지 하는 웹 프론트엔드를 만든다. 데모 수준이 아니라 사람들이 직접 쓰고 테스트할 수 있는 수준을 목표로 한다.

레퍼런스는 Google NotebookLM이다. NotebookLM의 "소스 추가 → 처리 → 질문하면 답변 + 출처 인용" 흐름을 Biblio의 "영상 업로드 → 처리 → 검색하면 답변 + 타임스탬프 출처"로 대응시킨다.

## 2. 사용자 흐름

```
[로그인/가입]
   │ 로그인 성공(인증 토큰 획득)
   ▼
[프로젝트 목록] ──"새 프로젝트"──▶ 프로젝트 생성
   │ 프로젝트 선택
   ▼
[프로젝트 워크스페이스]
   ├─ 영상: 목록 + 처리 상태 + 업로드(파일 / URL)
   └─ 검색: 질의 → 답변 + 인용 출처
                       │ 출처 선택
                       ▼
              [영상 재생] 해당 시점으로 이동 재생
```

검색 범위는 프로젝트 단위다. 검색과 영상 소유는 인증된 사용자 단위로 격리된다. 그래서 가입/로그인이 흐름의 필수 선행 단계다.

## 3. 화면 목록

| 화면 | 책임 |
|------|------|
| 로그인 / 가입 | 이메일·비밀번호로 계정 생성·인증, 인증 토큰 획득 |
| 프로젝트 목록 | 내 프로젝트 조회, 새 프로젝트 생성 진입 |
| 프로젝트 워크스페이스 | 한 프로젝트 안의 영상 관리(목록·상태·업로드)와 검색을 함께 제공 |
| 검색(대화형) | 질의와 답변을 대화 스레드로 쌓아 보여주고, 각 답변에 인용 출처(영상·시점·자막 조각)를 붙인다. |
| 영상 재생 | 선택한 출처의 영상을 해당 시점부터 재생 |

검색 화면은 대화 스레드 형태로 보여 준다. 화면에는 질의·답변이 순서대로 쌓이지만, 각 검색은 서로 독립이다. 후속 질의가 앞선 대화 맥락을 이어받지는 않는다. 맥락을 이어받는 멀티턴 대화는 이후 과제로 둔다(8절).

업로드는 워크스페이스 안에서 처리한다. 입력 방식은 두 가지(로컬 파일 / 외부 URL)이며 한 화면에서 탭으로 나눈다.

## 3-1. 레이아웃 (확정)

레퍼런스 NotebookLM의 화면 구성을 따르되, 우리 기능에 없는 부가 생성 패널(오디오 개요·마인드맵 등 "스튜디오")은 두지 않는다.

- 프로젝트 목록: 카드 그리드. 첫 칸은 새 프로젝트 만들기 카드, 각 카드는 제목·수정일·영상 개수를 보여 준다.
- 프로젝트 워크스페이스: 좌우 2분할. 왼쪽은 영상 소스 패널(영상 목록·처리 상태·업로드), 오른쪽은 대화형 검색 패널.
- 영상 재생: 검색 답변의 출처를 선택하면 떠 있는(플로팅) 미니 플레이어로 해당 시점부터 재생한다. 배경을 가리는 차단막을 두지 않아, 재생 중에도 검색과 업로드를 계속 사용할 수 있다. 플레이어는 이동·닫기가 가능하다.

## 4. 백엔드 연동 현황

화면이 의존하는 백엔드 기능의 준비 상태다. 프론트는 이 경계에 맞춰 만든다.

| 기능 | 상태 | 비고 |
|------|------|------|
| 검색 | 준비됨 | 질의를 보내면 답변과 인용 출처 목록을 돌려준다. 인용 출처에는 영상·시작/끝 시점·자막 조각이 들어 있다. |
| 영상 목록·상태 조회 | 준비됨 | 처리 진행 상태(대기·업로드됨·처리중·완료·실패)를 조회할 수 있다. |
| 파일 업로드 | 준비됨 | 업로드용 임시 URL을 받아 사용자가 직접 올린 뒤, 완료를 알리면 처리가 시작된다. |
| URL 업로드 | 일부 준비됨 | 계약·저장·처리 시작 신호까지는 있으나, 워커가 외부 URL에서 영상을 실제로 내려받는 단계가 비어 있다. 백엔드 보완 필요. |
| 영상 재생 | 준비됨 | 재생용 임시 URL을 받아 플레이어에 물려 특정 시점부터 재생한다. |
| 가입 / 로그인 | 없음 | 인증 토큰을 검증하는 코드만 있고, 발급(가입·로그인) 기능이 없다. 백엔드 신규 필요. |
| 프로젝트 생성·목록 | 없음 | 프로젝트 개념은 있으나 사용자가 만들고 조회하는 기능이 없다. 백엔드 신규 필요. |

## 5. 채택한 빌드 방식

프론트엔드를 먼저 만들고, 아직 없는 백엔드 기능은 가짜 응답(Mock)으로 대체한다.

- 외부 호출을 한 곳(`src/api/`)으로 모은다. 화면은 이 계층만 바라보고, 실제냐 가짜냐를 모른다.
- 준비된 기능(검색·영상·재생)은 실제 백엔드를 호출한다. 인증이 필요한 호출은 임시 토큰으로 진행한다.
- 없는 기능(가입·로그인·프로젝트)은 가짜 응답으로 채운다. 가짜 응답의 모양은 실제 백엔드가 쓰는 데이터 형식에 맞춘다.
- 백엔드 기능이 나오면 해당 호출부만 실제 주소로 교체한다. 화면은 건드리지 않는다.

이 방식은 백엔드를 기다리지 않고 화면과 흐름을 끝까지 만들 수 있게 한다. 가짜 응답 모양을 실제 형식에 맞춰 두는 것이 교체 비용을 줄이는 핵심이다.

## 6. 기술 선택

- 프레임워크: Next.js (App Router)
- 선택 이유: 폴더 구조가 곧 화면 주소가 되어 라우팅이 단순하고, 가짜 API를 앱 안의 서버 경로(route handler)에 둘 수 있다. 백엔드가 나오면 그 경로만 실제 호출로 바꾸면 되어 5절의 빌드 방식과 잘 맞는다. 단일 컨테이너로 배포하기에도 적합하다.

## 7. 인증과 보안 제약

인증은 이메일·비밀번호 방식이다. 단순함을 택하되 보안은 허술하지 않게 한다. 다음은 백엔드 발급 기능을 만들 때 지킬 제약이다.

- 비밀번호는 평문으로 저장하지 않는다. 단방향 해시(bcrypt 또는 argon2 계열)로 저장한다.
- 인증 토큰은 서명해 발급하고, 배포 환경은 HTTPS로 제공한다.

## 8. 다음 단계

이 문서로 화면·흐름·레이아웃·빌드 방식·기술 선택을 확정했다. 이후 순서:

1. 구현 계획 수립 — 화면 단위 작업 순서와 Mock 계층 구성을 정리한다.
2. 백엔드 보완(별도 작업) — 가입/로그인 발급, 프로젝트 생성·목록, URL 업로드의 외부 다운로드 단계.
3. 멀티턴 대화(후속 과제) — 검색이 이전 대화 맥락을 이어받도록 검색 API를 확장하고, 대화 내역 저장을 더한다. 현재는 매 검색이 독립이다.
