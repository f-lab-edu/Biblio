## 1. 목적

**지금 구조가 어디서, 어떻게 무너지는지 찾는다.**

상정한 수준의 환경에서 확인하는 테스트에서, 스트레스 테스트로 병목 지점을 찾는 쪽으로 초점을 옮겼다.

### 실행 전 사전 분석

실행 전에 구조를 이해하고 실측과 비교할 기준을 만든다.

| 산출물 | 확인할 내용 |
|---|---|
| Deployment Diagram | 요청 경로, 인스턴스 역할·대수·동시 처리 상한, 공유 자원 |
| 검색·색인 Value Stream Map | 단계별 처리 시간과 대기 시간, 아직 실측하지 못한 구간 |
| 병목 가설표 | 예상 지점, 근거, 실패 형태, 확인 지표, 대응 후보 |

가설과 다른 결과도 산출물이다. 실행 기록의 `예상과 달랐던 것`은 이 표를 기준으로 작성한다.

## 2. 사용자 수를 상정하지 않는다

결과는 **절대 수치와 그때의 구성**으로 보고한다.

```
"코퍼스 1만 청크 / 검색 임베딩 VM 1대(동시 처리 1) / Cloud Run 3대 /
 DB 커넥션 풀 기본값 구성에서, 동시 검색 N건부터 DB 커넥션이 동난다"
```

MAU·DAU를 정해 역산해봤으나, 현실적인 규모에서는 동시 요청이 스트레스 테스트라 할만큼 크게 발생하지 않음. 충분히 부하를 줄만큼 만들려면 가정을 부풀려야 해서 그 방식을 기각함

## 3. 무엇을 재고 무엇을 빼는가

| 구분 | 대상 | 판정 | 이유 |
|---|---|---|---|
| 통제 가능한 것 | 임베딩 VM, PostgreSQL, Cloud Run, 검색 코드 | 포함 | 설정·설계를 바꿀 수 있다 |
| 외부 | Gemini(LLM), STT, Vision | 제외 | 성능 통제 불가 + 대량 호출 비용 |

```
판정 구간 = query embedding + FTS + vector search + SOT gate
```

#103 실측에서 검색 응답 시간의 **96.9%가 LLM**이었다(평균 16.4초). 전체 시간을 지표로 삼으면 어떤 개선도 Gemini 변동에 묻힌다. 단계별 시간은 `search.execute.timing` 로그로 이미 수집된다.

**mock 방침**

- 검색 부하 — LLM만 mock, 임베딩·DB는 실제
- 필요 시 임베딩도 mock — DB만 따로 재기 위해
- 검증용으로 실제 Gemini를 소량 실행해 mock과 현실의 차이를 확인

## 4. 부하를 세 가지로 나눠 건다

검색과 영상 색인은 쓰는 자원이 다르다. #103에서 임베딩 VM을 분리해 추론 경합은 사라졌으나 **PostgreSQL은 여전히 한 대를 공유한다.**

| 부하 | 드러나는 것 |
|---|---|
| 검색만 | 검색 쪽 순수 한계 |
| 색인만 | 색인 쪽 순수 한계 |
| 둘 다 | 서로 방해하는 정도 |

```
서로 방해해서 잃는 양 = (검색만 한계 + 색인만 한계) − 둘 다 돌렸을 때 한계
```

따로만 재면 안 나오는 값이다.

## 5. 색인 부하는 fixture로 만든다

색인을 실제 영상으로 돌리면 매번 STT·Vision 비용이 붙는다. 둘은 측정 대상에서 뺀 구간이라, **한 번만 실제로 돌려 결과를 저장하고 그 뒤로는 저장본을 쓴다.**

```
처음 한 번:  실제 영상 → 다운로드 → GoogleSTT → GeminiVision → [저장]
                                                                 ↓
그 뒤로는:    (건너뜀)     FixtureSTT ──── FixtureVision ←──── [읽기]
                                ↓
                            청킹 → 임베딩 → DB    ← 이 구간만 측정
```

- 저장 지점은 **Vision 직후·청킹 직전.** 청킹은 코드라 매번 실제로 돌릴 때 설정을 바꿔가며 잴 수 있다
- fixture 어댑터는 지연 없이 바로 반환한다. 대신 Pipeline 전체 시간은 운영 실측값과 다른 값이 된다

**필요한 작업**

| 대상 | 지금 | 할 일 |
|---|---|---|
| Vision | `VisionAdapter`가 Protocol | `FixtureVisionAdapter` 작성 |
| STT | 구현체를 직접 받아 꽂을 자리가 없음 | Protocol 추출 후 `FixtureSTTAdapter` 작성 |
| 선택 | — | 환경변수로 실제/fixture 교체 |

**코퍼스 규모** — 전체 코퍼스를 실제 영상이나 자막 추출로는 못 채운다. 테스트용 영상셋을 구성해 한번 파이프라인을 돌린뒤 결과물을 참고해 공개 한국어 말뭉치와 생성 스크립트로 만든다.

| 코퍼스 | 필요 글자 수 |
|---:|---|
| 1천 청크 | 약 120만 자 |
| 1만 청크 | 약 1,200만 자 |
| 5만 청크 | 약 5,900만 자 |

## 6. 절차

```
0. Deployment Diagram·Value Stream Map·병목 가설표를 작성한다
1. 현재 구성 그대로 전체 경로에 부하를 올린다 → 깨질 때까지
2. 처음 막힌 지점과 실패 방식을 기록한다
3. 뒤쪽 확인이 필요하면 같은 배포환경의 해당 컴포넌트에 직접 부하를 준다
4. 확인한 병목 중 하나의 개선안을 적용한다
5. 같은 조건에서 전체 경로를 다시 측정한다

멈추는 때: 개선 1건을 같은 조건에서 검증했거나,
          확인한 병목이 읽기 복제본·샤딩처럼 범위 밖 작업을 요구할 때
```

특정 지점까지 부하를 보내려고 앞단 인스턴스 수나 동시성을 임의로 늘리지 않는다. 그렇게 해야 뒤로 부하가 간다면 그 사실 자체를 현재 구조의 결과로 기록한다.

뒤쪽 컴포넌트의 한계가 필요하면 배포환경의 해당 인스턴스에 직접 부하를 준다. 직접 진입하기 어려우면 앞단을 mock한다. 이 결과는 전체 시스템 처리량이 아닌 개별 컴포넌트의 한계로 구분해 보고한다.

**어느 설정을 개선할지는 미리 정하지 않는다.** 실제로 막힌 지점을 보고 운영 가능한 후보를 선택한 뒤 같은 조건에서 전후를 비교한다.

**지금 조정 가능한 설정** — 측정해서 정한 값은 하나도 없다.

| 구분 | 설정 | 현재 |
|---|---|---:|
| 임베딩 VM | 동시 처리 수 | 1 |
| 〃 | 검색 / 색인 요청 상한 | 32 / 4 |
| 〃 | 검색 / 색인 대기 상한 | 5초 / 20초 |
| 〃 | VM 크기·대수 | e2-standard-4, 검색 1 + 배치 1 |
| Cloud Run | 검색 서버 최대 대수 | 3 |
| 〃 | 색인 워커 최대 대수 · 프로세스 동시성 | 1 · 4 |
| 애플리케이션 | DB 커넥션 풀 | 5+10, 대기 30초 (설정한 적 없음) |
| 〃 | 청크 최대 어절 수 · 임베딩 배치 크기 | 300 · 16 |

임베딩 VM 값은 **검색용과 배치용이 같은 변수를 공유해서 한쪽만 따로 바꿀 수 없다.**

이 값들은 뒤쪽으로 부하를 보내기 위한 우회 수단이 아니라, 실제 병목으로 확인한 뒤 검토할 개선 후보다.

**규칙**

1. 전체 경로 테스트와 개별 컴포넌트 테스트를 구분한다
2. 부하 전파를 위해 앞단 설정을 임의로 늘리지 않는다
3. 개선 검증에서는 한 번에 설정 하나만 바꾼다
4. 매번 테스트 진입점·제외한 앞단·부하량·막힌 지점·실패 방식·회복 여부를 기록한다

## 7. 개선과 검증

찾은 병목 중 **하나만** 골라 고친다. 후보는 설정값, 인덱스, 코드, 자원 추가.

인프라 설정을 바꾸는 것도 해결책으로 인정하되 근거를 붙인다 — 왜 그 숫자인지, 어디부터 더 늘려도 안 좋아지는지, 대안 대비 왜 이건지.

**검증**

- 전후를 같은 조건에서 잰다 (코퍼스, 질의 목록, 부하 종류, mock 여부 동일)
- 고친 설정이 지속 부하에서도 유지되는지 1회 확인
- 비용이 늘면 얼마인지 기록
- 3회 반복해 중앙값과 범위를 쓴다. 여러 번을 합쳐 하나의 표본으로 만들지 않는다

## 8. 제약

| 항목 | 내용 |
|---|---|
| 예산 | GCP 잔여 약 25만원. 세션당 $3~10이라 20~50회 가능. 만료 2026년 9월 중순 |
| 부하 생성 위치 | k6를 같은 리전 GCP VM에서 실행 (노트북에서 쏘면 집 회선이 먼저 한계) |
| DB 보존 | PostgreSQL VM은 `stop`만. `destroy`하면 코퍼스가 사라짐 |
| 측정 조건 | 검색 서버 min=1 고정, cold start는 따로 기록 |
| 로컬 도커 | 장애 주입 등 GCP에서 하기 어려운 것만 보조로. **로컬 절대 수치는 보고서에 쓰지 않는다** |

**범위 밖**

- 용량 산정 — "MAU N명까지 감당" 형태의 결론은 내지 않는다
- Gemini 답변 품질 개선 — 유효한 작업이나 측정 방법이 달라 별도 이슈
- 다중 리전, 읽기 복제본, 샤딩
- 장시간 지속 부하

## 9. 산출물

1. 사전 분석 자료 — Deployment Diagram, 검색·색인 Value Stream Map, 병목 가설표
2. 매번의 측정 기록 — 전체 경로와 개별 컴포넌트를 구분한 병목 목록
3. 개선 1건의 전후 수치 — 같은 조건, 3회 반복
4. 서로 방해해서 잃는 양 — 따로 돌렸을 때와 같이 돌렸을 때의 차이
5. 이력서 문장 — "청크 M건·{구성} 환경에서 동시 검색 N건부터 {병목} 발생을 특정하고 {해결}로 개선". 구성 병기 필수
