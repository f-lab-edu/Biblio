# 임베딩 VM 분리 후 검색 503 재실험 계획 (#103 마지막 항목)

작성일: 2026-07-28
대상 브랜치: `feat/103-search-observability-embedding-isolation`
근거 자료: `2026-7-20-임베딩 경합 실험 원자료.md`, `2026-7-16-임베딩 run slot 경합 문제.md`

## 1. 목적

7월 20일과 **같은 조건**으로 영상 업로드와 검색을 겹쳐서, 검색 VM과 배치 VM을 분리한 뒤
영상 임베딩 중 검색 503이 사라졌는지 확인한다. 이 실험이 #103의 마지막 체크박스다.

## 2. 판정 기준

| 항목 | 7/20 기준선 (분리 전) | 이번 목표 |
|---|---|---|
| 영상 임베딩 중 검색 503 | 8건 중 1건 (index 7) | **0건** |
| 검색 성공 응답 평균 (클라이언트 측정) | 3.907초 | 기록만 (악화 시 원인 기재) |
| 영상 Pipeline total | 133.066초 | **146.372초 이하** (회귀 10% 이내) |
| 검색 query embedding inference | 0.414~0.443초 | 기록만 |
| video batch inference | 약 20.0초 | 기록만 |

기준선은 7/20 **실험 3**의 사용자 B 영상(`60be77bc-...`) 수치다.
이슈 본문의 `503 9/20 · 평균 11.626초 · Pipeline 165.142초`는 임시 `CHUNK_MAX_TOKENS=150`
스트레스 실험이므로 비교 대상이 아니다.

## 3. 실험 유효 조건 (이게 없으면 결과 무효)

분리 후에는 검색이 영상과 안 겹쳐도 당연히 성공한다. 따라서 아래 두 가지를 로그로
증명하지 못하면 "503이 사라졌다"고 판정하지 않는다.

1. 검색 8건 중 **최소 1건이 배치 VM의 `video_preprocess` inference 구간(약 20초) 안에 도착**했다.
   - 배치 VM `embedding.admission` 로그의 success 기록 시각에서 `inference_duration_ms`를 빼서 시작 시각을 역산하고,
     검색 VM `embedding.admission`의 `lane=search` 시각과 겹치는지 대조한다.
2. 같은 시간대에 **배치 VM에는 `lane=search` 로그가 0건**, **검색 VM에는 `lane=video_preprocess` 로그가 0건**이다.

1번이 성립하지 않으면 검색 시작 delay만 조정해 재실행한다 (아래 5-3).

## 4. 사전 조건

### 4-1. VM 기동과 모델 준비 확인

```bash
gcloud compute instances start biblio-perf-ed2d3cb0-postgres \
  biblio-perf-ed2d3cb0-embedding biblio-perf-ed2d3cb0-embedding-search \
  --zone=asia-northeast3-a
```

- PostgreSQL: `systemctl is-active postgresql` → `active`
- 배치 VM `10.20.3.14:8000/health`, 검색 VM `10.20.3.15:8000/health`
  → 두 곳 모두 `ready_model_versions`에 현재 active 버전(`bge-m3-base`) 포함

### 4-2. 배포 설정 확인 (변경하지 말고 값만 확인)

| 대상 | 확인할 값 |
|---|---|
| search-service | `EMBEDDING_API_URL` = `http://10.20.3.15:8000` |
| pipeline-worker | `EMBEDDING_API_URL` = `http://10.20.3.14:8000` |
| pipeline-worker | `CHUNK_MAX_TOKENS=300`, `EMBEDDING_BATCH_SIZE=4`, `EMBEDDING_TIMEOUT_SEC=180` |
| search-service | `EMBEDDING_TIMEOUT_SEC=15` |
| 두 임베딩 VM | `MAX_CONCURRENCY=1`, search wait 5초, video wait 20초 |

값이 다르면 실험을 멈추고 보고한다. 7/20과 조건이 달라지면 비교가 성립하지 않는다.

### 4-3. pipeline-worker 인스턴스 기동

`min_instance_count=0`이라 PGMQ 메시지만으로는 워커가 깨어나지 않는다.
Terraform이 아니라 gcloud로만 올린다 (평소 0이 정상 운용값이다).

```bash
for svc in pipeline-worker; do
    gcloud run services update "$svc" --region asia-northeast3 --min 1
  done

```
--min instance 1로 올리면 리비전이 생성되어버림 꼭 코드블럭에 있는 명령어로 올리셈
실험이 끝나면 반드시 0으로 되돌린다.

## 5. 실행 절차

### 5-1. 사용자·프로젝트 (7/20과 동일)

| 역할 | 값 |
|---|---|
| 업로드 사용자 | `a74590a0-9b78-43be-9634-b957d3e87628` |
| 업로드 프로젝트 | `aa76f74d-8f44-4a98-9fbd-b63c4daf4713` |
| 검색 사용자 | `72949036-7a3b-43d9-b164-6ba8a376bdce` |
| 검색용 READY 프로젝트 | `b679b349-3e89-4836-bc2c-5e7fe6d2ab66` |
| 영상 URL | `https://www.youtube.com/watch?v=XYSVIxGQwmE` |

검색을 업로드 프로젝트에서 하면 안 된다. Search는 프로젝트에 non-READY 영상이 하나라도
있으면 임베딩 호출 전에 409를 반환하므로 슬롯 경합 자체를 만들 수 없다.
실행 전에 검색용 프로젝트의 모든 영상이 READY인지 DB로 확인한다.

### 5-2. 호출 방식

- Frontend proxy 경유. Core API와 Search Service는 ingress/IAM 때문에 외부 직접 호출이 막혀 있다.
  - 영상 생성: `POST /api/v1/projects/{project_id}/videos` (`input_type=EXTERNAL_URL`, 성공 코드 **202**)
  - 검색: `POST /api/v1/search`
  - 다운로드 실패 시 재시도: `POST /api/v1/videos/{video_id}/retry`
- JWT는 Secret Manager `biblio-perf-ed2d3cb0-jwt-secret-key`에서 실행 중 메모리로만 읽고
  파일·로그·응답에 출력하지 않는다. `scripts/e2e/lib/http.py::make_jwt`를 재사용한다.
- 자동화 스크립트는 `/tmp`에 만들고 저장소에 남기지 않는다. 실험 후 삭제한다.

### 5-3. 타이밍

- 영상 **1개**만 업로드한다. 기준선 133.066초가 단독 영상 수치이므로 동일하게 맞춘다.
- 영상 생성 요청 직후 `search_schedule_started` marker 시각을 남기고, **90초 뒤부터
  2초 간격으로 검색 8건**을 스레드로 투입한다. 검색 문구는 `플랙 아머의 특징을 설명해줘 {index}`, index 0~7.
- 참고 타임라인 (7/20 실측): download 12.9초 → audio 2.3초 → STT 90.6초 → enrichment 6.9초 →
  **embedding 시작 T+114초 부근, 약 20초 지속**.
- 실행 후 3장의 유효 조건 1번이 성립하지 않으면 delay만 100~110초로 올려 재실행한다.
  다른 설정은 건드리지 않는다.

### 5-4. YouTube 다운로드 실패 대비

7/20에는 `Sign in to confirm you're not a bot`으로 영상 하나가 8초 만에 실패했다.
`FAILED/DOWNLOAD`가 나오면 retry API로 재시도하고, 재시도분을 본 실험 표본으로 쓴다.
배치 VM의 WARP 프록시(`YOUTUBE_PROXY_URL`) 경로는 그대로 유지한다.

## 8. 이번 범위 밖

- **동시 검색 5건 이상의 503**: 검색 VM도 슬롯 1개라 5초 대기 상한을 넘길 수 있다.
  VM별 슬롯 수·머신 타입 조정은 후속 이슈다.
- `/health`가 active 버전 기준이 아닌 문제 (아무 모델 하나만 ready여도 200).
- 영상 3개 이상, video admitted limit 4 초과, search limit 32 초과.
