# 영상 파이프라인 작업 단위 리팩토링 설계

- 작성일: 2026-08-17
- 대상: `services/pipeline-worker`, `services/core-api`, Queue·DB 배포 설정
- 상태: 구조와 첫 버전 범위 확정, 구현 전에 필요한 미결정 항목은 11절에 분리

## 1. 목적

현재 영상 하나가 `PREPROCESS_REQUEST` 하나로 다운로드부터 벡터 저장까지 Worker 슬롯 하나를 계속 점유한다. 이를 단계별 작업으로 나눠 다음 문제를 없앤다.

- 긴 영상이 Worker 슬롯을 오래 점유해 짧은 영상까지 기다리게 하는 문제
- 긴 영상이 더 많은 part·chunk를 만들어 FIFO 앞부분을 차지하는 문제
- 원본 영상과 중간 파일을 로컬 `/tmp`에 함께 보관하는 문제
- STT·Vision·embedding 일부만 실패해도 영상 전체를 다시 처리하는 문제
- 먼저 완성된 검색 청크가 무거운 후속 작업을 불필요하게 기다리는 문제

S4에서는 long 작업이 Worker 슬롯 4개를 선점한 뒤 10초 늦게 들어온 short 작업이 평균 약 395초 Queue에서 기다렸다. short 작업 자체의 평균 처리시간은 약 39초였다. 첫 버전의 우선 목표는 자원을 늘리는 것이 아니라 작업 단위 분리와 영상별 순환 배정으로 이 대기를 줄이는 것이다.

## 2. 첫 버전에서 바꾸지 않는 것

- `pipeline-worker` 인스턴스는 현재처럼 1대를 사용한다.
- STT 전용 서비스·이미지·인스턴스를 만들지 않는다.
- STT audio part는 `15분 + 5초 overlap`을 유지한다.
- STT part 동시성은 현재 값 2를 유지한다.
- 검색 청크는 현재의 공백 기준 최대 300개와 문장 1개 overlap 규칙을 유지한다.
- embedding batch size와 embedding VM 설정을 바꾸지 않는다.
- proxy video segment와 별도 디스크 볼륨을 도입하지 않는다.
- 영상이 완전히 끝나기 전 생성된 청크를 검색 결과에 노출하지 않는다.

15분을 유지하는 이유는 병합 코드가 다른 길이를 지원하지 않아서가 아니다. 첫 비교에서 작업 단위 분리 외의 변수를 늘리지 않기 위해서다.

## 3. 현재 구조

현재 `PipelineOrchestrator.run`이 한 요청 안에서 모든 단계를 실행한다.

```text
PREPROCESS_REQUEST
  → 원본 전체 다운로드
  → 전체 audio 추출
  → 필요하면 15분 audio part 생성
  → 모든 STT 결과 병합
  → 전체 transcript 청킹
  → 청크마다 원본에서 keyframe 추출
  → Vision
  → 영상 안에서 embedding batch 순차 실행
  → chunk·vector 일괄 저장
  → video READY
```

현재 코드 계약은 다음과 같다.

- GCS 원본을 로컬 `source.bin`에 전부 내려받는다.
- 긴 STT는 part를 2개씩 `gather`하고 두 결과가 모두 끝나야 다음 2개를 시작한다.
- overlap 단어는 두 part가 겹치는 구간의 중앙을 기준으로 한쪽 part에 귀속한다.
- 최종 transcript는 DB `transcript_segment`에 저장한다.
- 검색 청크의 `CHUNK_MAX_TOKENS=300`은 tokenizer token이 아니라 공백으로 나눈 단어 수다.
- Vision은 청크마다 전체 원본을 다시 탐색해 중간 시점의 JPEG 한 장을 만든다.
- embedding batch는 한 영상 안에서 앞 batch가 끝난 뒤 다음 batch를 요청한다.

## 4. 목표 구조

물리 Queue는 네 개로 나눈다.

```text
NORMALIZE_VIDEO
  → TRANSCRIBE_PART × N
  → 시간순 문장·검색 청크 조립
  → ENRICH_CHUNK × M
  → EMBED_BATCH
  → 완료 조건 확인
  → video READY
```

별도 `FINALIZE` Queue는 만들지 않는다. 마지막 vector 저장 작업이 완료 조건을 확인하고 READY를 갱신한다.

각 Queue는 같은 `pipeline-worker` 1대 안의 독립 consumer loop가 소비한다. 각 loop는 자신의 빈 슬롯이 있는 동안만 새 메시지를 읽고, 실행 중인 handler가 있어도 다른 Queue loop는 계속 동작한다. 현재 모든 Queue를 함께 제한하는 `WORKER_CONCURRENCY` 대신 stage별 실행 상한을 사용한다. STT·Vision·embedding의 외부 응답을 기다리는 동안 다른 Queue 소비를 중단하지 않는다. `NORMALIZE_VIDEO`와 `TRANSCRIBE_PART`의 첫 실행 상한은 각각 2다. 나머지 Queue의 실행 상한은 11절에서 결정한다.

### 4.1 데이터 흐름 배정

물리 Queue를 나누는 것만으로는 영상 간 공정성을 보장할 수 없다. 1시간 영상 A의 part 4개가 5분 영상 B의 part 1개보다 먼저 FIFO에 들어가면 STT 동시성 2에서도 `A0·A1 → A2·A3 → B0` 순서가 될 수 있다. 청크 수가 많은 `ENRICH_CHUNK`와 `EMBED_BATCH`에서도 같은 문제가 생긴다.

이를 막기 위해 part와 chunk를 모두 PGMQ에 미리 넣지 않는다.

```text
DB stage 작업 상태
  READY       실행 가능하지만 아직 Queue에 넣지 않음
  DISPATCHED  공정 배정기가 선택해 Queue에 넣음
  RUNNING     consumer가 실행 중
  COMPLETED   결과 저장 완료
  FAILED      재시도 한도를 넘긴 최종 실패
```

각 stage의 공정 배정기는 `Queue 대기 + 실행 중` 작업 수가 해당 stage 실행 상한을 넘지 않게 유지한다. 빈자리가 생길 때 다음 순서로 작업을 고른다.

1. `READY` 작업이 있는 영상 중 해당 stage에서 가장 오래 선택되지 않은 영상을 고른다. 시각이 같으면 가장 오래된 `READY` 작업, 그다음 `video_id` 순서로 고른다.
2. 선택한 영상에서 가장 오래된 작업 하나를 고른다.
3. 다른 영상에도 `READY` 작업이 있으면 그 영상을 먼저 한 번씩 고른다.
 4. 모든 대기 영상이 한 번씩 선택된 뒤에도 빈 슬롯이 있으면 같은 영상을 다시 선택한다.
5. 선택과 `DISPATCHED` 변경, PGMQ 발행은 7절의 원자성 계약으로 묶는다.

consumer는 message id가 일치하고 작업이 `DISPATCHED` 또는 `RUNNING`일 때만 실행한다. `DISPATCHED`는 `RUNNING`으로 바꾸고, process 종료 뒤 다시 보이는 `RUNNING` 메시지는 같은 작업의 재시도로 인정한다. handler가 끝나면 한 DB transaction에서 결과와 `COMPLETED`를 저장하고 배정기를 실행해 빈 슬롯을 채운다. commit이 끝난 뒤 현재 메시지를 ack한다. commit 후 ack 전에 종료돼 현재 메시지가 다시 보여도 완료 결과를 확인해 외부 작업을 반복하지 않는다.

예를 들어 STT 슬롯이 2개라면 A와 B가 함께 대기할 때는 각 영상에서 part 하나씩 실행한다. A만 대기하면 A의 part 두 개를 실행한다. A가 두 슬롯을 이미 사용 중일 때 B가 도착하면 실행 중인 작업을 중단하지는 않지만, 먼저 끝난 슬롯의 다음 작업은 B에 배정한다.

정상 작업 기준으로 새 영상 B는 이미 실행 중인 작업이 끝날 때까지만 기다린다. 아직 PGMQ에 발행하지 않은 A의 나머지 part·chunk 뒤로 밀리지 않는다. retry로 실행 슬롯이 장시간 유지되는 경우는 8절의 별도 실패 경로로 측정한다.

이 정책은 `TRANSCRIBE_PART`와 `ENRICH_CHUNK`에 적용한다. `EMBED_BATCH`는 같은 model version과 index 조건 안에서 영상별 chunk를 한 개씩 순환해 batch를 채운다. 시간순 청크 조립은 같은 영상 안의 순서를 다루는 짧은 DB 작업이므로 이 배정 대상에서 제외한다.

`NORMALIZE_VIDEO`는 영상당 ffmpeg 작업 하나라 실행 중간에 다른 영상으로 교체하지 않는다. 최대 두 개의 ffmpeg 자식 프로세스를 동시에 실행한다. 두 슬롯이 모두 실행 중이면 새 영상은 하나가 끝날 때까지 기다린다. normalization 자체의 선점과 재개는 첫 버전 범위가 아니다.

## 5. 단계별 설계

### 5.1 `NORMALIZE_VIDEO`

입력은 원본이 GCS에 저장된 영상 한 건이다.

GCS 원본을 순차적으로 읽으면서 ffmpeg가 다음 산출물을 만든다.

```text
GCS 원본
  → STT용 FLAC audio part
  → Vision 후보 JPEG
```

audio part 계약은 현재와 같다.

```text
part 0: 00:00 ~ 15:00
part 1: 14:55 ~ 30:00
part 2: 29:55 ~ 45:00
```

닫힌 audio part는 즉시 GCS에 업로드하고 DB에서 `READY`로 바꾼 뒤 STT 공정 배정기를 호출한다. 배정기는 빈 STT 슬롯이 있을 때만 `TRANSCRIBE_PART`를 발행한다. 업로드가 끝난 로컬 part는 삭제한다. 모든 part가 끝날 때까지 전체 audio 파일을 로컬에 보관하지 않는다.

후보 JPEG도 생성되는 대로 GCS에 업로드하고 로컬 파일을 삭제한다. timestamp와 GCS 경로는 전체 normalization이 끝나기 전에도 앞 구간에서 조회할 수 있도록 영속 저장한다. metadata의 저장 형식과 위치는 11절에서 결정한다. proxy video segment는 만들지 않는다.

`EXTERNAL_URL` 입력은 현재처럼 원본을 먼저 GCS에 저장한 뒤 같은 `NORMALIZE_VIDEO` 경로로 진입한다. 외부 URL 다운로드 과정의 전체 로컬 파일 제거는 첫 버전 범위가 아니다.

audio part가 닫힐 때마다 DB에 part 상태와 GCS 경로를 기록한다. 후보 JPEG가 준비된 시간 범위도 지속해서 기록한다. 전체 정규화 완료 시 예상 audio part 수를 확정한다.

`NORMALIZE_VIDEO` 실행 상한은 2다. 현재 Worker는 `asyncio.to_thread()`에서 `subprocess.run()`으로 ffmpeg 자식 프로세스를 실행한다. Worker 프로세스를 복제하지 않고 자식 프로세스를 최대 두 개 실행한다. ffmpeg 하나도 내부 thread를 여러 개 사용할 수 있으므로 CPU·메모리 검증 결과에 따라 상한 또는 ffmpeg thread 수를 조정한다.

### 5.2 `TRANSCRIBE_PART`

메시지 하나는 audio part 하나만 처리한다.

```text
video_id
pipeline_run_id
part_index
start_ms
end_ms
audio_storage_path
stt_model_version
trace_id
```

처리 순서는 다음과 같다.

1. 동일한 part와 model version의 완료 결과가 있으면 STT를 다시 호출하지 않는다.
2. GCS의 FLAC part를 Google BatchRecognize에 전달한다.
3. 단어, 구두점, 단어별 상대 timestamp를 보존한다.
4. part 결과를 영속 저장한 뒤 STT 상태를 `COMPLETED`로 바꾼다.
5. 해당 영상에서 앞에서부터 연속으로 완료된 part가 있으면 5.3의 조립 상태를 전진시킨다.
6. 앞 part가 없으면 결과만 저장하고 작업을 끝낸다. Worker가 앞 part를 기다리지 않는다.
7. STT 실행 슬롯을 반환하고 공정 배정기를 호출해 다음 영상을 우선 선택한다.

STT 작업은 전역 상한 2 안에서 part별로 병렬 실행한다. 검색 청크 조립 순서 때문에 STT 실행 자체를 순차화하지 않는다. 같은 영상만 대기 중이면 두 슬롯을 모두 사용할 수 있고, 여러 영상이 대기하면 영상별 한 part를 먼저 배정한다.

### 5.3 시간순 transcript·검색 청크 조립

영상별로 다음 상태를 둔다.

```text
next_part_index
pending_words
chunk_buffer
next_chunk_index
```

- `next_part_index`: 다음으로 반영해야 할 part 번호
- `pending_words`: 아직 구두점이나 강제 상한으로 닫히지 않은 단어와 timestamp
- `chunk_buffer`: 최대 300개에 도달하지 않은 완성 문장과 timestamp
- `next_chunk_index`: 다음 검색 청크 번호

조립기는 같은 영상에 대해 한 번에 하나만 실행한다. 영상별 DB 잠금 또는 동등한 충돌 방지 장치로 중복 chunk 생성을 막는다.

처리 규칙은 다음과 같다.

1. `next_part_index`의 STT 상태가 `COMPLETED`가 아니면 즉시 끝낸다.
2. part의 상대 timestamp를 영상 전체 timestamp로 바꾼다.
3. 5초 overlap의 중앙을 ownership 경계로 사용해 중복 단어를 제거한다.
4. `pending_words` 뒤에 현재 part의 소유 단어를 붙인다.
5. 구두점으로 끝난 문장을 `chunk_buffer`에 넣는다.
6. 구두점이 없어도 현재 코드와 같이 100단어에 도달하면 문장을 강제로 닫는다.
7. 다음 문장을 넣었을 때 공백 기준 300개를 넘으면 현재 buffer를 검색 청크로 확정한다.
8. 기존 규칙대로 마지막 문장 1개를 다음 청크에 overlap한다.
9. 확정한 청크를 DB에 저장한다. 해당 시간 범위의 후보 JPEG까지 준비됐으면 enrichment 상태를 `READY`로 바꾸고 공정 배정기를 호출한다. 아직이면 `WAITING_FRAME`으로 두고 Worker를 점유하지 않는다.
10. `next_part_index`를 증가시키고 STT가 이미 `COMPLETED`인 다음 part를 이어서 처리한다.
11. 마지막 part에서는 `pending_words`와 작은 `chunk_buffer`도 최종 청크로 확정한다.

part 완료 순서가 `0 → 2 → 1`이라면 part 2 결과는 저장만 하고 Worker를 반환한다. part 1 완료 이벤트가 part 1과 이미 완료된 part 2를 차례로 조립한다.

normalization 진행으로 대기 중인 청크의 시간 범위까지 후보 JPEG가 준비되면 enrichment 상태를 `WAITING_FRAME`에서 `READY`로 바꾸고 공정 배정기를 호출한다. 청크 생성과 후보 JPEG 준비 중 어느 쪽이 먼저 끝나도 같은 조건을 검사한다.

최종 transcript segment는 기존 DB 계약을 유지한다. 안정된 문장이 만들어질 때 DB에 저장하고, 모든 part가 반영되면 transcript 완료 상태를 기록한다.

### 5.4 `ENRICH_CHUNK`

메시지 하나는 확정된 검색 청크 하나를 처리한다.

```text
video_id
pipeline_run_id
chunk_index
chunking_version
stt_model_version
embedding_model_version
trace_id
```

청크 text·timestamp·후보 JPEG index 참조는 Queue payload에 복사하지 않고 `pipeline_chunk_work`에서 읽는다. Queue 재전달과 DB 상태가 서로 다른 값을 갖지 않게 하기 위해서다.

처리 순서는 다음과 같다.

1. 청크 시간 범위에 해당하는 후보 JPEG를 영속 metadata에서 찾는다.
2. 선택한 JPEG만 GCS에서 내려받는다.
3. 선택한 JPEG를 기존 `KEYFRAME` asset으로 등록하거나 기존 asset을 재사용한다.
4. Vision으로 caption, OCR, scene tag를 만든다.
5. 기존 방식대로 transcript와 Vision 결과를 합쳐 `enriched_text`를 만든다.
6. 기존 `chunk` 테이블에 enrichment가 끝난 청크를 저장한다.
7. enrichment 상태를 `COMPLETED`, embedding 상태를 `READY`로 바꾸고 embedding 공정 배정기를 호출한다.
8. enrichment 실행 슬롯을 반환하고 다음 영상을 우선 선택한다.
9. 로컬 JPEG를 삭제한다.

전체 원본 영상에서 청크마다 keyframe을 다시 추출하는 현재 경로는 제거한다.

### 5.5 `EMBED_BATCH`

공정 배정기가 같은 model version과 index를 사용하는 `READY` chunk를 영상별로 한 개씩 순환해 현재 batch size 이내로 묶는다. `EMBED_BATCH` 메시지는 배정이 끝난 chunk 참조 목록과 batch 식별자를 담는다. consumer가 FIFO 메시지를 읽은 뒤 임의로 다시 묶지 않는다.

처리 순서는 다음과 같다.

1. 메시지의 모든 chunk가 같은 model version과 index를 사용하는지 확인한다.
2. `enriched_text`를 embedding endpoint에 전달한다.
3. 반환 순서를 요청 chunk 순서와 대조한다.
4. chunk별 vector를 DB에 저장하고 embedding 상태를 `COMPLETED`로 바꾼다.
5. 동일 chunk와 model version의 vector가 이미 있으면 다시 저장하지 않는다.
6. 저장 후 각 영상의 완료 조건을 확인한다.
7. embedding 실행 슬롯을 반환하고 다음 영상별 순환 batch를 배정한다.

### 5.6 영상 완료 조건

다음을 모두 만족할 때만 video를 `READY`로 바꾼다.

- normalization 완료
- 예상한 모든 audio part의 STT 완료
- 모든 part가 transcript 조립 상태에 반영됨
- `pending_words` flush 완료
- 예상한 모든 검색 청크의 enrichment 완료
- 모든 검색 청크에 현재 embedding model·index의 vector가 하나씩 존재
- 삭제 요청 또는 최종 실패 상태가 아님

중간 청크와 vector는 먼저 저장할 수 있지만 video가 READY가 아니면 검색 서비스에서 보이지 않게 현재 SOT gate를 유지한다.

모든 stage 메시지는 `pipeline_run_id`가 현재 영상의 활성 run과 일치하는지 먼저 확인한다. 삭제·재처리 뒤 늦게 도착한 이전 run 메시지는 결과를 쓰거나 다음 메시지를 발행하지 않는다.

## 6. 저장 위치

확정된 저장 책임은 다음과 같다.

| 데이터 | 저장 위치 |
|---|---|
| 원본 영상 | GCS, 기존 계약 유지 |
| audio part | GCS |
| 후보 JPEG | GCS |
| 후보 JPEG timestamp·경로 metadata | DB 또는 GCS, 11절에서 결정 |
| part 완료 상태·순서 | DB |
| `pending_words`·`chunk_buffer`·다음 index | DB |
| enrichment 전 검색 청크 | DB `pipeline_chunk_work` 신규 |
| embedding batch와 처리 상태 | DB `pipeline_embedding_batch` 신규 |
| 영상별 마지막 stage 배정 시각 | DB `pipeline_stage_schedule` 신규 |
| 최종 transcript segment | DB `transcript_segment` |
| 검색 청크·Vision 결과 | DB `chunk` |
| vector | DB `vector_index_entry` |

part STT 결과 전문의 저장 위치는 아직 정하지 않았다. 메모리에만 보관할 수는 없다. 독립 Worker의 재시도와 순서가 뒤섞인 완료를 복구할 수 있도록 DB 또는 GCS에 영속 저장해야 한다.

신규 처리 상태는 다섯 책임으로 분리한다.

```text
pipeline_run
- 활성 run과 pipeline version
- normalization·transcript 완료 여부
- expected_part_count·expected_chunk_count
- 후보 JPEG가 준비된 마지막 영상 timestamp
- next_part_index·pending_words·chunk_buffer·next_chunk_index
- 충돌 방지 version

pipeline_audio_part
- part index와 시간 범위
- audio GCS 경로
- `stt_status`: `READY`·`DISPATCHED`·`RUNNING`·`COMPLETED`·`FAILED`
- 시도 횟수·PGMQ message id·결과 참조

pipeline_chunk_work
- chunk index와 text·시간 범위
- 후보 JPEG index 참조
- model·chunking version
- `enrichment_status`: `WAITING_FRAME`·`READY`·`DISPATCHED`·`RUNNING`·`COMPLETED`·`FAILED`
- `embedding_status`: `WAITING_ENRICHMENT`·`READY`·`DISPATCHED`·`RUNNING`·`COMPLETED`·`FAILED`
- PGMQ message id·embedding batch id

pipeline_embedding_batch
- batch id와 순서가 고정된 chunk 참조 목록
- embedding model version과 index
- `DISPATCHED`·`RUNNING`·`COMPLETED`·`FAILED` 상태
- 시도 횟수·PGMQ message id

pipeline_stage_schedule
- pipeline run과 stage
- 마지막 배정 시각
```

현재 실행 또는 Queue 대기 중인 작업 수는 `pipeline_audio_part`, `pipeline_chunk_work`, `pipeline_embedding_batch`의 상태에서 계산한다. embedding은 chunk 수가 아니라 `DISPATCHED`·`RUNNING` batch 수를 센다. 별도 count를 함께 저장해 두 값이 어긋나게 만들지 않는다.

`pipeline_audio_part`는 `(pipeline_run_id, part_index)`, `pipeline_chunk_work`는 `(pipeline_run_id, chunk_index)`, `pipeline_embedding_batch`는 `batch_id`, `pipeline_stage_schedule`은 `(pipeline_run_id, stage)`가 중복되지 않게 DB 제약을 둔다.

현재 `load_pipeline_state`는 해당 model version의 `transcript_segment`가 한 행이라도 있으면 transcript가 완료됐다고 판단한다. 리팩토링 후에는 `pipeline_run.transcript_completed`를 확인하도록 바꾼다. 일부 문장만 저장된 상태를 완료로 재사용하면 안 된다.

현재 `chunk`는 `enriched_text`와 model version을 필수로 요구한다. 청킹 직후의 초안은 `chunk`에 임시값으로 넣지 않고 `pipeline_chunk_work`에 저장한다. `ENRICH_CHUNK`가 끝났을 때만 기존 `chunk` 행을 만든다.

## 7. 멱등성과 Queue handoff

작업 식별자는 다음 조합을 기준으로 한다.

```text
NORMALIZE_VIDEO: video_id + pipeline_version
TRANSCRIBE_PART: video_id + part_index + stt_model_version
ENRICH_CHUNK: video_id + chunk_index + chunking_version + stt_model_version
EMBED_BATCH: batch_id
EMBED_BATCH item: chunk_id + embedding_model_version + index_name
```

각 handler는 외부 호출 전에 완료 결과를 확인하고, 같은 메시지가 다시 보여도 같은 결과를 하나만 남긴다.

공정 배정기는 stage별 PostgreSQL transaction advisory lock을 잡고 실행한다. 잠금 안에서 현재 `DISPATCHED`·`RUNNING` 수를 세고, 빈 슬롯만큼 서로 다른 영상을 우선 선택한다. 이를 통해 part 완료와 새 part 생성이 동시에 배정기를 호출해도 실행 상한을 넘기거나 같은 작업을 두 번 발행하지 않게 한다.

DB 상태 변경과 다음 PGMQ 메시지 발행은 같은 DB transaction 안에서 처리한다. 현재 PGMQ client는 독립 connection으로 enqueue하므로, transaction-bound enqueue 또는 DB outbox 중 하나로 바꿔야 한다. 선택은 11절에서 결정한다. GCS artifact가 필요한 단계는 다음 순서를 사용한다.

```text
결정적 GCS 경로에 업로드
  → DB 완료 상태와 artifact 경로 기록
  → 다음 Queue 메시지 발행
```

업로드 뒤 DB transaction 전에 실패하면 같은 경로에 재업로드할 수 있어야 한다. DB가 완료 상태인데 GCS object가 없는 순서는 허용하지 않는다.

## 8. 실패와 삭제

- retryable 오류는 Queue 메시지를 ack하지 않고 visibility timeout 뒤 다시 처리한다.
- retryable 메시지는 같은 실행 슬롯을 계속 점유한 것으로 계산하며, 재시도용 새 작업을 추가 배정하지 않는다.
- terminal 오류 또는 재시도 한도 초과는 해당 작업을 `FAILED`로 바꾸고 영상 실패를 확정한다. 같은 transaction에서 빈 슬롯을 다시 배정한 뒤 현재 메시지는 ack한다.
- 재시도는 영상 전체가 아니라 실패한 stage 작업만 다시 실행한다.
- 삭제 요청이 들어오면 새 stage 발행을 중단한다.
- 이미 실행 중인 외부 호출은 반환 직후 삭제 상태를 다시 확인하고 결과를 폐기한다.
- 완료된 GCS 중간 artifact는 삭제 정책에 따라 정리한다.
- process 종료 후 PGMQ 메시지가 다시 보이면 기존 `DISPATCHED`·`RUNNING` 상태와 message id를 대조해 같은 작업을 재개한다.
- `DISPATCHED`인데 대응하는 PGMQ 메시지나 outbox가 없는 상태는 주기적 복구 작업이 `READY`로 되돌린다.

Queue별 visibility timeout과 최대 재시도 횟수는 아직 정하지 않았다. 현재 preprocess 전체에 적용되는 30분 timeout을 네 Queue에 그대로 복사하지 않는다.

## 9. 구현 순서

1. stage 메시지 schema와 네 Queue를 추가한다.
2. `pipeline_run`, `pipeline_audio_part`, `pipeline_chunk_work`, `pipeline_embedding_batch`, `pipeline_stage_schedule` migration과 repository를 추가한다.
3. stage별 advisory lock, 실행 상한, 영상별 순환 선택을 담당하는 공정 배정기를 구현한다.
4. core-api는 `NORMALIZE_VIDEO`만 발행하고, stage handler는 다음 작업을 DB `READY`로 만든 뒤 배정기를 호출하게 한다.
5. 네 Queue를 독립적으로 소비하는 consumer loop와 stage별 실행 제한을 추가한다.
6. 기존 `PREPROCESS_REQUEST` handler를 `NORMALIZE_VIDEO` 시작점으로 바꾼다.
7. GCS 순차 입력과 audio part·후보 JPEG 산출 경로를 구현한다.
8. `TRANSCRIBE_PART` handler와 part 결과 복구를 구현한다.
9. 기존 word ownership과 청킹 규칙을 상태형 조립기로 옮긴다.
10. 청크 단위 `ENRICH_CHUNK` handler를 구현하고 원본 keyframe 재추출을 제거한다.
11. 영상별 순환 batch를 받는 `EMBED_BATCH` consumer와 chunk별 vector 저장을 구현한다.
12. 마지막 vector 저장 시 READY 조건을 검사한다.
13. 기존 영상 단위 `PipelineOrchestrator.run` 경로를 제거한다.

같은 책임을 기존 경로와 새 경로에 계속 유지하지 않는다. 전환 기간에만 어댑터를 허용하고 제거 조건을 테스트에 명시한다.

## 10. 검증

### 기능 검증

- 15분 part와 5초 overlap 구간이 현재와 같음
- overlap 단어가 한 번만 transcript에 포함됨
- part 완료 순서 `0 → 2 → 1`에서도 transcript·chunk 순서가 같음
- 미완성 문장이 다음 part와 연결됨
- 구두점 없는 100단어가 강제로 닫힘
- 300개 상한과 문장 1개 overlap이 현재 결과와 같음
- 중복 Queue 메시지에서 STT·Vision·vector가 중복 저장되지 않음
- Worker 종료 후 `pending_words`와 `chunk_buffer`에서 재개됨
- 마지막 part의 작은 청크가 flush됨
- 삭제와 stage retry가 READY를 잘못 만들지 않음
- A 영상 part 4개가 먼저 `READY`여도 B 영상 part가 도착하면 현재 실행 중인 A 작업 다음 슬롯에 B가 배정됨
- 여러 영상이 대기하면 STT·enrichment에서 영상별 작업 하나를 먼저 선택함
- 한 영상만 대기하면 해당 영상이 stage의 빈 슬롯을 모두 사용할 수 있음
- A 영상의 청크가 많아도 B 영상 청크가 enrichment Queue 뒤에 대량으로 밀리지 않음
- embedding batch가 호환되는 영상들의 chunk를 영상별로 순환해 구성함
- 동시 배정 호출에서도 `DISPATCHED`·`RUNNING` 수가 stage 상한을 넘지 않음
- retry 중인 작업이 새 슬롯으로 중복 계산되지 않음

### 성능 비교

기존 S1~S4 fixture와 환경을 그대로 사용한다.

```text
pipeline-worker: 1대
normalization ffmpeg 동시 실행: 2
STT part: 15분
STT overlap: 5초
STT 동시성: 2
영상별 순환 배정: 사용
embedding 설정: 기준선과 동일
```

비교 항목은 다음과 같다.

- long 뒤에 들어온 short의 Queue 대기시간
- stage Queue별 대기시간과 가장 오래된 메시지 나이
- stage·영상별 `READY` 대기시간과 연속 배정 횟수
- long 작업 실행 중 들어온 short가 각 stage에서 첫 슬롯을 받을 때까지의 시간
- part 완료부터 첫 검색 청크 발행까지의 시간
- 영상별 전체 완료시간
- Worker CPU·메모리와 로컬 임시파일 최대 크기
- STT·Vision·embedding 동시 작업 수
- ffmpeg 1개와 2개 실행 시 영상별 처리시간·CPU·메모리 변화
- stage별 재시도와 중복 처리 건수

영상별 순환 배정은 긴 영상의 작업 개수가 FIFO를 점유하지 않게 하는 기본 설계이므로 첫 비교에 포함한다. STT 전용 Worker, part 길이 축소, embedding 설정 변경은 함께 적용하지 않는다.

## 11. 구현 전에 결정할 항목

다음 항목은 현재 세션에서 값이 정해지지 않았다. 구현자가 임의로 확정하지 않는다.

1. 후보 JPEG 생성 간격과 해상도
2. 청크 시간 범위에 후보 JPEG가 여러 장일 때 선택 규칙
3. 후보 JPEG timestamp·GCS 경로 metadata를 DB와 GCS 중 어디에 어떤 단위로 저장할지
4. GCS 원본을 ffmpeg에 전달하는 방식: signed URL, file-like stream, stdin pipe 중 선택
5. 한 번의 ffmpeg 실행에서 5초 overlap audio part를 닫아 조기 업로드하는 구체 방식
6. part STT 결과 전문을 DB와 GCS 중 어디에 저장할지
7. part STT 결과·audio part·후보 JPEG의 보존 기간과 정리 시점
8. 네 Queue의 visibility timeout과 재시도 한도
9. `ENRICH_CHUNK`와 `EMBED_BATCH`의 실행 상한
10. `EMBED_BATCH`가 호환되는 여러 영상의 chunk를 모으기 위해 기다릴 최대 시간
11. DB 상태와 PGMQ 발행 원자성을 transaction-bound enqueue와 outbox 중 어떤 방식으로 보장할지

이 값들은 첫 버전의 storage schema·ffmpeg adapter·consumer 설정을 바꾸므로 해당 구현에 들어가기 전에 결정한다.

## 12. 후속 개선 조건

첫 리팩토링 결과에서 `TRANSCRIBE_PART` Queue가 계속 병목일 때만 다음을 별도 변경으로 적용한다.

1. STT 전용 최소 이미지와 배포 단위 분리
2. STT Worker 1대 기준 측정
3. STT Worker 수평 확장
4. 필요하면 part 길이를 15분에서 10분으로 축소
5. 10분에서도 단일 영상 완료시간이 문제일 때 5분 검토

각 변경은 앞 단계 설정을 고정한 상태에서 하나씩 비교한다.
