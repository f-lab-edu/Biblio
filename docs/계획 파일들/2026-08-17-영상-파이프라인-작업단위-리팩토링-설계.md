# 영상 파이프라인 작업 단위 리팩토링 설계

- 작성일: 2026-08-17
- 대상: `services/pipeline-worker`, `services/core-api`, Queue·DB 배포 설정
- 상태: 첫 버전 범위와 정책 결정 완료, 단계별 구현 진행 중

## 1. 목적과 범위

현재는 영상 하나가 다운로드부터 vector 저장까지 Worker 슬롯 하나를 계속 점유한다. 이를 단계별 작업으로 나눠 긴 영상이 짧은 영상과 후속 단계를 막지 않게 한다.

S4에서 long 작업 뒤 10초 늦게 들어온 short 작업은 평균 약 395초를 Queue에서 기다렸고 실제 처리시간은 약 39초였다. 첫 버전은 자원을 늘리지 않고 작업 분리와 영상별 순환 배정으로 이 대기를 줄인다.

첫 버전에서 유지할 조건은 다음과 같다.

- `pipeline-worker` 1대·1 vCPU·4Gi
- STT 전용 배포 단위 없음
- STT part `15분 + 5초 overlap`, 동시성 2
- 공백 기준 최대 300개와 문장 1개 overlap 청킹
- 기존 embedding batch size와 embedding VM 설정
- 별도 디스크 볼륨과 proxy video segment 없음
- 영상 완료 전 중간 청크를 검색 결과에 노출하지 않음

## 2. 목표 구조

```text
NORMALIZE_VIDEO
  → TRANSCRIBE_PART × N
  → ASSEMBLE_CHUNKS
  → ENRICH_CHUNK × M
  → EMBED_BATCH
  → 완료 조건 확인
  → video READY
```

물리 Queue는 `NORMALIZE_VIDEO`, `TRANSCRIBE_PART`, `ENRICH_CHUNK`, `EMBED_BATCH` 네 개다. `ASSEMBLE_CHUNKS`는 DB 상태를 짧게 전진시키는 내부 작업이다. 별도 `FINALIZE` Queue는 만들지 않고 마지막 vector 저장 작업이 완료 조건을 확인한다.

각 Queue는 같은 Worker 안의 독립 consumer loop가 소비한다. 전역 `WORKER_CONCURRENCY` 대신 stage별 실행 상한을 두며, 한 stage가 외부 응답을 기다려도 다른 Queue 소비는 계속한다.

### 2.1 작업 배정

part와 chunk를 모두 PGMQ에 미리 넣지 않고 DB에 대기시킨다.

```text
READY       실행 가능, Queue 미발행
DISPATCHED  Queue 발행 완료
RUNNING     consumer 실행 중
COMPLETED   결과 저장 완료
FAILED      재시도 한도 초과
```

작업 배정기는 stage별 advisory lock 안에서 `DISPATCHED + RUNNING`이 실행 상한을 넘지 않는 범위만 발행한다.

1. 해당 stage에서 가장 오래 선택되지 않은 영상을 고른다.
2. 시각이 같으면 가장 오래된 `READY`, 그다음 `video_id` 순서로 고른다.
3. 대기 영상마다 작업 하나를 먼저 선택한 뒤 남은 슬롯을 채운다.
4. 다른 영상이 없으면 한 영상이 빈 슬롯을 모두 사용할 수 있다.

이 정책은 `TRANSCRIBE_PART`와 `ENRICH_CHUNK`에 적용한다. `EMBED_BATCH`는 호환되는 chunk를 영상별로 하나씩 순환해 batch를 만든다. `NORMALIZE_VIDEO`는 영상당 작업 하나이며 실행 중 선점하지 않는다.

handler 성공 시 한 DB transaction에서 결과 저장, `COMPLETED`, 다음 작업 `DISPATCHED`, PGMQ 발행을 처리하고 commit 뒤 현재 메시지를 ack한다. commit 뒤 ack 전에 종료되어도 재전달된 작업은 완료 결과를 확인해 외부 호출을 반복하지 않는다.

## 3. 단계별 설계

### 3.1 `NORMALIZE_VIDEO`

Worker는 실행 직전에 GCS 원본 generation에 고정된 짧은 수명의 읽기 전용 signed URL을
발급한다. ffprobe와 ffmpeg는 이 URL을 HTTP 입력으로 사용하고 필요한 위치를 Range 요청으로
읽는다. 원본 전체를 Worker 메모리나 normalization 작업 디렉터리에 저장하지 않는다.
세부 선택과 보안·실패 계약은 [ADR-017](../ADR/ADR-017-normalization-gcs-media-input-strategy.md)을 따른다.

```text
GCS 원본
  ├─ STT용 FLAC part: 0~15:00, 14:55~30:00, ...
  └─ Vision 후보 JPEG
```

- FLAC 생성이 완료된 part는 GCS에 업로드하고 DB에서 `READY`로 바꾼 뒤 STT 작업 배정기를 호출한다.
- 업로드가 끝난 로컬 part와 JPEG는 즉시 삭제한다.
- 후보 JPEG의 timestamp와 GCS 경로는 normalization 완료 전에도 조회할 수 있게 영속 저장한다.
- 후보 JPEG는 60초 간격으로 생성한다. 첫 후보는 `min(영상 길이의 절반, 30초)`이며 이후 60초마다 만든다. 짧은 영상은 영상 중앙 한 장을 갖는다.
- 후보 JPEG는 가로 1280px를 넘지 않게 축소하고 세로 비율은 유지한다. 후보 전체는 같은 signed URL을 입력으로 한 번의 ffmpeg 실행에서 생성한다.
- 전체 완료 시 확정된 전체 part 수인 `total_part_count`와 normalization 완료 상태를 기록한다.
- `EXTERNAL_URL`은 원본을 GCS에 저장한 뒤 같은 경로로 들어온다. 외부 URL 다운로드의 전체 로컬 파일 제거는 첫 버전 범위가 아니다.
- 업로드가 끝난 로컬 FLAC·JPEG는 즉시 삭제하며, 나머지 임시 산출물도 성공·실패와 관계없이 normalization 실행이 끝날 때 삭제한다.

Worker가 1 vCPU이므로 ffmpeg 2개는 CPU 병렬 실행이 아니라 I/O 대기 중첩 후보다. 같은 입력에서 동시 실행 1과 2를 먼저 비교하고, 2가 short 시작 대기를 줄이면서 처리량 저하·자원 초과·timeout이 없을 때만 2를 사용한다.

### 3.2 `TRANSCRIBE_PART`

메시지는 `pipeline_run_id`, `part_index`, 시간 범위, audio GCS 경로, STT model version, `trace_id`를 가진다.

1. 같은 part와 model version의 완료 결과가 있으면 STT를 다시 호출하지 않는다.
2. GCS FLAC을 Google BatchRecognize에 전달한다.
3. 단어·구두점·단어별 상대 timestamp를 영속 저장하고 part를 `COMPLETED`로 바꾼다.
4. 앞에서부터 연속 완료된 part가 있으면 3.3의 조립 상태를 전진시킨다.
5. 앞 part가 없으면 결과만 저장하고 종료한다. Worker가 순서를 기다리지 않는다.

전역 동시성은 2다. 여러 영상이 대기하면 영상별 part 하나를 먼저 배정한다.

### 3.3 `ASSEMBLE_CHUNKS`

영상별 상태는 `next_part_index`, `pending_words`, `chunk_buffer`, `next_chunk_index`다. 같은 영상은 DB 잠금으로 한 번에 하나만 조립한다.

1. `next_part_index` part가 완료되지 않았으면 종료한다.
2. 상대 timestamp를 영상 전체 timestamp로 바꾼다.
3. 5초 overlap 중앙을 ownership 경계로 사용해 중복 단어를 제거한다.
4. 이전 `pending_words`와 현재 단어를 합친다.
5. 구두점 또는 기존 100단어 상한으로 문장 경계를 확정한다.
6. 문장을 최대 300개 단어까지 모으고, 확정 청크의 마지막 문장 하나를 다음 청크에 overlap한다.
7. 후보 JPEG가 준비됐으면 청크를 `READY`, 아니면 `WAITING_FRAME`으로 저장한다.
8. `next_part_index`를 올리고 이미 완료된 다음 part를 이어서 처리한다.
9. 마지막 part에서 남은 문장과 작은 청크를 모두 확정한다.

후보 JPEG가 나중에 준비되면 해당 청크를 `WAITING_FRAME`에서 `READY`로 바꾸고 배정기를 호출한다. 최종 transcript는 기존 `transcript_segment`에 저장하고 모든 part 반영 후 완료 상태를 기록한다.

### 3.4 `ENRICH_CHUNK`

메시지는 작업 식별자와 version만 담고 text·timestamp·후보 JPEG 참조는 `pipeline_chunk_work`에서 읽는다.

1. 청크 시간 범위에 맞는 후보 JPEG를 선택해 GCS에서 받는다.
2. 기존 `KEYFRAME` asset을 만들거나 재사용한다.
3. Vision caption·OCR·scene tag와 transcript를 합쳐 `enriched_text`를 만든다.
4. 기존 `chunk`에 저장하고 enrichment를 `COMPLETED`, embedding을 `READY`로 바꾼다.
5. embedding 배정기를 호출하고 로컬 JPEG를 삭제한다.

청크마다 전체 원본에서 keyframe을 다시 추출하는 기존 경로는 제거한다.

### 3.5 `EMBED_BATCH`

작업 배정기는 같은 model version과 index를 쓰는 `READY` chunk를 영상별로 순환해 기존 batch size 이내로 묶는다.

1. batch 조건과 chunk 순서를 검증한다.
2. `enriched_text`를 embedding endpoint에 전달한다.
3. 응답 순서를 대조해 chunk별 vector를 저장하고 embedding을 `COMPLETED`로 바꾼다.
4. 같은 chunk·model version·index의 vector는 중복 저장하지 않는다.
5. 참여 영상의 완료 조건을 확인하고 다음 batch를 배정한다.

### 3.6 영상 완료 조건

다음 조건을 모두 만족할 때만 video를 `READY`로 바꾼다.

- normalization과 모든 part STT 완료
- 모든 part가 조립 상태에 반영되고 `pending_words`가 flush됨
- 모든 `pipeline_chunk_work`의 enrichment 완료
- 모든 청크에 현재 model·index vector가 존재
- 삭제 요청과 최종 실패가 없음

모든 메시지는 먼저 `pipeline_run_id`가 현재 활성 run과 같은지 검사한다. 이전 run 메시지는 결과와 후속 작업을 만들지 않는다.

### 3.7 영상·프로젝트 삭제

삭제 요청은 특정 stage를 즉시 강제 종료하는 기능이 아니라, 삭제 대상에 새 결과가 붙지 않게 막는 fence다. `video.status = DELETING`을 영상 삭제 fence로 사용한다.

모든 stage handler와 작업 배정기는 다음 규칙을 공통으로 지킨다.

1. 작업을 배정하거나 외부 호출을 시작하기 전에 영상이 `DELETING`인지 확인한다.
2. 삭제 중이면 새 작업을 배정·발행하지 않고 `READY`·`DISPATCHED` 작업을 `CANCELLED`로 바꾼다.
3. ffmpeg, STT, Vision, embedding처럼 안전하게 중단할 수 없는 호출이 이미 실행 중이면 반환까지 기다린다.
4. 호출 반환 직후, 결과 저장 transaction 안에서 영상 행을 잠그고 삭제 상태를 다시 확인한다.
5. 삭제 중이면 반환 결과를 완료 결과로 저장하지 않고 다음 stage도 발행하지 않는다. 이번 실행이 만든 로컬·GCS 산출물은 삭제하고 작업을 `CANCELLED`로 바꾼다.
6. 삭제 중이 아니면 결과 저장과 다음 Queue 발행을 같은 transaction으로 처리한다.

삭제 처리는 해당 영상의 `RUNNING` 작업이 0개가 될 때까지 delete 메시지를 ack하지 않고 다시 시도한다. `DISPATCHED` 메시지는 외부 호출을 시작하지 않으므로 기다릴 대상이 아니며 `CANCELLED`로 바꾼다. Worker 종료로 남은 오래된 `RUNNING`은 기존 visibility timeout·복구 기준으로 실제 실행 여부를 판정한 뒤 `CANCELLED`로 회수한다.

실행 중 작업이 모두 반환하면 기존 영상 삭제 경로가 다음 순서로 정리한다.

```text
새 작업 배정·발행 차단
→ 실행 중 작업 반환과 결과 폐기 대기
→ 원본 영상, audio part, 후보 JPEG·KEYFRAME 등 GCS 산출물 삭제
→ transcript_segment, chunk, vector_index_entry 등 결과 행 삭제
→ video 행 hard delete
→ FK CASCADE로 pipeline_run과 part·chunk·batch·schedule 삭제
```

늦게 도착한 Queue 메시지는 영상 없음, `DELETING`, 이전 run, `CANCELLED` 중 하나를 확인하면 외부 호출이나 결과 생성 없이 ack한다. GCS 경로는 run과 작업 ID로 결정적으로 만들고 삭제 시 DB에 기록된 경로와 결정적 경로를 함께 정리해, DB 완료 기록 전에 업로드된 산출물도 남기지 않는다.

여러 영상의 chunk를 포함하는 embedding batch에서 일부 영상만 삭제되면 호출 자체는 끝까지 수행한다. 반환 후 삭제된 영상의 vector만 폐기하고, 삭제되지 않은 영상의 vector는 정상 저장한다.

프로젝트 삭제는 현재처럼 프로젝트에 속한 모든 영상을 먼저 영상 삭제 경로로 넘긴다. 소속 영상은 한 transaction에서 모두 `DELETING`으로 바꿔 정상·대기·실행 중 상태와 관계없이 새 작업을 차단하고 위 규칙에 따라 정리한다. 모든 영상의 삭제가 끝난 뒤에만 프로젝트 행과 프로젝트 단위 산출물을 삭제한다. 일부 영상에 실행 중 작업이 남아 있으면 프로젝트 삭제 메시지도 ack하지 않고 다시 시도한다.

## 4. 저장 구조

| 저장소 | 책임 |
|---|---|
| GCS | 원본, audio part, 후보 JPEG |
| 후보 JPEG metadata | DB `pipeline_frame_candidate`, 후보 한 장당 한 행 |
| part STT 전문 | GCS JSON, `pipeline_audio_part.result_ref`에 결정적 경로 저장 |
| `pipeline_run` 신규 | 활성 run, 원본 object 경로·generation, normalization·transcript 완료, `total_part_count`, 조립 상태, normalization message id·상태 시각 |
| `pipeline_audio_part` 신규 | `pipeline_run_id`, `audio_part_id`, `part_index`, 시간·GCS 경로, STT 상태·시도·message id·결과 참조·상태 시각 |
| `pipeline_chunk_work` 신규 | `pipeline_run_id`, `chunk_work_id`, `chunk_index`, text·시간·frame 참조, enrichment·embedding 상태·시도·message/batch id·상태 시각 |
| `pipeline_embedding_batch` 신규 | `batch_id`, 순서가 고정된 chunk 목록, model·index, 상태·시도·message id·상태 시각 |
| `pipeline_stage_schedule` 신규 | run·stage별 마지막 배정 시각 |
| 기존 결과 테이블 | `transcript_segment`, `chunk`, `vector_index_entry` 재사용 |

전체 chunk 수와 실행·대기 수는 상태 테이블에서 계산한다. 조립 완료 후 해당 run의 `pipeline_chunk_work` 행 수를 전체 chunk 수로 사용한다. embedding 대기는 chunk 수, 실행 중은 batch 수로 센다.

중복 방지 제약은 다음과 같다.

```text
pipeline_audio_part:       (pipeline_run_id, part_index)
pipeline_chunk_work:       (pipeline_run_id, chunk_index)
pipeline_embedding_batch:  batch_id
pipeline_stage_schedule:   (pipeline_run_id, stage)
```

일부 transcript가 저장됐다는 이유로 완료 처리하지 않는다. 기존 `load_pipeline_state`의 “한 행 존재” 판정은 `pipeline_run.transcript_completed` 확인으로 바꾼다. enrichment 전 초안은 기존 `chunk`가 아니라 `pipeline_chunk_work`에 둔다.

## 5. 일관성·실패 처리

작업 식별 기준은 다음과 같다.

```text
NORMALIZE_VIDEO: video_id + pipeline_version
TRANSCRIBE_PART: video_id + part_index + stt_model_version
ENRICH_CHUNK:    video_id + chunk_index + chunking_version + stt_model_version
EMBED_BATCH:     batch_id
vector:          chunk_id + embedding_model_version + index_name
```

- handler는 외부 호출 전에 기존 완료 결과를 확인한다.
- handler와 배정기는 외부 호출·결과 저장·후속 발행 전에 영상 삭제 fence를 확인한다.
- consumer는 message id가 일치하고 상태가 `DISPATCHED` 또는 `RUNNING`일 때만 실행한다.
- DB 상태 변경과 PGMQ 발행은 같은 transaction으로 묶는다. 현재 client는 별도 connection이므로 transaction-bound enqueue 또는 outbox가 필요하다.
- GCS 산출물은 `결정적 경로 업로드 → DB 완료·경로 기록 → 다음 Queue 발행` 순서를 지킨다.
- retryable 오류는 메시지를 ack하지 않고 같은 슬롯을 점유한 채 재시도한다.
- 재시도 한도 초과는 작업과 영상을 `FAILED`로 바꾸고 빈 슬롯을 다시 배정한 뒤 ack한다.
- `DISPATCHED`인데 PGMQ 메시지나 outbox가 없으면 복구 작업이 `READY`로 되돌린다.
- 작업 상태에는 삭제로 결과를 사용하지 않는 `CANCELLED`를 포함한다. `CANCELLED` 작업은 재시도·복구·완료 집계 대상에서 제외한다.
- 삭제 요청 후 새 작업을 발행하지 않는다. 실행 중 결과는 반환 직후 삭제 상태를 확인해 폐기하고, 모든 실행이 끝난 뒤 기존 영상·프로젝트 삭제 경로로 산출물과 상태 행을 정리한다.

Queue visibility timeout은 `NORMALIZE_VIDEO` 7200초, `TRANSCRIBE_PART` 4200초,
`ENRICH_CHUNK` 120초, `EMBED_BATCH` 300초다. stage handler의 최대 전달 횟수는
최초 실행을 포함해 3회다. provider adapter 내부 재시도는 이 횟수와 별도로 센다.

## 6. 로깅과 성능 계측

현재 로그는 영상별 고정 stage가 겹치지 않는다고 가정하고, Worker Python 프로세스만 측정한다. 새 구조는 part·chunk·stage가 겹치므로 작업 단위 로그와 timeline이 필요하다.

### 6.1 로그 계약

운영 환경은 Cloud Logging `jsonPayload`, 로컬은 같은 JSON 한 줄을 사용한다.

공통 필드:

```text
log_schema_version, timestamp_utc, event_name
trace_id, video_id, pipeline_run_id
stage, work_id, work_attempt
part_index, chunk_index, batch_id
queue_name, message_id, read_ct
```

`EMBED_BATCH`는 실행 로그를 한 번만 남기고 `trace_ids`, `video_ids`, `pipeline_run_ids`로 참여 영상을 연결한다. `work_id`는 DB 기본키를 쓰며 `NORMALIZE_VIDEO`는 `pipeline_run_id`, `ASSEMBLE_CHUNKS`는 실행별 UUID를 사용한다.

상태 이벤트는 다음으로 고정한다.

```text
pipeline.work.ready
pipeline.work.dispatched
pipeline.work.started
pipeline.work.succeeded
pipeline.work.retryable_failed
pipeline.work.failed
pipeline.work.skipped
pipeline.video.completed
pipeline.video.failed
```

상태와 상태 시각의 기준은 DB다. 상태 변경 transaction에서 PostgreSQL 시각을 저장하고 로그에 복사한다. 실행시간은 monotonic clock으로 잰다.

lifecycle에는 해당 상태 시각과 `ready_wait_ms`, `queue_wait_ms` 또는 `retry_wait_ms`, `execution_ms`를 기록한다. 실패에는 `failure_code`, `provider`, 재시도 가능 여부, handler·provider 시도 횟수, HTTP 상태와 재시도 대기시간을 기록한다.

`EMBED_BATCH`에는 READY 이벤트를 만들지 않고, `ASSEMBLE_CHUNKS`에는 READY와 DISPATCHED 이벤트를 만들지 않는다. 외부 adapter는 시도별 시간·오류만 기록하고 terminal stack trace는 stage handler에서 한 번만 남긴다.

내부 구간은 `ffmpeg.operation`, `gcs.operation`, `db.transaction`, `stt.request.*`, `vision.request.*`, `embedding.request.*`, `embedding.admission`으로 분리한다. 각 이벤트에는 작업 ID, 시작·완료 시각, duration, 상태·오류 code, 크기 또는 결과 개수만 기록한다.

로그에 transcript·OCR·caption 전문, embedding 입력·vector, 이미지·음성, 전체 GCS URI, signed URL·token, Gemini·STT body와 payload, 로컬 keyframe 경로를 기록하지 않는다.

### 6.2 표본과 timeline

- `queue.sample`: 네 Queue의 ready·invisible·가장 오래된 메시지 나이
- `stage.work.sample`: DB의 stage별 READY·DISPATCHED·RUNNING·FAILED와 가장 오래된 READY 대기. embedding READY는 chunk 수, 실행 중은 batch 수로 구분
- `worker.process.sample`: container cgroup CPU·메모리. 개발 환경만 process tree로 대체하고 측정 범위를 기록
- normalization: 실행 중 ffmpeg 수와 로컬 임시파일 크기
- embedding VM: 기존 host·container·endpoint와 슬롯 대기 계측 유지

CPU는 할당 vCPU, 메모리는 container limit을 각각 100%로 계산한다. 첫 비교는 Worker 자원 1초, Queue·DB 상태 5초 간격을 사용하고 실제 값은 `environment.json`에 저장한다.

새 실행 interval key는 `(stage, work_id, work_attempt)`다. 재시도는 별도 interval로 만들고, 여러 영상의 `EMBED_BATCH`는 실행 수를 한 번만 센다. stage span은 겹칠 수 있으므로 합산하지 않으며 영상 전체시간은 최초 요청부터 완료·실패까지 계산한다.

성능 보고서는 다음을 포함한다.

- stage·영상별 READY 대기, Queue 대기, 실행시간, wall-clock span
- Worker와 embedding VM CPU·메모리 최대·p50·p95
- CPU 5% 미만·80% 이상, 메모리 80% 이상 누적시간·최장 연속시간·비율
- CPU 5% 미만 구간과 GCS·DB·STT·Vision·embedding·endpoint 슬롯 대기의 겹친 시간

시간 겹침은 원인 후보일 뿐 인과관계로 단정하지 않는다. 기존 parser는 S1~S4 재현용으로 유지하고 새 JSON parser와 병렬 timeline을 별도 schema version으로 추가한다.

기준선 대응은 `download + audio → NORMALIZE_VIDEO`, `stt → TRANSCRIBE_PART`, `chunk_enrichment → ASSEMBLE_CHUNKS + ENRICH_CHUNK`, `embedding → EMBED_BATCH`, `persist → 마지막 결과 commit부터 READY commit`으로 고정한다.

## 7. 구현 순서

1. stage 메시지와 네 Queue 추가
2. 신규 상태 테이블과 repository 추가
3. advisory lock·실행 상한·영상별 순환 작업 배정기 구현
4. 네 독립 consumer loop와 stage별 실행 제한 구현
5. 공통 JSON 로그와 상태·자원 표본 수집 구현
6. `PREPROCESS_REQUEST`를 `NORMALIZE_VIDEO` 시작점으로 변경
7. generation 고정 GCS signed URL HTTP 입력과 audio part·후보 JPEG 생성 구현
8. `TRANSCRIBE_PART`와 상태형 `ASSEMBLE_CHUNKS` 구현
9. `ENRICH_CHUNK`와 `EMBED_BATCH` 구현
10. 영상 READY 판정과 삭제·복구 경로 구현
11. 부하 테스트 parser·timeline 변경
12. 기존 영상 단위 `PipelineOrchestrator.run` 제거

기존 경로와 새 경로에 같은 책임을 계속 유지하지 않는다.

## 8. 검증

기능 검증:

- 15분 part·5초 audio overlap, overlap ownership 결과가 현재와 같음
- part 완료 순서가 뒤섞여도 transcript·chunk 순서가 같음
- 미완성 문장, 100단어 상한, 300단어 청크, 문장 overlap, 마지막 flush가 현재 규칙과 같음
- Worker 종료 후 조립 상태에서 재개됨
- 중복·이전 run·삭제 메시지가 외부 호출과 결과를 중복 생성하지 않음
- normalization·STT·Vision·embedding 실행 중 삭제 요청이 들어오면 실행 중 호출만 반환까지 기다리고, 결과·후속 메시지·GCS 산출물이 남지 않음
- 영상 삭제가 원본과 모든 중간·최종 산출물 및 pipeline 작업 상태를 정리함
- 프로젝트 삭제가 정상·대기·실행 중인 영상을 모두 같은 영상 삭제 경로로 정리한 뒤 프로젝트를 삭제함
- 여러 영상의 embedding batch 중 한 영상만 삭제해도 다른 영상 결과는 보존되고 삭제 영상 결과만 폐기됨
- 여러 영상이 대기하면 영상별 작업 하나를 먼저 배정하고, 한 영상만 있으면 빈 슬롯을 모두 사용함
- 동시 배정에서도 실행 상한을 넘지 않고 retry 작업을 새 슬롯으로 세지 않음
- embedding batch가 호환 조건과 영상별 순환 선택을 지킴
- lifecycle 시작 시도마다 성공·재시도 실패·최종 실패 중 하나가 대응함
- 병렬 stage를 timeline이 보존하고 기존 parser가 S1~S4를 같은 값으로 읽음
- 로그에 제외 대상 데이터가 없고 ffmpeg 자원이 Worker 표본에 포함됨

성능 비교 조건:

```text
pipeline-worker: 1대·1 vCPU·4Gi
STT: 15분 + 5초 overlap, 동시성 2
영상별 순환 배정: 사용
embedding: 기준선과 동일
normalization ffmpeg: 동시 실행 1과 2 사전 비교 후 고정
```

비교값은 long 뒤 short의 첫 슬롯·완료 대기, stage별 READY·Queue 대기, part 완료부터 첫 청크 발행, 영상별 완료시간, stage 동시 작업 수, CPU·메모리·임시파일, 재시도·중복 처리 수다.

선택한다. 작업 범위나 외부 시스템 권한이 크게 달라질 때만 사용자에게 확인한다.

## 10. 후속 개선 조건

첫 결과에서 `TRANSCRIBE_PART`가 계속 병목일 때만 STT 최소 이미지 분리, Worker 수평 확장, part 길이 10분·5분을 순서대로 별도 비교한다. 각 변경은 앞 설정을 고정하고 하나씩 측정한다.
