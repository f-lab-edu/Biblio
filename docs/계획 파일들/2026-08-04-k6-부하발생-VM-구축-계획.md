# k6 부하 발생 VM 구축 계획

- 작성일: 2026-08-04
- 대상 이슈: [#104 검색 스트레스 테스트와 병목 탐색](https://github.com/f-lab-edu/Biblio/issues/104)
- 상태: 구현 대기

## 1. 목표

같은 리전과 VPC 안에서 k6를 실행해 검색·색인 스트레스 테스트의 부하를 안정적으로 발생시킨다.

개인 노트북의 CPU와 인터넷 회선이 먼저 한계에 도달해 결과를 왜곡하지 않게 하고, 테스트가 끝나면 VM을 중지해 비용을 통제한다. Fixture, 코퍼스, 고정 query set과 실제 부하 시나리오는 이 VM 위에서 실행하지만, 이번 작업에서는 실행 환경까지만 구축한다.

## 2. 범위

### 포함

- k6 전용 Compute Engine VM
- 전용 서비스 계정과 최소 IAM 권한
- 외부 IP 없는 VPC 연결
- IAP SSH 접속
- k6와 점검 도구 설치
- 테스트 파일 동기화·실행·결과 회수·VM 중지 명령
- smoke test와 부하 발생기 자체 병목 확인
- 비용 방지를 위한 기본 중지 상태와 자동 종료

### 제외

- FixtureSTTAdapter·FixtureVisionAdapter 구현
- 코퍼스 생성·적재
- 고정 query set 작성
- 검색·색인·혼합 k6 시나리오 구현
- PostgreSQL 접속 자격증명 부여
- 실제 스트레스 테스트 실행
- 애플리케이션·DB·임베딩 설정 변경

## 3. VM 구성

| 항목 | 값 |
|---|---|
| 이름 | `${name_prefix}-k6-runner` |
| 리전·존 | `asia-northeast3` / `asia-northeast3-a` |
| 머신 타입 | `e2-medium` |
| 지속 CPU | 1 vCPU 상당 |
| 메모리 | 4GB |
| 부팅 디스크 | 10GB `pd-standard` |
| 외부 IP | 없음 |
| subnet | 기존 `cloudrun` subnet |
| 접속 | IAP SSH |
| 평상시 상태 | `TERMINATED` |
| 자동 종료 | 기동 후 4시간 |
| VM 종류 | 표준 VM. Spot 미사용 |
| k6 | `v2.0.0` 고정 |

`e2-small`은 지속 CPU가 0.5 vCPU 상당이라 몇 분 이상 이어지는 테스트에서 부하 발생기가 먼저 제한될 수 있다. `e2-medium`으로 시작하고, 자체 병목 기준을 넘을 때만 `e2-standard-2`로 올린다.

Spot VM은 더 저렴하지만 테스트 중 선점되면 실행 결과를 폐기해야 한다. 정식 측정의 안정성을 우선해 사용하지 않는다.

## 4. 네트워크 설계

### 4.1 기존 경로 재사용

k6 VM을 기존 `cloudrun` subnet에 둔다. 이 subnet에서 다음 경로는 이미 허용돼 있다.

- 검색·배치 임베딩 VM의 TCP 8000
- PostgreSQL VM의 TCP 5432

별도 subnet과 정적 내부 IP는 만들지 않는다. k6 VM은 요청을 보내는 쪽이므로 고정된 내부 IP도 필요 없다.

### 4.2 Cloud NAT 보완

현재 Cloud NAT 대상은 `postgres`와 `embedding` subnet뿐이다. 외부 IP가 없는 k6 VM이 k6 바이너리와 패키지를 내려받으려면 `cloudrun` subnet을 기존 NAT 대상에 추가해야 한다.

이 변경은 기존 NAT 리소스를 재사용하며, 별도 NAT Gateway를 만들지 않는다.

### 4.3 IAP SSH

`load-test` 네트워크 태그를 추가하고 다음 방화벽 규칙을 만든다.

```text
source: 35.235.240.0/20
target tag: load-test
protocol/port: tcp/22
```

VM에는 외부 IP를 붙이지 않고 OS Login을 사용한다. 프로젝트 SSH 키는 차단한다.

## 5. IAM 설계

기존 IAM 모듈에 `load-test` 서비스 계정을 추가한다.

초기 권한:

- `roles/run.invoker`: Search Service
- `roles/run.invoker`: Core API
- `roles/logging.logWriter`
- `roles/monitoring.metricWriter`

초기에는 다음 권한을 주지 않는다.

- Secret Manager 접근
- DB 비밀번호 접근
- Storage 관리자
- 프로젝트 전체 Cloud Run 호출 권한

검색 API의 애플리케이션 인증과 PostgreSQL 직접 테스트의 DB 인증은 시나리오 설계 단계에서 별도로 결정한다.

## 6. Terraform 변경 범위

### 6.1 신규 모듈

```text
infra/terraform/modules/load_test_vm/
├── main.tf
├── variables.tf
├── outputs.tf
└── startup-k6.sh.tftpl
```

모듈 책임:

- Compute Engine VM과 부팅 디스크 생성
- 네트워크·서비스 계정·OS Login 연결
- 기본 상태를 `TERMINATED`로 유지
- `allow_stopping_for_update` 적용
- 멱등한 시작 스크립트 실행
- VM 이름과 내부 IP 출력

### 6.2 기존 파일 수정

| 파일 | 변경 |
|---|---|
| `infra/terraform/modules/network/main.tf` | Cloud NAT에 `cloudrun` subnet 추가, k6 IAP SSH 방화벽 추가 |
| `infra/terraform/modules/network/outputs.tf` | load-test 네트워크 태그 출력 |
| `infra/terraform/modules/iam/main.tf` | `load-test` 서비스 계정과 로깅·모니터링 권한 추가 |
| `infra/terraform/envs/gcp-perf/main.tf` | `load_test_vm` 모듈과 Cloud Run 서비스별 invoker 권한 추가 |
| `infra/terraform/envs/gcp-perf/variables.tf` | 머신 타입·디스크 크기·k6 버전·자동 종료 시간 변수 추가 |
| `infra/terraform/envs/gcp-perf/outputs.tf` | VM 이름·존·내부 IP 출력 |
| `infra/terraform/envs/gcp-perf/terraform.tfvars.example` | 기본값 예시 추가 |

`terraform plan`에서 기존 PostgreSQL·임베딩 VM이나 Cloud Run 서비스 교체가 나오면 적용하지 않고 원인을 먼저 확인한다.

## 7. 시작 스크립트

`startup-k6.sh.tftpl`은 재부팅할 때 반복 실행돼도 같은 결과가 되게 작성한다.

설치 대상:

- k6 `v2.0.0`
- `jq`
- `htop`
- `iftop`
- PostgreSQL client
- Google Cloud Ops Agent

동작:

1. 설치된 k6 버전을 확인한다.
2. 지정 버전과 다를 때만 바이너리와 checksum을 내려받아 검증 후 설치한다.
3. Ops Agent를 시작한다.
4. 기동 후 4시간 뒤 VM을 종료하는 systemd 작업을 등록한다.

테스트 파일과 자격증명은 시작 스크립트에 넣지 않는다.

## 8. 테스트 파일 운용

테스트 파일의 원본은 로컬 저장소에 둔다.

```text
load-tests/k6/
├── smoke.js
├── scenarios/
├── lib/
└── data/
```

VM에서 직접 수정한 파일을 원본으로 사용하지 않는다. 실행 전 IAP SCP로 동기화한다. 이렇게 하면 VM을 파기해도 시나리오가 사라지지 않고, Git SHA로 실행 조건을 추적할 수 있다.

운영 명령은 하나의 스크립트에 하위 명령으로 모은다.

```text
scripts/load-test/runner.sh start
scripts/load-test/runner.sh sync
scripts/load-test/runner.sh smoke
scripts/load-test/runner.sh run <scenario>
scripts/load-test/runner.sh collect
scripts/load-test/runner.sh stop
scripts/load-test/runner.sh status
```

`run`이 실패해도 종료 처리에서 VM 중지를 시도한다. 이 처리와 별개로 VM 내부의 4시간 자동 종료를 비용 안전장치로 둔다.

## 9. 결과 보존

VM 디스크는 실행 중 임시 저장소로만 사용한다.

```text
artifacts/load-tests/<날짜-시각>/<scenario>/
├── metadata.json
├── summary.json
├── raw.json.gz
└── console.log
```

`metadata.json` 기록 항목:

- Git SHA
- k6 버전
- k6 VM 머신 타입
- 대상 URL
- 코퍼스 청크 수
- 부하 종류와 단계
- query set hash
- Fixture·코퍼스 manifest hash
- 대상 서비스의 주요 설정

실행 후 IAP SCP로 로컬에 회수한 다음 VM을 중지한다. 초기 구축에서는 별도 GCS 결과 버킷을 만들지 않는다. 결과 용량이 로컬 관리 범위를 넘을 때 전용 버킷과 보존 주기를 추가한다.

## 10. 검증 계획

### 10.1 정적 검증

1. `terraform fmt -check`
2. `terraform validate`
3. `terraform plan`
4. 계획 결과에서 기존 자원 교체·삭제가 없는지 확인

### 10.2 배포 검증

1. 적용 후 k6 VM이 `TERMINATED`인지 확인
2. VM 시작
3. IAP SSH 접속
4. `k6 version` 확인
5. 시스템 시각과 Ops Agent 상태 확인
6. 검색·배치 임베딩 VM `/health` 호출
7. Search Service·Core API용 ID token 발급과 호출 확인
8. `1 VU / 10초` smoke 실행
9. 결과 파일 회수
10. VM 중지와 4시간 자동 종료 확인

## 11. 부하 발생기 자체 판정 기준

다음 조건을 모두 만족한 실행만 대상 시스템의 결과로 인정한다.

- k6 VM CPU 사용률 80% 미만
- 메모리 사용률 90% 미만
- `dropped_iterations = 0`
- 네트워크 대역폭 포화 없음
- 파일 디스크립터 부족 오류 없음
- VM 재시작·중단 없음

조건을 넘으면 대상 시스템의 병목으로 판정하지 않는다. 먼저 k6 설정과 VU 할당을 확인하고, VM 자원이 원인이면 머신 타입을 `e2-standard-2`로 올려 같은 조건을 다시 실행한다.
