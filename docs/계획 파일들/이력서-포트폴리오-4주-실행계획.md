## 1. 결론

한 달 안에 이력서에 넣을 **정량 사례 2개**를 완성하고 포장한다.

1. **임베딩 자원 경합 해소** — ✅ **1주차 완료(7/28 실측 검증)**. 검색 전용 VM 분리로 영상 임베딩 추론 중 검색 503을 제거했다. 전후 수치는 3절 1주차 참고.
2. **검색 병목 계측·개선** — 지금 구조가 **어디서, 어떻게 무너지는지** 찾고 확인한 병목 중 하나를 고쳐 전후 비교를 만든다. **유력 후보를 미리 적지 않는다** — 7/28 실측에서 LLM이 검색 시간의 96.9%를 차지해 후보 판단이 바뀔 수 있다(7절 8번).

### 상정 규모 체계 폐기 (2026-07-29)

2주차 선행 조건이던 **트래픽 모델·SLO 정의를 폐기했다.** DAU/MAU·피크 동시 비율을 1차 출처로 검증한 결과 "피크 동시 = DAU의 10~15%"에 근거가 없었고(블로그 관행), k6 공식 산식을 적용하면 이 서비스 규모의 실제 동시 검색은 1건 안팎이 나온다. 시스템을 흔들 숫자를 만들려면 가정을 부풀려야 한다.

대신 **결과를 절대 수치 + 그때의 구성으로 보고한다.** 구성 명시가 곧 재현 조건이자 기준점이다.

> "코퍼스 1만 청크 / 검색 임베딩 VM 1대(동시 처리 1) / Cloud Run 3대 / DB 커넥션 풀 기본값 구성에서, 동시 검색 N건부터 DB 커넥션이 동난다"

사용자 수 환산("MAU N명까지 감당")은 양방향 모두 하지 않는다.

### 기준선 수치 정정 (2026-07-28)

작성 시점에 쓴 `검색 20건 중 503 9건`은 임시 `CHUNK_MAX_TOKENS=150` 스트레스 실험 수치였다. 운영 조건은 300단어이므로 **정확한 before는 `검색 8건 중 503 1건`**이다. 이 문서 안의 `9/20` 표기는 모두 정정했다. 이력서·보고서에는 300단어 기준선만 쓴다.

나머지는 전부 자르거나 최소 범위로 줄인다. 세 문서의 공통 결론과 같다:

> 새 기능·새 기술을 더하는 것보다, 같은 조건에서 재현 가능한 전후 수치를 만드는 것이 취업에 유리하다.

**코퍼스 채우는 시간이 글자 수보다 먼저 걸린다 (7/30 정정)**

배포된 `EMBEDDING_BATCH_SIZE`는 **4**다. 앞서 16으로 적었던 건 코드 기본값만 보고 쓴 값이고, Terraform 기본값과 실제 배포값 모두 4다. 7/28의 배치 추론 20.794초는 **청크 4개**를 처리한 시간이라 청크당 약 5초다.

| 코퍼스 | 배치 수 | 추정 소요 |
|---:|---:|---|
| 1천 청크 | 250 | 약 1.4시간 |
| 1만 청크 | 2,500 | 약 14시간 |
| 5만 청크 | 12,500 | 약 72시간 |

배치당 20.794초를 그대로 곱한 추정값이다. **5만 청크는 이 방식으로는 이번 달에 못 만든다.**

**우회 수단이 있다.** 검색 경로에서 벡터 정렬은 exact KNN이라 벡터 내용과 무관하게 건수에만 비례한다. 1024차원 랜덤 단위벡터를 `vector_index_entry`에 직접 넣으면 임베딩 VM을 건너뛸 수 있고, 텍스트는 실제 말뭉치를 쓰므로 FTS 측정도 유효하다. 쿼리 임베딩은 요청당 1건이라 실제로 돌려도 부담이 없다. 쓸 수 없는 건 **ANN 도입 시점 측정**(벡터 분포가 결과를 좌우)과 **색인 경로 측정**(임베딩이 측정 대상 그 자체) 두 경우다.

**멘토가 제시한 대안 방향 (20번째, 이번 달 범위 밖)**

멘토는 VM 2대 고정 대신 **작업 단위를 잘게 쪼개 한 대가 검색·색인을 모두 담당**하는 설계를 제안했다(검색이 오래 대기하지 않을 수준으로). 검색이 많고 색인이 드물면 지금 구조는 VM 한 대가 논다는 지적이다. 통신 횟수 증가로 전체 영상 처리 시간은 느려질 수 있다.

이건 7/20에 설계 확정하고 보류한 **임베딩 우선순위 게이트**와 같은 방향이다. 이번 달에 구현하지 않는다 — #103 VM 분리가 이미 배포돼 있고 before 수치도 그 구성으로 잡았다. 대신 **2주차 "검색만 / 색인만 / 둘 다" 측정이 두 설계(분리 유지 vs 공유+작은 작업 단위)를 비교할 실측 근거를 만든다.** 관측 항목 13·14(CPU 로드율·워커 유휴 시간)가 그 판단 자료다. 결론은 4주차 ADR에 "전환 조건"으로 남긴다.

**관측 인프라 방침 (7/28 결정)**

"절대 안 쓴다"가 아니라 **단계적으로 간다**. 지금 단계에서 외부 인프라 없이 되는 것은 그렇게 하고, 필요해지면 붙인다.

| 단계 | 내용 | 비용 |
|---|---|---|
| **1단계 (이번 달)** | loguru 구조화 로그 + Cloud Monitoring 대시보드·로그 기반 메트릭 + CLI + k6 출력 | 코드 변경 0 |

**1단계로 충분한 근거**: 부하테스트에서 봐야 할 12개 항목을 대조한 결과 전부 기존 로그와 GCP 기본 기능으로 커버된다(2주차 C 표 참고). 자체 프로메테우스 서버를 세울 필요는 없다.

**되돌릴 수 있는 선택이다**: GMP는 기존 Cloud Monitoring 지표를 PromQL로 질의할 수 있고 그라파나도 붙일 수 있다. 1단계 산출물이 2·3단계에서 버려지지 않으므로, 지금 안 쓰는 것이 나중을 막지 않는다.

**도입 트리거 (하나라도 걸리면 2단계 검토)**
1. 로그에 안 남는 런타임 지표(event loop lag, 스레드 큐 길이 등)가 실제 병목으로 지목될 때
2. 서비스가 상시 가동으로 바뀌어 추세 관찰과 알림이 필요해질 때
3. 로그 수집 비용이 메트릭 방식보다 비싸질 때
4. 여러 서비스 지표를 한 질의로 엮어야 해서 PromQL의 유연성이 실제로 필요해질 때

이 판단 과정(12개 항목 대조 + 단계 설계 + 트리거)을 ADR로 남긴다. "안 써봤다"가 아니라 "필요 조건을 정의하고 단계를 설계했다"가 된다.

2. **Fixture 어댑터 2개 + 환경변수 교체** — 색인 부하를 외부 API 비용 없이 걸기 위한 구현. **미해소**
3. **코퍼스 생성 스크립트** — 5만은 글자 수(5,900만 자)보다 **임베딩 시간(약 72시간)이 먼저 걸린다.** 실제 자막 수집으로도 불가하므로 공개 말뭉치 + 합성이 필수이고, 목표 규모는 소요시간을 재고 확정한다. **미해소**

2·3은 **검색 전체 경로·색인 측정의 선행 조건**이고, 컴포넌트 단독 측정(검색 임베딩 VM)에는 필요 없다. 8/5·8/7 측정이 그래서 먼저 진행됐다.

7/28~7/30에 확인한 사실도 측정 설계에 반영돼 있다.

- 검색 응답의 96.9%가 LLM이다. 판정 지표를 retrieval 구간으로 한정하지 않으면 어떤 개선도 숫자에 안 보인다
- 검색 VM도 동시 처리 1이다. 동시 검색을 올리면 여기서 먼저 무너질 수 있다 (병목 가설표 1번). 산수상 12건이라는 숫자는 **실측이 아니다**
- 두 임베딩 VM이 조정 변수를 공유한다. 검색 쪽만 튜닝하려면 Terraform 변수 분리가 선행된다
- **`containerConcurrency`가 검색·색인 모두 80이다** (7/30 실측). 검색은 3대 × 80 = 요청 240건을 동시에 받는데 DB 커넥션은 45개, 임베딩 동시 처리는 1이다. 앞단에서 거절하지 않고 받아 뒤에서 대기하다 실패하는 구조라 병목 가설표에 넣는다
- **현재 코퍼스가 168건이다.** 지금 상태로 부하를 걸면 DB 쪽은 거의 아무것도 안 하는 셈이라, 코퍼스를 키우기 전 측정은 임베딩·Cloud Run·커넥션 풀 구간 확인용으로만 쓴다

## 7. 주의사항 (세 문서 공통 지침)

1. **before 수치를 고치기 전에 수집한다.** 고치고 나면 "개선 전"은 다시 만들 수 없다. 임베딩 경합은 7/20 실측이 이미 before다. 검색 병목도 2주차 측정값을 확보하기 전에 인덱스를 넣지 않는다.
2. **측정 조건을 수치 옆에 반드시 병기한다.** "10배 빨라짐"이 아니라 "청크 5만 건, e2-standard-4, p95 800ms → 8ms". 조건 없는 수치는 면접에서 역으로 찔린다.
3. **Gemini 시간과 retrieval 시간을 분리한다.** cold/warm도 분리. — 7/28 실측으로 이게 선택이 아니라 필수임이 확인됐다(8번 참고).
4. 측정 결과를 보기 전에 인덱스를 먼저 넣지 않는다. 병목은 하나만 고친다.
5. 검색용 임베딩은 반드시 같은 모델(bge-m3)의 용량 분리다. 다른 모델을 쓰면 벡터 공간이 달라 검색이 깨진다.
6. 과장 금지 목록 준수: "ANN 구현" X (exact), "모든 테스트 자동화" X, "운영 E2E 완주" X (dry-run), "이벤트 드리븐 MSA" X (동기 HTTP + 폴링 큐).
7. 워커 min=0은 의도된 운용. 실험 때만 min=1로 올리고 종료 후 복구. `--min 1`로 올릴 때 리비전이 새로 생기지 않게 주의(7/28 실험 런북 4-3 참고).
8. **검색 지표는 LLM을 뺀 retrieval 구간으로 정의한다 (7/28 추가).** 7/28 실측에서 검색 전체 시간의 96.9%가 LLM이었다(평균 16.4초, 최대 41.2초). 전체 응답시간을 지표로 쓰면 어떤 retrieval 개선도 Gemini 변동에 묻힌다. k6 임계값·전후 비교 모두 retrieval 구간 기준으로 잡는다.
9. **작은 표본에 비율을 붙이지 않는다 (7/28 추가).** 검색 8건으로 "오류율 12.5% → 0%"를 주장하면 표본 수로 찔린다. 표본이 작을 때는 메커니즘과 재현 조건으로 쓰고, 비율·p95는 부하테스트로 표본을 채운 뒤에 붙인다.
10. **측정 전에 가설을 적어둔다 (7/28 추가, 7/29 강화).** 예상이 맞으면 설계 이해의 근거가 되고, 틀리면 그 자체가 더 좋은 보고서 재료가 된다. 즉흥 메모가 아니라 **병목 가설표**(예상 지점 / 근거 / 실패 형태 / 확인 지표 / 대응 후보) 형태로 남긴다. 실행보다 구조 이해가 먼저라는 멘토 지적을 반영한 것이다.
11. **앞단을 임의로 늘려 뒤쪽에 부하를 보내지 않는다 (7/29 추가, 멘토 지적).** 처음부터 의도된 환경을 만들면 "예상 못한 지점에서 부하 확인"과 상반된다. 전체 경로 테스트에서는 **현재 구성에서 처음 막히는 지점까지를 결과로 기록한다.** 뒤쪽 컴포넌트의 한계가 필요하면 같은 배포환경의 해당 컴포넌트에 직접 부하를 주는 **별도 테스트**로 확인하고, 테스트 진입점과 제외한 앞단을 결과에 함께 적는다.
    **앞단을 풀어야만 뒤가 보인다는 것 자체를 아키텍처 문제의 신호로 읽는다.** 멘토 표현으로는 "의미가 없다기보다 굳이 그렇게 할 이유가 없고, 그렇게 해야 테스트가 된다는 것 자체가 아키텍처에 문제가 있다는 신호"다. 그래서 이 관찰은 버리는 게 아니라 결과로 남기고, 개선안 후보도 "동시 처리 수를 올린다" 하나로 좁히지 않는다.
12. **컴포넌트 단위로 나눠 잰다 (7/29 추가, 멘토 지적).** 배포환경에서 서비스 전체를 한 번에 재는 건 빈도가 낮고 귀속도 애매하다. 개별 컴포넌트 측정값은 전체 시스템 처리량이 아니라는 것을 결과에 명시한다.
13. **계산값과 실측값을 구분해 쓴다 (7/29 추가).** "동시 12건에서 503"은 설정값 나눗셈에서 나온 산수이고 실측된 적이 없다. 문서와 보고서에서 산수는 산수로, 실측은 조건과 함께 적는다.
14. **상정 사용자 수를 결론에 쓰지 않는다 (7/29 추가).** "MAU N명까지 감당" 형태의 환산은 양방향 모두 하지 않는다. 결과는 절대 수치 + 그때의 구성으로 보고한다(1절 참고).
