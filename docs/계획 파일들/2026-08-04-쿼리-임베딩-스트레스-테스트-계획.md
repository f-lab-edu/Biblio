# 쿼리 임베딩 VM 스트레스 테스트 계획

- 작성일: 2026-08-04

- 상위 계획: `2026-07-29-검색-부하테스트-계획.md`
- 선행 작업: k6 부하 발생 VM 구축 완료
- 상태: 실행 준비 — 축소 진단 B안 확정

## 1. 목표

배포된 검색 임베딩 VM의 `/embed`를 직접 호출해 현재 구성에서 다음 값을 찾는다.

- 검색 요청을 오류 없이 처리하는 최대 도착률
- 응답 지연이 증가하기 시작하는 구간
- 최초 503 발생 지점과 원인 (`queue_timeout` 또는 `queue_full`)
- 부하 제거 후 자동으로 정상 상태로 돌아오는지
- 부하 발생기와 대상 VM 중 어느 쪽이 먼저 한계에 도달했는지

이 테스트는 검색 시스템 전체 처리량을 재는 테스트가 아니다. Search Service, PostgreSQL 검색, LLM을 건너뛰고 검색 임베딩 VM 한 대의 처리 한계만 측정한다.

측정 결과는 추후 검색과 배치 임베딩을 한 VM에서 처리하는 구조를 검토할 때 검색 전용 기준선으로 재사용한다.

## 2. 범위

### 포함

- k6 VM에서 검색 임베딩 VM의 private endpoint 직접 호출
- 검색 요청과 비슷한 길이 분포를 가진 고정 입력 세트
- 열린 부하 모델을 이용한 단계별 도착률 증가
- HTTP 응답 시간·상태 코드·전송 오류 측정
- 서버의 admission 로그를 이용한 대기 시간과 503 원인 구분
- 대상 VM의 CPU·메모리·네트워크와 재시작 여부 측정
- 각 단계 종료 후 회복 확인
- 1·2·3·4 RPS 초기 진단을 각 1회 실행하고 결과 파일 보존

### 제외

- Search Service API 전체 경로
- PostgreSQL, 코퍼스, 고정 검색 query set
- FixtureSTTAdapter·FixtureVisionAdapter
- 배치 임베딩 부하와 검색·배치 혼합 부하
- 모델 교체와 임베딩 품질 평가
- `MAX_CONCURRENCY`, 요청 수용 상한, 대기 상한 변경
- 장시간 soak test

## 3. 현재 대상과 요청 계약

### 3.1 대상

| 항목 | 현재 값 |
|---|---|
| 대상 | 검색 임베딩 VM 1대 |
| endpoint | Terraform `search_embedding_endpoint_url`의 `/embed` |
| 네트워크 | 외부 IP 없이 k6 VM에서 VPC private IP로 접근 |
| VM 사양 | `e2-standard-4` |
| 모델 | `model_release.active_model_version`과 `/health` ready 목록이 함께 확인한 버전 |
| 동시 추론 수 | `MAX_CONCURRENCY=1` |
| 검색 요청 수용 상한 | `SEARCH_REQUEST_LIMIT=32` |
| 검색 슬롯 대기 상한 | `SEARCH_WAIT_TIMEOUT_SEC=5` |
| 실제 호출자 timeout | Search Service 기준 15초 |

위 값은 실행 직전에 Terraform 출력, VM 환경 설정, ModelRelease SOT, `/health` 응답으로 다시 확인해 `metadata.json`에 기록한다. 코드 기본값과 배포값이 다르면 배포값을 기준으로 한다.

모델 버전은 `/health.ready_model_versions`의 첫 값을 임의로 고르지 않는다. 운영자가 기존의 보호된 DB 조회 경로로 `model_release.active_model_version`을 읽어 runner에 전달하고, 그 버전이 `/health.ready_model_versions`에 포함될 때만 실행한다. runner와 k6 VM에는 이 확인을 위해 DB 자격증명을 부여하지 않는다.

### 3.2 요청

```http
POST /embed
Content-Type: application/json
X-Embedding-Workload: search
X-Trace-Id: loadtest-<run-id>-<iteration>
```

```json
{
  "texts": ["고정 입력 세트에서 선택한 검색 문장 한 개"],
  "model_version": "<ready model version>"
}
```

검색 workload는 요청당 `texts`가 정확히 한 개여야 한다. 모델 버전 누락, 빈 문자열, 여러 문장 전송으로 발생한 400은 시스템 한계가 아니라 시나리오 오류로 처리한다.

### 3.3 응답 분류

| 응답 | 해석 |
|---|---|
| 200 | 임베딩 완료 |
| 400 | 요청 또는 모델 버전 오류. 실행 무효 |
| 503 + `queue_timeout` 로그 | 슬롯을 5초 안에 얻지 못함 |
| 503 + `queue_full` 로그 | 검색 요청 수용 상한 32에 도달함 |
| 연결 실패·client timeout | HTTP 계층 또는 VM 이상. 503과 별도 기록 |

k6의 `http_req_failed` 하나만으로 판정하지 않는다. 스트레스 테스트에서는 503 자체가 찾으려는 결과이므로 상태별 사용자 정의 지표를 따로 기록한다.

## 4. 고정 입력 세트

### 4.1 목적

임베딩 VM 테스트에는 검색 코퍼스가 필요 없다. 입력 문장의 의미보다 길이와 토큰 수가 추론 시간에 미치는 영향이 중요하다.

운영 검색어 원문은 fixture에 복사하지 않는다. 기존 `search_response_snapshot.query_text`에서 다음 분포만 읽고 같은 분포의 합성 한국어 문장을 만든다.

- 문자 수: 최소·p50·p95·최대
- 띄어쓰기 기준 어절 수: p50·p95
- 빈 문자열을 제외한 표본 수

운영 표본이 부족하면 짧음·중간·김 세 구간을 동일 비율로 구성하고, 해당 사실을 manifest에 적는다.

길이 분포 조회는 테스트 데이터 준비 단계에서 운영자가 기존의 보호된 DB 접근 경로로 한 번만 수행한다. 원문과 DB 자격증명은 파일로 내보내지 않으며 k6 VM에는 DB 접근 권한을 추가하지 않는다.

### 4.2 파일

```text
load-tests/k6/data/search-embedding-inputs.json
```

파일에는 다음을 기록한다.

```json
{
  "schema_version": 1,
  "source": "synthetic-length-profile",
  "queries": [
    {"id": "q-001", "text": "합성 검색 문장"}
  ]
}
```

k6는 입력을 실행마다 임의로 바꾸지 않고 고정 순서로 순환한다. 실행 메타데이터에는 파일 SHA-256을 `query_set_hash`로 기록한다.

### 4.3 사전 검증

- 모든 `text`가 비어 있지 않음
- 요청당 텍스트 한 개만 사용
- endpoint의 `MAX_TEXT_LENGTH_CHARS` 이하
- 입력 문자 수·어절 수 분포가 manifest와 일치
- 같은 Git SHA와 파일 hash로 다시 실행할 수 있음

## 5. 부하 모델

### 5.1 열린 모델 사용

`constant-arrival-rate`를 사용한다. 응답이 느려져도 정해진 도착률을 유지해야 대기열 증가와 503 발생 지점을 볼 수 있다.

각 도착률은 별도 run으로 실행한다. 여러 단계를 한 run에 넣으면 앞 단계에서 쌓인 대기 요청이 다음 단계 결과에 섞일 수 있기 때문이다.

### 5.2 초기 탐색

현재 실측된 쿼리 임베딩 약 0.42초와 동시 추론 수 1을 기준으로 다음 값을 초기 탐색값으로 사용한다. 이는 통과 기준이 아니라 시작점이다.

| 단계 | 도착률 | 실행 시간 | 목적 |
|---|---:|---:|---|
| 준비 | 1 RPS | 30초 | 모델·CPU warm-up. 본 결과에서 제외 |
| 1 | 1 RPS | 2분 | 낮은 부하 기준선 |
| 2 | 2 RPS | 2분 | 예상 처리 한계 부근 |
| 3 | 3 RPS | 2분 | 대기 증가와 최초 503 탐색 |
| 4 | 4 RPS | 2분 | 앞 단계가 안정적일 때만 실행 |

초기 진단은 각 도착률을 1회만 실행한다. 최초 503이 확인되면 더 높은 단계로 계속 올리지 않는다. 3 RPS가 안정적이고 대상이 회복된 경우에만 4 RPS를 실행한다.

초기 진단에서는 직전 안정 단계와 최초 실패 단계 사이를 더 좁히거나 같은 조건을 3회 반복하지 않는다. 4 RPS까지 503이 없더라도 자동으로 도착률을 더 높이지 않고, 초기 진단 결과를 확인한 뒤 사용자와 다음 범위를 결정한다.

초기 진단 후 다음 기준으로 후속 작업을 결정한다.

- 503이 발생했고 대상 VM CPU에 여유가 있으면 동시성·스레드 제한을 개선 후보로 검토한다.
- 503이 발생했고 대상 VM CPU가 포화됐다면 현재 VM 처리 한계로 기록하고 코퍼스·PostgreSQL 테스트로 이동한다.
- 4 RPS까지 503이 없으면 최고 무오류 도착률을 `4 RPS 이상`으로 기록하고 추가 탐색 여부를 사용자와 결정한다.
- CPU 상태나 503 원인이 명확하지 않으면 범위를 넓히지 않고 로그와 수집 지표부터 보완한다.

### 5.3 k6 VU 확보

열린 모델에서 VU 부족으로 `dropped_iterations`가 생기면 의도한 부하가 대상에 도달하지 않는다.

`preAllocatedVUs`와 `maxVUs`는 다음 조건을 만족하도록 각 단계의 도착률과 15초 client timeout을 기준으로 계산한다.

```text
필요 VU 하한 = ceil(도착률 × client timeout)
```

여기에 여유분을 두되 실제 값은 단계별 metadata에 기록한다. `dropped_iterations > 0`이면 대상 VM 결과로 사용하지 않고 k6 VU와 부하 발생기 상태를 먼저 조정한다.

## 6. 실행 순서

### 6.1 사전 상태 고정

1. Git SHA와 변경 파일 유무를 기록한다.
2. 배치 임베딩 VM을 중지해 vCPU 할당량과 혼합 부하를 제거한다.
3. 검색 임베딩 VM과 필요한 제어용 DB 상태를 확인한다.
4. k6 VM과 검색 임베딩 VM의 시작 전 상태, 머신 타입·zone·boot ID를 기록한다.
5. 검색 임베딩 VM을 시작하고 `/health`가 200이 될 때까지 기다린다.
6. ModelRelease의 active model version이 `/health.ready_model_versions`에 포함되는지 확인한다.
7. 단일 `/embed` 요청으로 200과 벡터 반환을 확인한다.
8. 최근 endpoint 로그에 다른 검색·배치 요청이 없는지 확인한다.

사전 요청이 실패하면 스트레스 단계를 시작하지 않는다.

### 6.2 코드 동기화와 실행

기존 명령 계약은 유지하되, 실행 제어는 책임별 Python 모듈로 분리한다. `runner.sh`는 기존 호출 방식을 보존하는 얇은 진입점으로만 사용한다.

여러 도착률을 한 세션에서 실행하므로 시작·실행·종료 명령을 분리한다.

```bash
scripts/load-test/runner.sh search-embedding-start --model-version <버전>
scripts/load-test/runner.sh search-embedding-run \
  --rate <요청 수> \
  --time-unit <단위> \
  --duration <시간>
scripts/load-test/runner.sh search-embedding-stop
```

세 명령을 합친 전체 흐름은 다음과 같다.

```text
대상 VM 준비 확인
→ k6 VM 시작
→ 입력·시나리오 동기화
→ 대상 VM 지표 수집 시작
→ k6 실행
→ endpoint 로그와 결과 회수
→ 두 VM의 회복·상태 확인
→ k6 VM 중지
```

`search-embedding-start`는 두 VM의 시작 전 상태를 로컬 상태 파일에 기록한다. 검색 임베딩 VM과 k6 VM은 여러 단계 사이에서 유지해 모델 재로딩과 VM 재시작을 반복하지 않는다.

`search-embedding-stop`은 sampler와 남은 프로세스를 종료하고, 세 VM을 세션 시작 전 상태로 복구한다. 원래 `TERMINATED`였던 VM만 중지하며, 원래 실행 중이던 VM을 임의로 끄지 않는다.

`search-embedding-run`이 실패하면 해당 run의 sampler 종료·결과 회수·회복 확인은 시도하지만, 다음 진단이나 재시도를 위해 VM 세션은 유지한다. sampler 종료를 확인하지 못한 경우에는 `active_run_id`를 상태 파일에 남겨 후속 정리가 대상을 잃지 않게 한다. INT·TERM 신호에는 전체 세션 복구를 시도한다. 터미널 강제 종료나 일반 run 실패 뒤에는 `search-embedding-stop`을 독립적으로 실행해 세션을 끝낸다.

### 6.3 단계 사이 회복

각 run이 끝나면 다음 조건을 확인한 뒤 다음 단계로 간다.

- `/health` 200
- 단일 probe `/embed` 200
- 서버 로그의 검색 대기열이 비어 있음
- 대상 VM CPU가 유휴 수준으로 하락
- 컨테이너와 VM의 boot ID가 실행 전과 같음

회복되지 않으면 다음 단계를 실행하지 않고 해당 run의 실패 형태로 기록한다.

## 7. 관측 항목

### 7.1 k6에서 측정

- 전체 요청 수와 실제 도착률
- 200 수·비율
- 503 수·비율
- 예상하지 않은 4xx·5xx
- 연결 실패와 client timeout
- 전체 요청 p50·p95·p99
- 200 응답만의 p50·p95·p99
- `dropped_iterations`

503이 빠르게 반환되면 전체 `http_req_duration`이 오히려 낮아질 수 있다. 따라서 성공 응답만 따로 담는 Trend를 추가하고, 전체 응답 시간만으로 성능이 좋아졌다고 해석하지 않는다.

### 7.2 endpoint 로그에서 측정

`embedding.admission` 로그를 `X-Trace-Id`의 run ID로 필터링한다. 각 run 시작·종료 UTC 시각과 컨테이너 ID를 먼저 기록하고, target을 중지하기 전에 `docker logs`에서 해당 시간 구간을 가져온 뒤 trace ID를 다시 대조한다.

- `admission_result`: `granted`, `queue_timeout`, `queue_full`
- `queue_wait_ms`
- `inference_duration_ms`
- `search_queue_depth`
- `batch_size`
- `max_text_chars`
- `model_version`

client p95 증가가 실제 추론 시간 증가인지, 슬롯 대기 증가인지 이 로그로 구분한다.

같은 시간 구간에 run ID가 다른 `search` 요청이나 `video_preprocess` 요청이 있으면 그 수를 metadata에 기록하고 해당 run을 혼합 부하로 보아 기준선에서 제외한다.

### 7.3 대상 VM에서 측정

현재 검색 임베딩 VM에는 Ops Agent가 설치되어 있지 않으므로 메모리를 Cloud Monitoring만으로 판정하지 않는다. 테스트 동안 IAP SSH의 단일 sampler로 다음 값을 1초 간격으로 수집한다. sampler는 각 run 시작 전에 target boot ID와 UTC 시각을 기록한 뒤 시작하고, 마지막 회복 probe가 끝난 뒤 종료한다.

- VM CPU
- 메모리 사용률
- 네트워크 bytes/s
- 컨테이너 실행 상태
- VM boot ID
- 파일 디스크립터 오류와 OOM 흔적

sampler가 대상 VM 성능에 영향을 주는지 1 RPS 기준선에서 sampler 사용 전후를 한 번 비교한다. 차이가 측정 잡음보다 크면 수집 간격을 늘리고 그 값을 기록한다.

## 8. 판정

### 8.1 run 유효성

다음을 모두 만족한 run만 대상 VM 결과로 사용한다.

- k6 runner의 기존 acceptance 통과
- `dropped_iterations = 0`
- 예상하지 않은 400 응답 없음
- 사용한 모델 버전이 run 시작과 종료 시 동일
- 대상 VM과 컨테이너 재시작 없음
- 대상 지표와 endpoint 로그 회수 완료
- 다른 workload 요청이 섞이지 않음

### 8.2 결과 정의

| 결과 | 정의 |
|---|---|
| 낮은 부하 기준선 | 1 RPS에서 얻은 성공 응답 지연과 추론 시간 |
| 최고 무오류 도착률 | 초기 진단 범위에서 503·전송 오류 없이 완료한 가장 높은 단계. 4 RPS까지 안정적이면 `4 RPS 이상`으로 기록 |
| 지연 증가 구간 | 성공 응답 p95와 `queue_wait_ms`가 직전 단계보다 뚜렷하게 증가한 구간. 수치와 원자료를 함께 기록 |
| 최초 실패 구간 | `queue_timeout` 또는 `queue_full`이 처음 재현된 단계 |
| 회복 여부 | 부하 제거 후 health와 probe 요청이 정상화됐는지 |

현재 계획에는 임의의 서비스 SLO를 새로 만들지 않는다. 상위 계획의 retrieval p95 1초는 참고선으로만 표시하고, 이번 개별 컴포넌트 테스트의 합격 기준으로 사용하지 않는다.

초기 진단은 단계마다 1회만 실행하므로 측정값을 확정된 처리 한계로 표현하지 않는다. 반복 측정을 별도로 결정한 경우 경계가 run마다 다르면 하나의 숫자로 확정하지 않고 범위로 보고한다.

### 8.3 중단 조건

- 사전 검증 실패
- 예상하지 않은 400 또는 잘못된 모델 버전
- k6 runner 자체 병목
- 대상 VM·컨테이너 재시작 또는 health 실패
- 결과·로그 수집 실패
- 최초 503을 재현한 뒤에도 더 높은 단계로 진행하려는 경우

중단 후에도 결과 회수와 VM 종료를 시도한다.

## 10. 구현 순서

1. 기존 검색 query 길이 분포를 원문 없이 집계한다.
2. 고정 합성 입력 세트와 hash 생성 규칙을 작성한다.
3. `search-embedding.js`에 요청 계약과 상태별 지표를 구현한다.
4. 기존 명령 계약을 유지하는 Python 실행기에 검색 임베딩 target 조회·준비·정리 흐름을 구현한다.
5. 대상 VM sampler와 endpoint 로그 회수를 추가한다.
6. 정적 검사와 잘못된 요청·모델 버전 실패 경로를 검증한다.
7. 1 RPS warm-up과 기준선을 실행한다.
8. 1·2·3·4 RPS를 단계마다 1회 실행하되 최초 503에서 중단한다.
9. 부하 제거 후 회복과 두 VM 종료를 확인한다.
10. 503 원인과 대상 VM CPU 상태를 대조해 개선 실험·다음 컴포넌트 테스트·추가 탐색 중 하나를 사용자와 결정한다.

## 12. 후속 테스트와의 관계

이 시나리오와 입력 세트는 다음 비교에서 그대로 재사용한다.

1. 현재 검색 전용 VM의 검색-only 기준선
2. 검색·배치 공유 VM의 검색-only 기준선
3. 공유 VM에서 배치 실행 중 검색 부하
4. 검색 우선순위 또는 슬롯 예약 적용 후 재측정

각 비교에서는 모델, 입력 hash, 도착률, 실행 시간, VM 사양을 동일하게 유지한다. VM 사양을 바꾸면 코드·정책 개선과 자원 증가 효과를 분리해 보고한다.
