# 영상 파이프라인 리팩토링 구현 절차

- 기준 설계: `2026-08-17-영상-파이프라인-작업단위-리팩토링-설계.md`
- 목적: 에이전트가 한 번에 전체를 수정하지 않고, 검증 가능한 단위로 구현·검토·수정한다.

## 1. 공통 진행 규칙

각 단계는 다음 순서로 진행한다.

```text
구현 요청
  → 관련 테스트 실행
  → 해당 단계 코드 리뷰
  → finding 수정
  → 테스트와 재검토
  → 통과한 경우에만 다음 단계
```

모든 구현 요청에 다음 조건을 포함한다.

- 기준 설계 문서를 먼저 읽는다.
- codebase-memory-mcp로 현재 구현과 호출 관계를 확인한다.
- 같은 책임의 기존 코드가 있으면 새로 복사하지 않고 재사용하거나 일관되게 확장한다.
- Python·FastAPI·테스트를 수정하면 `docs/prompts/python_fastapi_sonar_rules.md`를 따른다.
- 사용자 작업을 덮어쓰거나 관련 없는 코드를 수정하지 않는다.
- 관련 테스트와 `git diff --check`를 실행한다.
- 변경 파일, 테스트 결과, 남은 위험을 보고한다.
- 구현 중 미결정 사항이 나오면 현재 코드와 설계 원칙을 근거로 권장안을 선택해 진행한다.
- 선택한 결정은 기준 설계 문서의 `결정 기록`에 `결정 내용`, `근거`, `영향`, `적용 단계`로 남긴다.
- 권장안을 선택하면 작업 범위나 외부 시스템의 권한이 크게 달라지는 경우에만 사용자에게 확인한다.
- 이번 단계 범위만 구현하고 다음 단계는 시작하지 않는다.

삭제 처리는 모든 단계에서 지켜야 하는 공통 계약이다.

- `video.status = DELETING` 이후에는 새 작업을 배정·발행하지 않는다.
- 안전하게 중단할 수 없는 외부 호출은 반환까지 기다리되, 반환 직후 삭제 상태를 다시 확인한다.
- 삭제 중이면 결과를 저장하거나 다음 단계로 넘기지 않고 이번 실행이 만든 로컬·GCS 산출물을 지운다.
- 작업 중인 영상 삭제와 프로젝트 삭제는 기존 `DeleteVideoUseCase` 정리 경로를 재사용한다.
- 프로젝트는 소속 영상이 모두 삭제된 뒤 삭제한다.
- 늦은 메시지는 외부 호출 없이 ack하고, 여러 영상 embedding batch에서는 삭제 영상 결과만 폐기한다.

리뷰 결과는 심각도 순서로 보고한다. finding이 있으면 확인된 문제만 수정하고 같은 검증을 다시 실행한다. 다음 조건을 모두 만족해야 다음 단계로 넘어간다.

- 현재 단계의 기능 테스트가 통과한다.
- 해결되지 않은 높은 우선순위 finding이 없다.
- 이번 단계에서 추가되거나 변경된 DB·메시지·상태 계약과 결정 근거가 기록됐다.
- 임시 중복 구현이 있다면 제거 시점이 명시됐다.

## 2. 1단계: DB migration과 repository

### 구현 요청문

```text
설계 문서를 기준으로 신규 작업 상태 테이블과 repository를 구현해줘.

이번 작업 범위:
- pipeline_run
- pipeline_audio_part
- pipeline_chunk_work
- pipeline_embedding_batch
- pipeline_stage_schedule
- migration, model, repository와 관련 테스트

반드시 포함할 것:
- 영상의 현재 활성 pipeline run 구분
- pipeline_run.total_part_count
- pipeline_audio_part의 pipeline_run_id와 part_index
- pipeline_chunk_work의 pipeline_run_id와 chunk_index
- 설계 문서의 중복 방지 제약
- 작업 상태, 시도 횟수, message id, 결과 참조와 상태 시각
- 이전 run과 현재 run을 구분하는 조회
- run과 작업 상태의 CANCELLED 전환
- 영상별 RUNNING 작업 수 조회와 삭제 대기 판정
- READY·DISPATCHED 작업을 한 번에 CANCELLED로 바꾸는 API

아직 Queue consumer, STT, Vision, embedding은 구현하지 마라.
이번 단계 범위만 구현하고 다음 단계는 시작하지 마라.
```

### 리뷰 중점

- 중복 방지 제약이 충분한가
- 잘못된 상태 전환을 허용하는가
- 이전 run의 데이터와 현재 run이 섞일 수 있는가
- message id와 시도 횟수 갱신이 안전한가
- 실제 작업 행과 `pipeline_run` 상태가 어긋날 수 있는가
- CANCELLED 작업이 재배정·복구·완료 집계에 포함될 수 있는가
- 영상 삭제 시 RUNNING 작업과 기다리지 않아도 되는 DISPATCHED 작업을 구분하는가
- migration 적용과 rollback이 안전한가
- 기존 repository와 책임이 중복되는가

### 통과 조건

- repository 통합 테스트가 통과한다.
- 중복 insert와 잘못된 상태 변경이 차단된다.
- 이후 단계가 사용할 조회·상태 변경 API가 확정됐다.

## 3. 2단계: Queue 메시지와 작업 배정기

### 구현 요청문

```text
신규 작업 상태 테이블을 사용해 Queue 메시지 schema와 작업 배정기를 구현해줘.

이번 작업 범위:
- NORMALIZE_VIDEO, TRANSCRIBE_PART, ENRICH_CHUNK, EMBED_BATCH 메시지 schema
- READY 작업 선택
- 영상별 순환 배정
- stage별 실행 상한
- advisory lock
- READY에서 DISPATCHED로 변경하고 PGMQ에 발행
- DB 상태 변경과 Queue 발행의 원자성
- message id와 상태를 이용한 오래된·중복 메시지 검사
- 테스트용 가짜 handler와 관련 테스트

테스트는 외부 STT, Vision, embedding API 호출 없이 진행
로직 자체는 gcp 배포환경에서 외부 인프라 밑 vm 호출 상황에 맞게

검증할 상황:
- 영상 A의 작업이 많아도 영상 B가 다음 빈 슬롯을 받는다.
- 영상이 하나뿐이면 해당 영상이 빈 슬롯을 모두 사용한다.
- 동시 배정에도 실행 상한을 넘지 않는다.
- 같은 작업이 두 번 발행되지 않는다.
- 오래된 메시지와 완료된 작업의 재전달은 실행되지 않는다.
- DELETING 영상의 READY·DISPATCHED 작업은 CANCELLED가 되고 새 메시지가 발행되지 않는다.

이번 단계 범위만 구현하고 실제 stage 로직은 시작하지 마라.
```

### 리뷰 중점

- 영상별 배정이 공정한가
- 동시 호출에서 실행 상한을 지키는가
- DB commit과 Queue 발행 사이에 작업을 잃을 틈이 있는가
- advisory lock의 범위가 적절한가
- 중복 메시지와 발행 실패를 복구할 수 있는가
- 삭제 fence 확인과 READY 선택 사이의 경쟁으로 삭제 영상 작업이 발행될 수 있는가

### 통과 조건

- 여러 영상의 배정 순서 테스트가 통과한다.
- 동시 배정·중복 메시지·Worker 종료 복구 테스트가 통과한다.

## 4. 3단계: `NORMALIZE_VIDEO`

### 구현 요청문

```text
NORMALIZE_VIDEO stage만 구현해줘.

이번 작업 범위:
- generation에 고정된 짧은 수명의 GCS V4 signed URL을 ffprobe·ffmpeg HTTP 입력으로 전달
- 원본 전체를 Worker 메모리나 로컬 파일에 저장하지 않고 FLAC part는 HTTP Range로 탐색
- 15분 + 5초 overlap FLAC part 생성
- part별 GCS 업로드와 pipeline_audio_part 생성
- 완료된 part를 READY로 바꾸고 STT 작업 배정기 호출
- 후보 JPEG 생성과 metadata 저장
- normalization 완료 시 total_part_count 확정
- normalization message id와 상태 변경
- 로컬 임시파일 삭제
- 멱등한 재시도, 로그와 관련 테스트

기존 audio 추출과 ffmpeg 기능을 먼저 찾아 재사용해라.
아직 실제 TRANSCRIBE_PART, ASSEMBLE_CHUNKS, ENRICH_CHUNK,
EMBED_BATCH는 구현하지 마라.

검증할 상황:
- 짧은 영상과 긴 영상의 정확한 part 시간 범위
- 5초 overlap
- 중복 실행과 중간 실패 후 재시도
- GCS 업로드와 DB 기록 순서
- `moov`가 앞과 뒤에 있는 MP4 입력, signed URL 만료·서명 실패, 재시도 중 generation 변경
- signed URL이 DB·Queue·로그·예외에 남지 않음
- 임시파일 정리
- normalization 완료 전에는 total_part_count가 확정되지 않음
- ffmpeg 실행 중 삭제 요청이 오면 반환 후 part·JPEG를 폐기하고 STT를 발행하지 않음

이번 단계 범위만 구현하고 다음 단계는 시작하지 마라.
```

### 리뷰 중점

- 기존 ffmpeg 책임을 중복 구현했는가
- part 추출의 `-ss`가 HTTP 입력 앞에 있어 목표 구간으로 seek하는가
- part가 누락되거나 중복될 수 있는가
- GCS 업로드와 DB 완료 기록 순서가 안전한가
- `total_part_count` 확정 시점이 정확한가
- 실패와 재시도 후 로컬 파일이 남는가
- 삭제 요청 이후 DB·GCS 산출물이나 STT 메시지가 남는가

### 통과 조건

- normalization 단독 통합 테스트가 통과한다.
- 기존과 같은 part 구간과 overlap 결과를 만든다.
- 중복 실행에도 같은 GCS 산출물과 DB 행 하나만 남는다.
- 실행 중 삭제 테스트에서 원본 이외의 normalization 산출물과 후속 메시지가 남지 않는다.
- 원본 전체 파일이 workdir에 만들어지지 않고, generation 변경 재시도는 같은 입력으로 처리되지 않는다.
- 실제 배포 전 staging에서 Worker 서비스 계정의 signed URL 생성과 HTTP Range smoke test가 통과한다.

## 5. 4단계: `TRANSCRIBE_PART`

### 구현 요청문

```text
TRANSCRIBE_PART stage만 구현해줘.

이번 작업 범위:
- pipeline_audio_part에서 입력 조회
- GCS FLAC을 STT에 전달
- 단어, 구두점, 상대 timestamp 저장
- STT 상태, 시도 횟수와 message id 변경
- 같은 part의 완료 결과 재사용
- 이전 run과 오래된 message id 차단
- 완료 후 ASSEMBLE_CHUNKS 호출 경계 연결
- 로그와 관련 테스트

ASSEMBLE_CHUNKS의 실제 조립 로직은 아직 구현하지 마라.

검증할 상황:
- 같은 part 메시지 재전달
- part 완료 순서가 뒤섞임
- retryable 실패와 최종 실패
- STT 성공 후 DB 저장 전에 Worker가 종료되는 경우
- 삭제 요청 중 외부 결과가 반환되는 경우
- STT 반환 결과와 part GCS 산출물을 폐기하고 ASSEMBLE_CHUNKS를 발행하지 않는 경우

이번 단계 범위만 구현하고 다음 단계는 시작하지 마라.
```

### 리뷰 중점

- STT 재호출을 막을 수 있는 범위가 명확한가
- 외부 호출과 DB transaction 경계가 안전한가
- 완료 결과가 재시도에 충분한 형태로 저장되는가
- 이전 run과 삭제된 영상의 결과를 폐기하는가

### 통과 조건

- 실패한 part만 재시도된다.
- 완료된 part의 재전달은 STT를 다시 호출하지 않는다.
- part 완료 순서와 관계없이 결과가 보존된다.
- 실행 중 삭제된 영상에는 STT 결과와 후속 메시지가 남지 않는다.

## 6. 5단계: `ASSEMBLE_CHUNKS`

이 단계는 순서·중복 제거·중간 상태 복구를 함께 다루므로 다른 stage와 합치지 않는다.

### 구현 요청문

```text
ASSEMBLE_CHUNKS만 구현해줘.

이번 작업 범위:
- 영상별 조립 상태 잠금
- next_part_index부터 연속 완료된 part 처리
- 상대 timestamp를 영상 전체 timestamp로 변경
- 5초 overlap의 중복 단어 제거
- pending_words 연결과 문장 경계 확정
- 구두점 없는 100단어 문장 종료
- 최대 300단어 chunk 생성과 마지막 문장 하나 overlap
- pipeline_chunk_work 저장
- 마지막 part의 pending_words flush
- 조립 완료 상태 기록
- Worker 종료 후 조립 재개
- 로그와 관련 테스트

기존 transcript 병합과 chunking 결과를 기준으로 비교해라.
ENRICH_CHUNK는 호출하지 말고 pipeline_chunk_work를 READY 또는
WAITING_FRAME으로 만드는 것까지만 구현해라.

검증할 상황:
- part 완료 순서 0 → 2 → 1
- overlap 단어 중복 제거
- part 사이에서 이어지는 미완성 문장
- 100단어 강제 종료와 300단어 chunk 상한
- 문장 하나 overlap
- 마지막 작은 chunk flush
- 조립 중 Worker 종료와 재개
- 같은 part와 chunk의 중복 조립 방지
- 조립 transaction과 삭제 요청이 겹쳐도 chunk와 후속 작업이 남지 않음

이번 단계 범위만 구현하고 다음 단계는 시작하지 마라.
```

### 리뷰 중점

- 기존 병합·청킹 결과와 같은가
- DB 잠금 범위가 너무 넓거나 좁지 않은가
- `next_part_index`가 결과 저장보다 먼저 전진할 수 있는가
- 같은 chunk가 중복 생성될 수 있는가
- 마지막 flush가 정확히 한 번 실행되는가
- 삭제 fence를 잠근 상태에서 확인해 조립 결과 저장과 삭제가 엇갈리지 않는가

### 통과 조건

- 기존 transcript·chunk 비교 테스트가 통과한다.
- 순서 뒤섞임, 중복 실행, 중간 종료와 재개 테스트가 통과한다.
- 높은 우선순위 리뷰 finding이 남아 있지 않다.

## 7. 6단계: `ENRICH_CHUNK`

### 구현 요청문

```text
ENRICH_CHUNK stage만 구현해줘.

이번 작업 범위:
- pipeline_chunk_work 조회
- chunk 시간 범위에 맞는 후보 JPEG 선택
- GCS JPEG 다운로드
- 기존 KEYFRAME asset 생성 또는 재사용
- Vision caption, OCR, scene tag 생성
- transcript와 합쳐 enriched_text 생성
- 기존 chunk 테이블에 결과 저장
- enrichment 상태, 시도 횟수와 message id 변경
- embedding 상태를 READY로 변경하고 배정기 호출
- 로컬 JPEG 삭제
- 로그와 관련 테스트

EMBED_BATCH의 실제 embedding 호출은 구현하지 마라.
기존처럼 원본 영상에서 keyframe을 다시 추출하지 마라.

검증할 상황:
- 중복 메시지와 오래된 message id
- 기존 완료 결과 재사용
- WAITING_FRAME에서 READY 전환
- Vision 실패와 재시도
- 삭제 요청
- 임시 JPEG 삭제
- Vision 반환 결과, KEYFRAME·chunk 저장과 EMBED_BATCH 발행을 모두 폐기하는 경우

이번 단계 범위만 구현하고 다음 단계는 시작하지 마라.
```

### 리뷰 중점

- Vision을 불필요하게 중복 호출하는 구간이 있는가
- KEYFRAME이 중복 생성될 수 있는가
- 후보 JPEG 선택 규칙을 지키는가
- `pipeline_chunk_work`와 기존 `chunk`의 책임이 분리됐는가
- 실패 후 로컬 파일을 정리하는가
- 삭제 중 Vision 결과와 GCS·DB 산출물이 남는가

### 통과 조건

- 성공·재시도·최종 실패 테스트가 통과한다.
- 동일 chunk의 결과를 중복 저장하지 않는다.
- 후보 JPEG를 재사용하고 원본 영상 keyframe을 다시 추출하지 않는다.

## 8. 7단계: `EMBED_BATCH`와 영상 완료 판정

### 구현 요청문

```text
EMBED_BATCH와 영상 완료 판정만 구현해줘.

이번 작업 범위:
- 호환되는 READY chunk를 영상별로 순환 선택
- 기존 batch size 이내로 batch 구성
- pipeline_embedding_batch 저장
- embedding endpoint 호출
- 응답과 chunk 순서 검증
- chunk별 vector 저장과 embedding 완료 상태 변경
- 같은 model version과 index의 vector 중복 방지
- 참여 영상의 최종 완료 조건 확인
- 조건 충족 시 video를 READY로 변경
- 로그와 관련 테스트

영상 완료 조건:
- normalization 완료
- 모든 part STT 완료
- 모든 part가 조립 상태에 반영됨
- pending_words flush 완료
- 모든 pipeline_chunk_work enrichment 완료
- 모든 chunk에 현재 model과 index의 vector가 존재
- 삭제 요청과 최종 실패가 없음
- 현재 활성 pipeline_run만 상태를 변경할 수 있음

삭제 계약:
- embedding 호출 전과 반환 후 삭제 상태 확인
- 여러 영상 batch에서 삭제 영상 vector만 폐기
- 삭제 영상의 완료 판정과 후속 batch 발행 금지

이번 단계만 구현하고 consumer 전환이나 기존 경로 제거는 하지 마라.
```

### 리뷰 중점

- 한 영상의 chunk가 batch를 독점하는가
- model version과 index가 다른 chunk가 섞이는가
- 응답 순서와 chunk 대응이 정확한가
- vector가 중복 저장될 수 있는가
- 일부 작업만 끝났는데 video가 READY가 될 수 있는가
- 이전 run이 현재 video 상태를 변경할 수 있는가
- 일부 영상 삭제가 같은 batch의 정상 영상 결과까지 폐기하는가

### 통과 조건

- 전체 완료 조건을 모두 만족할 때만 video가 READY가 된다.
- 누락·실패·삭제·이전 run 상태에서는 READY가 되지 않는다.
- 여러 영상의 embedding batch 순환 선택 테스트가 통과한다.
- embedding 실행 중 영상 하나를 삭제하는 혼합 batch 테스트가 통과한다.

## 9. 8단계: consumer 전환과 기존 경로 제거

### 구현 요청문

```text
검증된 stage들을 실제 Queue consumer에 연결하고 기존 영상 단위 경로를 제거해줘.

이번 작업 범위:
- 네 Queue의 독립 consumer loop
- stage별 동시 실행 제한
- 정상 종료 처리
- DISPATCHED 메시지 복구
- 삭제 요청 처리
- video.status를 DELETING으로 사용하는 삭제 fence
- READY·DISPATCHED 작업 CANCELLED 처리와 늦은 메시지 ack
- RUNNING 작업이 0개가 될 때까지 삭제 메시지 재시도
- 반환 결과와 로컬·GCS 산출물 폐기
- 기존 DeleteVideoUseCase를 통한 원본·중간·최종 산출물 및 영상 삭제
- 프로젝트의 모든 영상을 한 transaction에서 DELETING으로 전환하고 같은 영상 삭제 경로로 정리
- 모든 영상 삭제 후 프로젝트 삭제
- PREPROCESS_REQUEST를 NORMALIZE_VIDEO 시작점으로 전환
- 기존 PipelineOrchestrator.run의 중복 책임 제거
- 사용하지 않는 기존 코드와 설정 제거
- 전체 통합 테스트

새 경로와 기존 경로에 같은 책임을 남기지 마라.
삭제 전에 호출 경로와 테스트 참조를 확인하라.
이 단계에서는 기능 전환까지만 하고 성능 설정은 임의로 조정하지 마라.
```

### 리뷰 중점

- 기존 경로가 실제 호출 경로에서 제거됐는가
- consumer loop가 서로 독립적으로 진행되는가
- 정상 종료 중 메시지를 잃을 수 있는가
- 복구 작업이 정상 실행 중인 작업을 되돌릴 수 있는가
- 삭제 요청 후 후속 작업이 발행될 수 있는가
- 취소할 수 없는 작업의 반환 결과와 GCS 산출물이 남을 수 있는가
- 실행 중 작업이 남았는데 영상·프로젝트를 먼저 삭제할 수 있는가
- 프로젝트 삭제가 작업 중인 영상을 빠뜨리거나 영상 삭제 책임을 중복 구현하는가
- 늦게 도착한 메시지가 삭제된 영상의 외부 API를 호출할 수 있는가
- 사용하지 않는 설정·adapter·테스트가 남아 있는가

### 통과 조건

- 전체 통합 테스트가 통과한다.
- Worker 재시작 후 미완료 작업이 복구된다.
- 기존 영상 단위 처리 경로와 중복 책임이 제거됐다.
- 각 stage 실행 중 영상 삭제 테스트에서 실행 중 호출만 끝까지 수행되고 결과와 후속 메시지는 남지 않는다.
- 프로젝트 삭제가 처리 상태와 관계없이 모든 영상을 정리한 뒤 완료된다.

## 10. 9단계: 부하 테스트와 최종 리뷰

### 검증 요청문

```text
새 영상 파이프라인의 기능·성능 검증을 실행해줘.

검증 범위:
- 기존 S1~S4 조건 재현
- long 영상 뒤 short 영상의 첫 슬롯 대기와 완료시간
- stage별 READY 대기, Queue 대기와 실제 실행시간
- Worker와 embedding VM의 CPU·메모리
- 로컬 임시파일 최대 크기
- 재시도와 중복 처리 횟수
- 여러 stage의 병렬 timeline
- 기존 결과와 transcript·chunk 결과 비교

성능 결과만 보고 설정을 임의로 변경하지 마라.
측정값, 확인된 원인, 가능한 원인 후보를 구분해서 보고하라.
```

### 최종 리뷰 요청문

```text
영상 파이프라인 작업 단위 리팩토링 전체 변경을 최종 리뷰해줘.

중점 확인:
- 데이터 무결성
- 중복 외부 호출
- Queue와 DB 원자성
- Worker 종료와 복구
- 이전 run 메시지
- 삭제 요청
- stage별 실행 중 영상 삭제와 프로젝트 삭제
- 삭제 뒤 늦게 도착한 Queue 메시지
- 여러 영상 embedding batch 중 일부 영상 삭제
- 동시성 상한과 영상별 공정성
- CPU·메모리·임시파일 사용량
- 기존 책임의 중복 또는 미사용 코드
- 테스트에서 빠진 실패 경로

코드는 수정하지 말고 finding을 심각도 순으로 보고해줘.
```

### 최종 통과 조건

- 기능 결과가 기존과 같다.
- long 영상 뒤 short 영상의 대기가 줄었다.
- 자원 초과나 새로운 병목이 없다.
- 실패·삭제·중복·재시작 경로가 검증됐다.
- 삭제 후 원본·중간·최종 GCS 산출물, 결과 행, pipeline 작업 상태와 후속 메시지가 남지 않는다.
- 기존 처리 경로와 임시 adapter가 제거됐다.
- 해결되지 않은 높은 우선순위 finding이 없다.

## 11. 단계별 작업 관리

각 단계는 가능하면 별도 커밋 또는 PR로 분리한다. 커밋이나 PR 설명에는 다음 내용을 남긴다.

```text
구현 범위:
의도적으로 제외한 범위:
상태·메시지 계약 변경:
작업 중 결정한 내용·근거·영향:
실행한 테스트:
리뷰 finding과 수정 결과:
다음 단계의 시작 조건:
```

특히 `NORMALIZE_VIDEO`, `TRANSCRIBE_PART`, `ASSEMBLE_CHUNKS`, `ENRICH_CHUNK`, `EMBED_BATCH`는 각각 독립된 구현·리뷰 단위로 유지한다.
