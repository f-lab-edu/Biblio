## 1. 목표

**지금 구조가 어디서, 어떻게 무너지는지 찾는다.**

현재 설계에 맞게 상정한 수준의 환경에서 테스트 → 스트레스 테스트를 통한 병목지점으로 초점을 옮겼음.

### 실행 전 사전 분석

테스트를 실행하기 전에 현재 구조에서 예상 가능한 병목을 먼저 정리한다. 목적은 결과를 미리 단정하는 것이 아니라, **각 컴포넌트의 역할과 부하가 흐르는 경로를 이해하고 실측 결과와 비교할 기준을 만드는 것**이다.

| 산출물 | 확인할 내용 |
|---|---|
| Deployment Diagram | 검색·색인 요청 경로, 인스턴스 역할과 대수, 동시 처리 상한, 공유 PostgreSQL과 외부 서비스 |
| 검색·색인 Value Stream Map | 단계별 처리 시간과 대기 시간, 아직 실측하지 못한 구간 |
| 병목 가설표 | 예상 지점, 예상 근거, 실패 형태, 확인 지표, 대응 후보 |

가설과 다른 결과도 실패가 아니라 산출물이다. 5장의 `예상과 달랐던 것`은 이 사전 분석을 기준으로 작성한다.

### 앞의 병목이 뒤를 가린다

검색 임베딩 VM의 동시 처리 수가 1이고, 대기 상한이 5초, 쿼리 추론이 약 0.42초다. 산수로는 동시 12건쯤부터 503이 날 것으로 보이나 **아직 재보지 않았다.** 실제로 잰 503은 7/20의 검색 8건 중 1건이고, 그때는 검색과 색인이 임베딩 VM을 같이 쓰던 조건이라 지금과 다르다.

어느 숫자든 그 지점을 넘긴 요청은 임베딩 앞에서 잘려 DB까지 가지 못한다.

```
검색 요청 → [임베딩 동시 처리 1] → DB 커넥션 → PostgreSQL → 벡터 검색
              ↑ 여기서 다 막힘        ↑ ──── 부하가 도달한 적 없음 ────↑
```

뒤쪽 구간은 부하를 받아본 적이 없어서 상태를 모른다. 전체 경로 테스트에서는 **현재 구성에서 처음 막히는 지점까지를 결과로 기록한다.** 뒤쪽 컴포넌트의 한계가 필요하면 앞단 인스턴스 수나 동시성을 임의로 늘리지 않고, 같은 배포환경에서 해당 컴포넌트에 직접 부하를 주는 별도 테스트로 확인한다(4장).

## 2. 측정 조건

### 2.1 측정 기준

상정 사용자 수를 정하지 않는다. **결과는 절대 수치와 그때의 구성으로 보고한다.**

```
"코퍼스 1만 청크 / 검색 임베딩 VM 1대(동시 처리 1) / Cloud Run 3대 /
 DB 커넥션 풀 기본값 구성에서, 동시 검색 N건부터 DB 커넥션이 동난다"
```

구성을 명시하면 그 자체가 재현 조건이자 기준점이 된다. 사용자 수 환산은 하지 않는다 — 정직하게 계산하면 이 서비스의 현실적 규모에서는 동시 요청이 1건 안팎이라, 시스템을 흔들 만한 숫자를 만들려면 가정을 부풀려야 한다.

### 2.2 부하를 세 가지로 나눠 건다

검색과 영상 색인은 쓰는 자원이 다르다.

| 워크로드 | 특성 | 쓰는 자원 |
|---|---|---|
| 검색 | 짧음(쿼리 임베딩 약 0.42초), 사용자가 기다림 | **검색** 임베딩 VM, PostgreSQL(읽기), Gemini |
| 영상 색인 | 김(1건당 약 120초), 백그라운드 | **배치** 임베딩 VM, PostgreSQL(쓰기), STT, Vision |

#103에서 임베딩 VM을 분리해 둘의 추론 경합은 사라졌다. **PostgreSQL은 여전히 1대를 공유한다.** 그래서 둘을 항상 같이 돌리지 않고 **따로 돌린 경우와 같이 돌린 경우를 나눠서 잰다.**

| 부하 | 드러나는 것 |
|---|---|
| **검색만** | 검색 쪽의 순수 한계 (검색 임베딩 VM, Cloud Run, DB 읽기) |
| **색인만** | 색인 쪽의 순수 한계 (배치 임베딩 VM, 워커, DB 쓰기) |
| **둘 다** | 서로 방해하는 정도 |

세 가지를 다 재면 따로 잴 때는 안 보이는 숫자가 나온다.

```
서로 방해해서 잃는 양 = (검색만 한계 + 색인만 한계) − 둘 다 돌렸을 때 한계
```

이게 PostgreSQL 한 대를 같이 써서 잃는 양이다. 검색이 무너질 때 색인까지 같이 망가지는지, 반대도 그런지를 여기서 본다.

셋을 매번 다 돌리면 실행 횟수가 너무 늘어나므로 이렇게 묶는다.

| 언제 | 무엇을 |
|---|---|
| 첫 번째 (기준선) | 세 가지 전부 |
| 그 뒤 | 그때 늘린 설정이 검색 쪽이면 검색만, 색인 쪽이면 색인만 |
| 매번 끝에 | 둘 다 1회 → 방해량이 어떻게 변하는지 |
| 개선 후 | 세 가지 전부 |

색인 부하와 코퍼스는 같은 fixture로 만든다(2.3).

### 2.3 fixture와 코퍼스

#### 용어

| 말 | 뜻 |
|---|---|
| **fixture** | STT·Vision이 뱉은 출력을 저장해둔 데이터 (대본 + 캡션·OCR·태그) |
| **코퍼스** | 그 fixture를 파이프라인에 태워 DB에 쌓인 청크 |
| **fixture 어댑터** | 외부 API를 부르는 대신 저장해둔 fixture를 읽어 돌려주는 어댑터 |

#### 하나의 흐름, 두 가지 쓰임

fixture를 파이프라인에 태우면 **그 실행 자체가 색인 부하**이고, **쌓인 결과가 검색 부하의 조회 대상**이 된다.

```
[fixture] → 청킹 → 임베딩 → DB → [코퍼스]
            └── 이 구간이 색인 부하 ──┘     └ 검색 부하가 여기를 조회 ┘
```

STT·Vision은 3장에서 측정 대상에서 뺀 구간이라, **딱 한 번만 실제로 돌려 결과를 저장하고 그 뒤로는 저장본을 쓴다.**

```
처음 한 번:  실제 영상 → 다운로드 → GoogleSTT → GeminiVision → [fixture 저장]
                                                              ↓
그 뒤로는:   (건너뜀)      FixtureSTT ──── FixtureVision ←────── [읽기]
```

- **저장 지점은 Vision 직후·청킹 직전.** 청킹은 우리 코드라 매번 실제로 돌려야 `CHUNK_MAX_TOKENS`를 바꿔가며 잴 수 있다
- **fixture 어댑터는 지연 없이 바로 반환한다.** STT 대기는 개선 대상이 아니고, 바로 반환해야 부하가 우리 인프라에 몰린다. 대신 Pipeline total은 운영 실측값과 다른 값이 된다

#### 어댑터 교체 지점

| 대상 | 지금 상태 | 할 일 |
|---|---|---|
| Vision | `VisionAdapter`가 Protocol. `MockVisionAdapter`가 그 자리에 꽂히는 걸 이미 증명 | `FixtureVisionAdapter` 작성 (Mock은 고정값 반환이라 그대로 못 씀) |
| STT | `pipeline_orchestrator.py:72`가 구현체 `GoogleSTTAdapter`를 직접 받음. 꽂을 자리가 없음 | **Protocol 추출** 후 `FixtureSTTAdapter` 작성 |
| 선택 | — | `bootstrap.py`에서 환경변수로 실제/fixture 교체 |

#### 얼마나 필요한가

실측 기준값 — 4분 19초 자막에 운영 청킹 로직을 그대로 돌린 결과다.

| 항목 | 값 |
|---|---|
| 어절당 글자 수 | **3.85자** |
| 평균 문장 길이 | 38자 (약 10어절) |
| 청크당 | 300어절 ≈ **1,150~1,200자** |

`CHUNK_MAX_TOKENS`는 실제 토큰이 아니라 **띄어쓰기로 나눈 어절 수**다(`chunking_service.py:76`의 `text.split()`). 생성기도 글자 수가 아니라 어절 수로 맞춘다.

| 코퍼스 | 필요 글자 수 | 영상 환산 |
|---:|---|---|
| 1천 청크 | 약 120만 자 | 약 45시간 |
| 1만 청크 | 약 1,200만 자 | 약 440시간 |
| 5만 청크 | 약 5,900만 자 | 약 2,100시간 |

**출발점 — 현재 코퍼스는 168건이다** (7/30 실측). 검색이 훑는 `vector_index_entry` 기준이고, 그중 운영 인덱스 `vector-bge-m3-base`가 148건(프로젝트 12개)이다. 검색은 프로젝트 단위라 **한 번의 검색이 실제로 훑는 건 가장 큰 프로젝트에서도 58건**이다.

#### 코퍼스를 채우는 데 걸리는 시간

글자 수보다 이쪽이 먼저 걸린다. 배치 크기가 4라서 청크 수에 비례해 임베딩 호출이 늘어난다.

| 코퍼스 | 배치 수 | 추정 소요 |
|---:|---:|---|
| 1천 청크 | 250 | 약 1.4시간 |
| 1만 청크 | 2,500 | 약 14시간 |
| 5만 청크 | 12,500 | 약 72시간 |

배치당 20.794초(7/28 실측, 청크 4개)를 그대로 곱한 **추정값**이다. 텍스트 길이와 캐시 상태에 따라 달라지므로 100청크를 실제로 넣어 재고 환산한 뒤 목표 규모를 확정한다.

**우회 수단 — 벡터를 직접 넣는다.** 검색 경로에서 벡터 정렬은 exact KNN이라 벡터 내용과 무관하게 건수에만 비례한다(아래 "주의 — 주제 다양성" 참고). 1024차원 랜덤 단위벡터를 `vector_index_entry`에 직접 넣으면 임베딩 VM을 건너뛸 수 있고, 텍스트는 실제 말뭉치를 쓰므로 FTS 측정도 유효하다. 쿼리 임베딩은 요청당 1건이라 실제로 돌려도 부담이 없다.

쓸 수 없는 경우는 둘이다. **ANN 도입 시점 측정** — 벡터 분포가 결과를 좌우한다. **색인 경로 측정** — 임베딩이 측정 대상 그 자체다.

#### 어떻게 만드나

실제 영상이나 유튜브 자막 수확으로는 위 분량을 못 채운다. **소수만 실제로 뽑아 문체 기준을 잡고, 분량은 공개 말뭉치로 채운다.**

| 필요한 것 | 조달 |
|---|---|
| 문체 프로파일 (어절 길이, 문장 길이) | 처음 한 번 돌릴 때 실제 자막에서 추출 |
| **`enriched_text` 길이 분포** | 운영 DB에서 조회 (아래 실측값 확보됨) |
| 분량·어휘 | 공개 한국어 말뭉치 |
| 합성 | 말뭉치를 문체 프로파일에 맞춰 재단하고 타임스탬프 부여 |

**Vision 텍스트를 반드시 포함한다.** 임베딩에 들어가는 건 대본이 아니라 `enriched_text`(대본 + 캡션 + OCR + 태그)이므로(`pipeline_orchestrator.py:466`), 대본만 만들면 실제보다 짧은 입력으로 재게 된다.

**`enriched_text` 길이 실측** (7/30, 표본 148건)

| 최소 | 평균 | p95 | 최대 |
|---:|---:|---:|---:|
| 136자 | 1,251자 | 1,984자 | 2,757자 |

생성기는 이 분포를 목표로 맞춘다. 덧붙여 이 값은 별도 이슈로 뺀 "임베딩 입력 길이 상한 없음" 건의 실제 위험도 알려준다 — 최대가 2,757자면 bge-m3의 8,192 토큰 한계에서 멀어 **현재 데이터에서는 상한 없음이 문제를 일으키지 않는다.**

#### 주의 — 주제 다양성

지금은 exact KNN·GIN 없는 FTS라 전량 스캔이다. 내용과 무관하게 건수에만 비례하므로 합성 데이터로 충분하다.

다만 **코퍼스를 키워 ANN 도입 시점을 잴 때는 벡터 분포가 결과를 좌우한다.** 같은 문장을 재조합하면 벡터가 뭉쳐 실제보다 좋게 나온다. 말뭉치를 여러 분야에서 고르게 뽑아 어휘와 주제를 분산시킨다.

### 2.4 참고 지표

판정에 쓰지 않고 해석 기준으로만 쓴다.

| 지표 | 참고선 | 출처 |
|---|---|---|
| retrieval p95 | 1,000ms | Nielsen — 사고 흐름이 끊기지 않는 한계 |
| 쿼리 임베딩 | 현재 약 430ms | 공개 사례 대비 한 자릿수 느림(BGE-M3 CPU 약 31ms) |
| 영상 Pipeline total | 133.066초 (7/20 기준선) | 회귀 확인용 |
| STT 배치 요청 | 분당 106건 (`us_batch_requests_count`) | Google STT v2 할당량 |

평균이 아니라 백분위수(p95·p99)를 쓴다.

STT 배치 요청은 색인 부하를 걸 때만 본다. STT 실패 시 재시도가 같은 파일을 새로 접수하는 구조라(`google_stt_adapter.py`), 실패가 나면 영상 하나당 최대 4배로 늘어난다. 이 값이 한도에 붙으면 그때 나오는 429는 Google 쪽 문제가 아니라 우리가 만든 것이므로, 병목 판정 전에 먼저 확인한다. Cloud Monitoring `serviceruntime.googleapis.com/quota/rate/net_usage`에서 읽는다.

### 2.5 부하 시나리오 모양

| 모델 | 정의 | 쓰는 곳 |
|---|---|---|
| 닫힌 모델 | 가상 사용자 N명이 검색 → 생각 시간 → 반복 | 실사용에 가까운 형태 |
| 열린 모델 | 초당 도착률 고정, 응답 지연과 무관하게 계속 투입 | **한계 탐색.** 서비스가 느려져도 부하가 안 줄어 큐 적체가 드러남 |

한계 탐색은 열린 모델로 한다. 닫힌 모델은 응답이 느려지면 부하도 같이 줄어 한계가 실제보다 높게 보인다.

## 3. 측정 대상

| 구분 | 대상 | 판정 | 이유 |
|---|---|---|---|
| 우리 것 | 임베딩 VM, PostgreSQL, Cloud Run, 검색 코드 | 포함 | 설정·설계를 바꿀 수 있다 |
| 외부 | Gemini(LLM), STT, Vision | 제외 | 성능 통제 불가 + 대량 호출 비용 |

```
판정 구간 = query embedding + FTS + vector search + SOT gate
            (LLM·프롬프트 조립·스냅샷 저장 제외)
```

`search.execute.timing` 로그의 단계별 값을 합산한다(#103 구현). 근거는 7/28 실측에서 검색 응답 시간의 **96.9%가 LLM 단계**였다는 것(평균 16.4초, 최대 41.2초).

**Gemini는 속도 지표에서만 뺀다.** 프롬프트 개선을 통한 답변 품질 향상은 별도 이슈로 다룬다(측정 방법이 달라 같은 실험에 넣을 수 없음).

### mock 방침

- **주 시나리오** — LLM만 mock, 임베딩·DB는 실제 (`services/search-service/src/infra/llm/mock_adapter.py`)
- **보조 시나리오** — 임베딩도 mock, DB만 측정 (4장에서 임베딩 병목을 건너뛸 때도 사용)
- **검증용** — 실제 Gemini E2E 소량 실행, mock과 현실의 괴리 확인

## 4. 막히는 지점 찾기

### 4.1 방법

전체 경로 테스트와 개별 컴포넌트 테스트를 구분한다.

```
0. Deployment Diagram·Value Stream Map·병목 가설표를 작성한다
1. 현재 구성 그대로 전체 경로에 부하를 올린다 → 깨질 때까지
2. 처음 막힌 지점과 실패 방식을 기록한다
3. 뒤쪽 확인이 필요하면 같은 배포환경의 해당 컴포넌트에 직접 부하를 준다
4. 확인한 병목 중 하나의 개선안을 적용한다
5. 같은 조건에서 전체 경로를 다시 측정한다

멈추는 때: 개선 1건을 같은 조건에서 검증했거나,
          확인한 병목이 읽기 복제본·샤딩처럼 범위 밖 작업을 요구할 때
```

특정 지점까지 부하를 보내기 위해 앞단 인스턴스를 스케일 아웃하거나 동시성을 임의로 늘리지 않는다. 그렇게 해야만 뒤쪽에 부하가 도달한다면, 그 사실 자체를 현재 구조의 결과로 기록한다.

**앞단을 풀어야만 뒤가 보인다는 것은 아키텍처 문제의 신호로 읽는다.** 그 방법이 무의미해서 안 하는 게 아니라, 그렇게까지 해야 테스트가 된다는 상황 자체가 결과이기 때문이다. 그래서 이 관찰은 "측정 불가"가 아니라 "여기서 잘려 뒤는 부하를 받아본 적이 없다"는 기록으로 남긴다.

이 관점은 개선안 선택에도 영향을 준다. 앞단이 병목일 때 후보가 "동시 처리 수를 올린다" 하나로 좁아지지 않는다. 왜 그 자리에 단일 슬롯이 강제되는지, 작업 단위를 줄여 같은 자원으로 더 잘게 흘릴 수 있는지까지 후보에 들어간다(6장).

개별 컴포넌트 테스트는 전체 시스템의 처리량을 뜻하지 않는다. 예를 들어 PostgreSQL을 확인할 때는 임베딩을 mock하거나 DB 검색 경로를 직접 호출하고, 임베딩 VM을 확인할 때는 해당 배포 인스턴스에 직접 요청한다. 테스트 진입점과 제외한 앞단을 결과에 함께 적는다.

**어느 설정을 개선할지는 미리 정하지 않는다.** 실제로 막힌 지점을 보고 후보를 선택한다. 개선 뒤 다음 병목이 드러나면 그것도 결과지만, 뒤쪽을 보기 위한 목적으로 운영할 계획이 없는 설정을 적용하지 않는다.

각 번(1번째, 2번째, …)은 5장 양식으로 기록한다.

### 4.2 지금 조정 가능한 설정

측정해서 정한 값은 하나도 없다. 전부 기본값이거나 개발 중 편의로 잡은 숫자다.

**임베딩 VM** — 검색용(`10.20.3.15`)과 배치용(`10.20.3.14`) 2대. 아래 값은 **두 VM이 같은 변수를 공유해서 한쪽만 따로 바꿀 수 없다.**

| 설정 | 현재 |
|---|---:|
| 동시 처리 수 (`MAX_CONCURRENCY`) | 1 |
| 검색 요청 상한 | 32 |
| 색인 요청 상한 | 4 |
| 검색 대기 상한 | 5초 |
| 색인 대기 상한 | 20초 |
| VM 크기 | e2-standard-4 |
| VM 대수 | 각 1대 (module 블록에 IP가 박혀 있음) |

**Cloud Run** (7/30 배포 실측)

| 설정 | 현재 |
|---|---:|
| 검색 서버 최소·최대 대수 | 0 / 3 |
| 색인 워커 최대 대수 | 1 |
| 색인 워커 프로세스 동시성 (`WORKER_CONCURRENCY`) | 4 |
| 검색 서버 인스턴스당 동시 요청 상한 (`containerConcurrency`) | 80 |
| 색인 워커 〃 | 80 |
| 검색 서버 자원 | cpu 1 / mem 512Mi |
| 색인 워커 자원 | cpu 1 / mem 4Gi |

**애플리케이션**

| 설정 | 현재 | 위치 |
|---|---:|---|
| DB 커넥션 풀 | 5+10, 대기 30초 | `search-service/src/infra/db/session.py:5` (설정한 적 없음) |
| 청크 최대 어절 수 (`CHUNK_MAX_TOKENS`) | 300 | `pipeline-worker/src/config/settings.py:76` |
| 임베딩 배치 크기 (`EMBEDDING_BATCH_SIZE`) | **4** | Terraform 기본값. 배포 실측(7/30) |
| 임베딩 호출 상한 (`EMBEDDING_TIMEOUT_SEC`) | 색인 180초 / 검색 15초 | 배포 실측(7/30) |

배치 크기는 코드 기본값(`settings.py:76`)이 16이지만 **배포된 값은 4**다. Terraform 기본값이 4이고 `gcloud run services describe`로 확인했다. 7/28 실험의 배치 추론 20.794초는 **청크 4개를 한 번에 처리한 시간**이므로 청크당 약 5초다.

**받아들이는 양과 처리할 수 있는 양의 격차** — `containerConcurrency` 80 × 3대 = 요청 240건을 동시에 받지만, DB 커넥션은 3 × 15 = 45개이고 임베딩 VM 동시 처리는 1이다. 앞단에서 거절하지 않고 받아 뒤에서 대기하다 실패하는 구조라 병목 가설표에 포함한다.

이 값들은 **뒤쪽으로 부하를 보내기 위한 우회 수단이 아니라 개선 후보**다. 실제 병목으로 확인한 뒤 운영 가능한 후보로 판단했을 때만 바꾸고, 6장의 기준에 따라 같은 조건에서 전후를 비교한다. 뒤쪽 컴포넌트의 한계만 필요하면 이 값을 임의로 바꾸는 대신 4.1의 개별 컴포넌트 테스트를 사용한다.

### 4.3 DB 커넥션 풀 대기 30초

`session.py:5`가 `create_async_engine(database_url, future=True, pool_pre_ping=True)`뿐이라 SQLAlchemy 기본값이 적용된다.

```
pool_size 5 + max_overflow 10  →  인스턴스당 최대 15 커넥션
pool_timeout 30초              →  풀 고갈 시 30초 대기
```

임베딩 대기 상한 5초의 6배다. 커넥션이 동나면 빠르게 503으로 실패하는 대신 **30초를 기다렸다 실패한다.** 현재 Cloud Run max 3 × 15 = 45라 동시 20건 수준으로는 도달하지 않는다.

### 4.4 규칙

1. **전체 경로 테스트와 개별 컴포넌트 테스트를 구분한다.** 둘의 처리량을 같은 의미로 보고하지 않는다
2. 특정 컴포넌트까지 부하를 보내기 위해 앞단 인스턴스 수나 동시성을 임의로 늘리지 않는다
3. 개선안을 검증할 때는 **한 번에 값 하나만 바꾼다.** 두 개를 같이 바꾸면 원인을 특정할 수 없다
4. 매번 5장 양식으로 기록하고, 부하를 뺀 뒤 자동 회복되는지 확인한다

## 6. 개선안 선택과 검증

### 6.1 후보 유형

4장에서 찾은 병목 중 **하나만** 골라 고친다.

| 유형 | 예 | 비용 |
|---|---|---|
| 설정값 | 커넥션 풀, `MAX_CONCURRENCY`, 대기 상한 | 0 |
| 인덱스 | FTS GIN, 벡터 인덱스 | 0 |
| 코드 | 쿼리 구조, 배치 방식 | 0 |
| 자원 추가 | VM 크기·대수, 인스턴스 수 | 있음. 기록 필수 |

**벡터 인덱스 — ADR-012 근거.** ADR-012(제안됨, 2026-06-01) §5는 현재 벡터 검색이 exact KNN이며 ANN 인덱스를 두지 않는다고 명시한다. 미도입 사유는 ①데이터 규모가 작음 ②임베딩 차원 미확정. 도입할 때는 버전 간 벡터 공간이 섞이지 않도록 버전별 부분 인덱스 또는 `index_name` 기준 리스트 파티셔닝을 쓴다.

현재 상태는 `search_repository.py:343`의 `ORDER BY vie.embedding_vector <=> CAST(:query_embedding AS vector)`이고, 벡터 인덱스도 FTS GIN 인덱스도 없다.

**운영 DB 인덱스 실측 (7/30)**

| 테이블 | 인덱스 |
|---|---|
| `chunk` | `chunk_pkey` 하나뿐 — **FTS GIN 없음** |
| `vector_index_entry` | `vector_index_entry_pkey(index_name, chunk_id)`, `idx_vector_index_entry_project_index(project_id, index_name)` — **벡터 인덱스 없음** |
| `video` | pkey, `idx_video_project_id`, `idx_video_user_created`, `idx_video_user_status` |
| `project` | pkey, `idx_project_lifecycle_state`, `idx_project_search_serving_state`, `idx_project_user_created` |

**EXPLAIN으로 확인한 실행 계획** — `WHERE index_name=... AND project_id=... ORDER BY embedding_vector <=> q.v LIMIT 5`

```
Limit → Sort (top-N heapsort, Memory 25kB)
      → Nested Loop
      → Seq Scan on vector_index_entry (Filter, Rows Removed by Filter: 110)
Buffers: shared hit=359 read=41
Planning 1.526ms / Execution 6.291ms  (168건 중 58건 정렬)
```

`idx_vector_index_entry_project_index`가 있는데도 플래너가 Seq Scan을 골랐다. 168행·5버퍼라 인덱스를 타는 비용이 더 크기 때문이다. 코퍼스가 커지면 필터는 인덱스를 타겠지만 **정렬은 매칭된 전체 행을 훑는다.** 벡터 검색이 코퍼스 크기에 선형 비례한다는 예상은 이 구조에서 나온다.

ADR은 "데이터 규모가 커지는 시점에 도입"이라고만 적고 그 시점을 정의하지 않았다. **코퍼스를 키우면서 "청크 몇 건부터 exact KNN이 참고선을 못 지키는가"를 재면 그 값이 ADR이 비워둔 도입 임계점이 된다.**

### 6.2 인프라 설정 변경도 해결책이다

4.1에서 봤듯 현재 값은 미검증 기본값이라 원래 값으로 되돌릴 이유가 없다. 다만 근거를 붙인다.

- 왜 그 숫자인지 (측정으로 특정)
- 어디부터 더 늘려도 안 좋아지는지 (수확 체감 지점)
- 대안 대비 왜 이건지 (비용 포함)

**"더 늘려도 안 좋아지는 지점"을 찾는 것이 이 이슈의 가장 좋은 산출물이 될 수 있다.**

### 6.3 검증 규칙

1. **전후를 같은 조건에서 잰다** — 코퍼스, 질의 목록, 부하 종류, mock 여부 동일
2. **"후" 설정이 지속 부하에서도 유지되는지** 1회 확인
3. 비용이 늘면 얼마인지 기록
4. 3회 반복해 run별 p95의 중앙값과 범위를 쓴다. 여러 run을 합쳐 하나의 표본으로 만들지 않는다

| 항목 | 값 |

예산이 충분해 계정 추가나 환경 이전은 하지 않는다. 신규 프로젝트는 vCPU 할당량이 낮아 큰 부하를 못 걸고, Terraform 재적용·시크릿·이미지 재푸시·DB fixture 재생성에 최소 한 세션이 든다.

### 7.2 챙길 것

| # | 항목 | 이유 |
|---|---|---|
| 1 | **k6를 같은 리전 GCP VM에서 실행** | 노트북에서 쏘면 집 회선이 먼저 한계에 걸린다. e2-medium이면 충분(시간당 약 40원) |
| 2 | **PostgreSQL VM은 `stop`만, `destroy` 금지** | 부팅 디스크에 DB가 있어 5만 청크 fixture가 날아간다 |
| 3 | 세션 종료 시 VM stop + 워커 min=0 복귀 | 켜둔 채 두면 하루 $22~30 |
| 4 | Billing 예산 알림 | 잔액 기준 임계값 |
| 5 | 측정 중 Search Service min=1 고정 | cold start는 별도 기록 |
| 6 | ~~측정 전 `pg_indexes`·`max_connections` 확인~~ | **7/30 완료.** `max_connections=100`, 인덱스 현황은 6.1 참고 |
| 7 | fixture는 manifest·hash·Git SHA 기록 | 재현용 |
| 8 | ~~`enriched_text` 길이 분포 조회~~ | **7/30 완료.** 2.3 참고 |
| 9 | 측정마다 코퍼스 건수를 기록 | 출발점 168건. 규모가 바뀌면 결과 해석 조건이 바뀐다 |

**PostgreSQL 기본 설정 실측 (7/30)** — `max_connections=100`, `shared_buffers=128MB`, `work_mem=4MB`. 셋 다 기본값이고 조정한 적이 없다. `shared_buffers` 128MB는 e2-standard-4(16GB)에서 작은 편이라, 코퍼스가 커진 뒤 버퍼 적중률이 떨어지면 개선 후보가 될 수 있다.

### 7.3 로컬 도커 (보조)

`docker-compose.yml`에 전체 스택이 뜬다. GCP에서 하기 어려운 것만 맡긴다 — 부하 중 컨테이너 강제 종료 같은 장애 주입, 깨고 고치기 수십 회 반복.

**로컬 절대 수치는 보고서에 쓰지 않는다.** 하드웨어가 달라 전이되지 않는다. 전이되는 건 고장의 모양(순서, 회복 여부, 연쇄 여부)뿐이다.

- 용량 산정(capacity planning) — 상정 사용자 수를 정하지 않으므로 "MAU N명까지 감당" 형태의 결론은 내지 않는다. 결과는 절대 수치와 구성으로만 보고한다(2.1)
