# Biblio 영상 파이프라인 처리능력 테스트 계획

- 작성일: 2026-08-13
- 상태: 실행 대기

## 1. 목적

현재 배포 구성에서 영상이 여러 건 들어왔을 때의 처리량, 대기시간, 병목과 실패 형태를 기준선으로 남긴다. 이후 개선은 같은 영상과 같은 부하 조건으로 다시 측정해 판단한다.

결과는 사용자 수로 환산하지 않고 아래처럼 구성과 함께 기록한다.

> pipeline-worker 1대, worker 동시성 4, 고정 영상셋에서 동시 요청 8건의 완료 처리량·queue 대기 p95·단계별 p95

## 2. 측정 범위

측정 경로는 test driver의 `/complete` 요청 시작부터 `READY` 또는 `FAILED`까지다.

```text
POST /videos/{video_id}/complete
→ PGMQ 대기
→ 다운로드 → 오디오 추출 → STT → Vision 보강 → 임베딩 → DB 저장
→ READY | FAILED
```

- 실제 GCP 성능 환경과 실제 STT·Vision·배치 임베딩 VM을 사용한다.
- 파일 업로드 시간은 제외한다. 모든 파일을 먼저 업로드하고 `/complete` 호출 시각부터 측정한다.
- 검색 부하는 함께 주지 않는다. 영상 처리 기준선과 검색 경합 테스트를 분리한다.
- 설정과 인스턴스 수는 테스트 도중 바꾸지 않는다.
- 장시간 지속 부하와 최대 사용자 수 환산은 범위 밖이다.

## 3. 실행 전 준비

### 3.1 계측

다음 계측은 이미 있으므로 수정하지 않고 그대로 사용한다.

- `pipeline.timing`: 영상별 `download`, `audio`, `stt`, `chunk_enrichment`, `embedding`, `persist`, 전체 처리시간
- `embedding.admission`: 임베딩 요청의 queue 대기시간, queue depth, 허용·거절 결과
- `scripts/load-test/target-vm-sampler.sh`: 임베딩 VM의 host·container·endpoint process CPU와 메모리 시계열
- Cloud Monitoring: pipeline-worker 인스턴스 수, CPU, 메모리

아래 계측만 추가한다.

| 값 | 계산 기준 |
|---|---|
| API·발행시간 | PGMQ enqueue 시각 - `/complete` 요청 시작 시각 |
| queue 대기시간 | consumer 처리 시작 시각 - PGMQ enqueue 시각 |
| 전체 처리시간 | 영상의 최종 상태 기록 시각 - `/complete` 요청 시작 시각 |
| 전체 완료시간 | 마지막 영상의 최종 상태 기록 시각 - 첫 `/complete` 요청 시작 시각 |
| 처리량 | 성공한 영상 수 / 전체 완료시간 |

추가 작업은 다음으로 제한한다.

1. test driver가 `/complete` 요청 시작·응답 시각과 최종 상태 확인 시각을 저장한다.
2. PGMQ client가 현재 버리는 `enqueued_at`과 `read_ct`를 `BrokerMessage`에 보존한다. consumer 시작 로그에는 `trace_id`, `video_id`, `issued_at`, `enqueued_at`, `read_ct`, 처리 시작 시각을 남긴다. `attempt`는 발행 재시도, `read_ct`는 queue 재전달 횟수로 구분한다.
3. 각 단계의 시작·종료 로그에 `timestamp_utc`, `trace_id`, `video_id`, `stage`, `event=started|finished`, `status`를 남긴다. 실패해도 `finished` 로그를 남긴다.
4. preprocess queue의 ready·invisible 수와 가장 오래된 메시지 나이를 5초 간격으로 저장한다.
5. 실행 후 단계 구간과 자원 표본을 UTC 기준으로 합쳐 `timeline.csv`를 만든다. 보간하지 않으며 각 자원 표본의 실제 시각을 유지한다.
6. smoke test에서 Cloud Monitoring 표본이 한 단계에 3개 미만이면, 테스트 환경에서만 worker process CPU·RSS를 1초 간격으로 기록한다. 이 경우에도 Cloud Monitoring 원본은 함께 보존한다.

`timeline.csv`에는 자원 표본 시각마다 실행 중인 영상 수, 단계별 실행 수, queue depth, worker CPU·메모리, 임베딩 VM CPU·메모리와 자원 표본 출처를 기록한다. 한 영상에서 여러 단계가 동시에 진행되지 않으므로 단계별 실행 수의 합은 실행 중인 영상 수와 같아야 한다.

### 3.2 고정 영상셋

아래 세 파일을 정하고 `fixtures.json`에 경로, SHA-256, 길이, 크기, codec, 해상도를 기록한다.

| 구분 | 길이 | 용도 |
|---|---:|---|
| short | 2~3분 | 짧은 작업의 대기시간 확인 |
| medium | 10~15분 | 기본 처리량 측정 |
| long | 25~30분 | STT 분할과 긴 작업 점유 확인 |

- 같은 구분의 동시 요청에는 같은 파일의 복제본을 사용한다.
- 매 실행마다 새 `video_id`와 새 GCS object key를 사용한다. 기존 `READY` 영상을 재사용하지 않는다.
- 측정 전에 각 파일 1건이 `READY`까지 가는 smoke test를 통과해야 한다.

### 3.3 환경 고정

실행 시작 시 다음을 `environment.json`으로 저장한다.

- git SHA와 각 배포 image digest
- pipeline-worker 최소·최대 인스턴스, CPU, 메모리, `WORKER_CONCURRENCY`
- STT part 길이·overlap·동시성
- preprocess visibility timeout과 stale processing reclaim 시간
- Vision model·동시성·timeout
- embedding model·batch size·timeout과 배치 VM 사양
- DB VM 사양과 주요 connection pool 설정
- 실행 시작·종료 시각, GCP project·region

성능 환경의 기본값 `min_instance_count=0`은 PGMQ 메시지만으로 worker를 기동하지 못하므로 처리능력 기준선에는 사용하지 않는다. 테스트 시작 전에 pipeline-worker를 `min=1`, `max=1`로 고정하고 ready 로그를 확인한다. 이 결과는 **warm 1-instance 기준선**으로 명시하며 개선 전후에 같은 값을 사용한다. 테스트와 정리가 끝나면 `min=0`으로 복구한다. cold start와 scale-out은 별도 테스트로 분리한다.

preprocess, delete, project-delete queue가 모두 비어 있고 feedback-loop의 batch·reindex 작업과 다른 부하 테스트가 실행 중이 아닐 때만 시작한다. 이 조건은 매 반복 전에도 확인한다.

## 4. 테스트 시나리오

각 시나리오는 3회 실행한다. 반복 사이에는 세 worker queue가 모두 비었고 이전 영상이 모두 최종 상태인지 확인한다.

| ID | 요청 방식 | 확인할 내용 |
|---|---|---|
| S1 | short·medium·long 각 1건을 순차 실행 | 길이별 단계 시간과 단일 영상 기준선 |
| S2 | medium 4건 동시 발행 | 현재 worker 동시성 4의 처리량과 자원 경합 |
| S3 | medium 8건 동시 발행 | 4건 처리 중 나머지 4건의 queue 대기와 backlog 해소 |
| S4 | long 4건 동시 발행, 10초 뒤 short 4건 발행 | 긴 작업이 짧은 작업을 미루는 정도 |

동시 발행은 첫 요청과 마지막 요청의 발행 시각 차이가 1초 이내여야 한다. 조건을 벗어나면 해당 반복은 다시 실행한다.

test driver는 S1~S4를 기본 preset으로 제공하되 요청 수, 동시성, 반복 횟수, fixture
구성, phase 간 지연을 실행 인자로 조절할 수 있게 한다. S1~S4의 기본값과 일치하는
실행만 기준선 비교에 사용하고, 값을 바꾼 실행은 탐색 실험으로 구분한다. 실행 전에는
선택한 값, 총 요청 수와 fixture 총길이를 출력한다.

비용 계산과 승인 책임은 driver에 넣지 않는다. 실제 실행 전에 에이전트가
`scripts/gcp/billing/`의 BigQuery billing query로 최근 서비스·resource 비용을 조회하고,
driver가 출력한 workload를 기준으로 예상 비용 범위와 추정 근거를 사용자에게 제시한다.
사용자가 승인한 뒤에만 실제 요청을 발행한다. billing export는 과거 실비이므로 예상
비용을 확정값으로 표현하지 않는다.

S3까지 실패 없이 queue가 해소되더라도 요청 수를 임의로 늘리지 않는다. 더 큰 범위가 필요하면 S3 결과와 비용을 확인한 뒤 12건, 16건을 별도 실험으로 추가한다.

## 5. 수집 항목

### 5.1 결과 지표

- 성공·실패·재시도·timeout 건수와 실패 단계
- 영상별 queue 대기시간, 처리시간, 전체 처리시간
- 단계별 `download`, `audio`, `stt`, `chunk_enrichment`, `embedding`, `persist` 시간
- 시나리오 전체 완료시간과 시간당 완료 영상 수
- short 영상이 long 영상 뒤에서 기다린 시간
- 최대 동시 실행 영상 수와 단계별 동시 실행 수

각 시나리오는 반복별 원시값을 보존한다. S1은 short·medium·long을 섞지 않고 fixture별 3회 중앙값과 범위를 쓴다. S2~S4는 전체 영상 표본의 p50·관측 p95·최댓값을 쓰고, 표본이 작아 모집단 p95 추정치가 아님을 명시한다.

### 5.2 자원과 외부 오류

- pipeline-worker 인스턴스 수, CPU, 메모리와 같은 시각의 실행 단계
- 배치 임베딩 VM CPU, 메모리와 기존 `embedding.admission`의 요청 대기·queue depth·거절 건수
- PostgreSQL CPU, connection 수와 느린 query
- STT·Vision·GCS의 429, 5xx, timeout
- preprocess queue depth와 가장 오래 기다린 메시지 나이

외부 API 오류도 버리지 않고 현재 운영 경로의 결과로 기록한다. 인증 실패, 잘못된 fixture, 계측 누락처럼 테스트 준비 문제만 무효 실행으로 분류한다.

자원 사용률은 단계와 queue 상태를 함께 보고 아래처럼 판정한다.

| 관측 | 판정 |
|---|---|
| 실행 영상 4건, STT·embedding 단계, queue 잔존, worker CPU 여유 | 전체 pipeline을 점유하는 동시성 슬롯이 병목인 후보 |
| ffmpeg·chunk 보강 중 worker CPU 포화 | worker 연산 자원이 병목인 후보 |
| embedding 대기 증가와 embedding VM CPU 포화 | embedding VM이 병목인 후보 |
| queue가 남았는데 실행 영상이 4건 미만 | queue 소비 또는 consumer 동작 이상 |

판정표에서 CPU 여유는 50% 미만, CPU 포화는 80% 이상이 10초 이상 지속된 상태로 정의한다. 임계값은 `environment.json`에 저장하고 반복 중 바꾸지 않는다. 메모리 사용률만으로 유휴 상태를 판정하지 않는다. 1초 worker 표본을 사용해도 한 단계에 표본이 3개 미만이면 그 단계의 자원 판정은 `자료 부족`으로 기록한다.

## 6. 실행 순서

1. 3.1의 추가 계측과 test driver만 구현하고 단위 테스트를 통과시킨다. 기존 `pipeline.timing`, `embedding.admission`, VM sampler는 재구현하지 않는다. driver는 S1~S4 preset과 실행 인자 override를 검증하고 실제 요청을 보내기 전에 선택한 workload를 출력한다. 에이전트가 BigQuery billing 자료로 예상 비용을 제시하고 사용자가 승인한 뒤 실행한다.
2. 환경·fixture manifest를 저장하고 short·medium·long smoke test를 실행한다.
3. S1 → S2 → S3 → S4 순서로 각 3회 실행한다.
4. 매 반복 뒤 세 queue 해소, 최종 상태, invisible message 재등장 여부와 자원 회복을 확인한다.
5. 로그·Monitoring·DB 상태를 `run_id`와 `trace_id`로 모아 결과 폴더에 저장한다.
6. 병목 하나와 개선 가설 하나를 선택한다. 개선에 필요한 image·설정 변경 목록과 이유를 기록하고, 그 밖의 환경은 기준선과 같게 유지한 채 S1~S4를 다시 실행한다.

## 7. 중단과 유효성 기준

S2~S4는 burst 전체를 먼저 발행하므로 아래 조건은 **현재 반복이 아니라 다음 반복을 중단하는 조건**이다. 이미 들어간 작업은 마지막 발행 후 `2 × QUEUE_VISIBILITY_TIMEOUT_SEC`까지 관찰한다.

- 실패 또는 timeout이 연속 2건 발생
- queue visibility timeout 안에 처리가 끝나지 않을 가능성이 생김
- worker 또는 DB 메모리 90% 이상이 5분간 지속
- STT·Vision quota 사용량이 한도의 80% 도달
- 사용자에게 승인받은 요청 수·반복 횟수 밖의 추가 실행이 필요함

관찰시간 안에 `PROCESSING` 또는 invisible message가 남으면 해당 반복을 실패로 기록하고 다음 반복을 시작하지 않는다. 원시 자료를 먼저 보존한 뒤 worker를 재기동해 stale claim 재수거를 기다린다. 모든 영상이 최종 상태가 된 후 test project를 기존 삭제 API로 정리하며 DB를 직접 수정하지 않는다. 정리가 끝나지 않으면 다음 시나리오로 진행하지 않는다.

결과 비교에 사용할 실행은 다음을 모두 만족해야 한다.

- 기준선 반복끼리는 fixture hash와 배포 구성이 일치함
- 개선 비교에서는 문서화한 변경 목록 외 환경 값이 기준선과 일치함
- 모든 요청의 `video_id`, `trace_id`, 발행·시작·종료 시각이 존재함
- 모든 영상의 각 단계에 `started`와 `finished`가 한 쌍으로 존재함
- 로그와 자원 표본이 실행 전체 구간을 덮음
- 세 worker queue와 공유 DB·embedding VM에 테스트 외 작업이 없었음
