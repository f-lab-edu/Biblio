# 문서 수정 검증 기준

> 이 기준은 수정된 문서 검증 전 반드시 읽고 숙지해야 한다. 임의로 검증되는 상황이 존재해선 안 된다.

---

## 검증 기준

### 1. SOT 정합성 (최우선)

- 수정된 내용이 `docs/system-design.md`와 모순되지 않는가?
- Gate Keeper가 인용한 SOT 근거 범위를 벗어난 수정이 없는가?
- system-design에 없는 내용이 임의로 추가되지 않았는가?

### 2. 교차 문서 일관성

- **직접 수정 파일 ↔ 연쇄 수정 파일**: 공유 계약(API, 메시지 스키마, 상태값, 변수명)이 양쪽에서 일치하는가?
- **수정된 파일 ↔ 미수정 파일**: "주의 확인" 대상 파일에 암묵적 충돌이 발생하지 않았는가?
- 용어, 기술스택, 에러 코드 체계가 전체 문서에서 통일되어 있는가?

### 3. 임의 추가 내용 검출

- 사전에 합의되지 않은 내용이 추가되지 않았는가?
- 변경 요청 범위를 벗어난 "개선" 수정이 없는가?
- 근거 없이 추가된 기술 선택, 정책, 수치가 없는가?

### 4. 수정 범위 준수

- Gate Keeper가 식별한 수정 대상 섹션만 변경되었는가?
- 범위 밖 섹션이 의도치 않게 변경되지 않았는가?

### 5. 완료 기준 유지

수정 후에도 문서가 여전히 아래 기준을 충족하는가?

- (1) 충분한 맥락
- (2) 구조 (디자인)
- (3) 요구사항 (제약사항 포함)
- (4) 검증(완료) 기준
- (5) AI Agent가 즉시 작업 할당 가능한 수준

### 6. 오버엔지니어링 검출

- 수정 과정에서 MVP 수준을 초과하는 사항이 추가되지 않았는가?

## 피드백 출력 형식

각 피드백 항목은 **구체적인 수정 지시** 형태로 작성한다:

```
[기준 N] [파일명] §X.X: 현재 "A"로 수정되었으나, system-design 기준 "B"로 변경 필요
[기준 N] [파일명] §X.X: 수정 범위를 벗어난 변경 — 원래 내용으로 복원 필요
[기준 N] [파일A] ↔ [파일B]: 메시지 스키마 불일치 — 필드 "X"가 파일A에만 추가됨
```

모든 기준을 통과한 경우 **PASS**를 명시한다.
